# dev-auth

`dev-auth` is a cross-platform, system-agnostic, account-agnostic credential adapter for one bounded automation principal shared by processes running as the same operating-system user. It has no provider-state model, deployment behavior, arbitrary vault browser, human-credential fallback, or owner-specific policy.

The workstation authority writes `config.toml` under the operating system's standard per-user application configuration directory and enrolls one 1Password Service Account token through `dev-auth enroll`. Enrollment reads standard input and writes directly to the configured native credential-store entry: Secret Service on Linux and WSL, Keychain on macOS, and Credential Manager on Windows. Each device requires one intentional enrollment because a credential cannot securely retrieve itself. The binary contains no vault name, account owner, GitHub owner, repository, installation ID, executable location, or operating-system account name.

Configuration declares the native credential-store service/account names, exact absolute executable paths, arbitrary `op://vault/item/field` references, GitHub App ID, installation selection mode, and exact permissions. Bare executable names and relative paths are rejected for built-in tools and declared execution profiles so a shadowed `PATH` entry cannot receive the Service Account token, a GitHub installation token, profile secrets, or signing-agent access. The workstation provisioner resolves trusted platform executables and renders their absolute paths; WSL uses paths inside its Linux environment, while native Windows uses drive-qualified paths. Dynamic mode asks GitHub’s authenticated `GET /repos/{owner}/{repo}/installation` endpoint for the requested repository, verifies the returned App ID, account, permission map, and suspension state, and then mints a token narrowed back to that one repository. GitHub’s App installations are therefore the live account/repository authority; a workstation list does not need to change when an all-repositories installation receives a new repository. Static installation and repository allowlists remain available for installations intentionally managed that way, and configuration must choose exactly one mode. The required permission map is Actions-read, Checks-read, Contents-write, Metadata-read, Pull-requests-write, and Statuses-read. Owner and repository matching is case-insensitive. See [GitHub’s repository-installation endpoint and installation-token contract](https://docs.github.com/en/rest/apps/apps#get-a-repository-installation-for-the-authenticated-app).

Configuration and cache roots come from the operating system's standard directories. Derived GitHub installation tokens live in the native credential store rather than plaintext cache files; the filesystem contains only scope-hash lock files for cross-process single-flight refresh. Unix builds additionally enforce owner-only modes, ownership, link count, and no-follow file opening. All builds reject symlinks and unexpected file types. A new build removes legacy file-backed token caches without reading or reporting their values.

Git config uses `credential.useHttpPath=true` and the standard `git-credential-dev-auth` helper only inside an automation-workspace `includeIf` scope. The parser accepts the protocol's blank-line or end-of-file termination, ignores unrecognized and multi-valued capability attributes, and rejects duplicate authority fields. A successful `get` returns a short-lived installation token and its expiry through the Git credential protocol. A failure returns `quit=true`, so Git cannot continue to a human credential helper or prompt. `store` discards input, and `erase` removes only the exact repository-scoped credential-store entry. The three frontend names are derived aliases of the same signed executable: Unix provisioning may use links, while Windows provisioning may use `.exe` hardlinks or identical verified copies. The binary recognizes both native forms without changing the credential protocol. See [Git credentials](https://git-scm.com/docs/gitcredentials), [Git credential protocol](https://git-scm.com/docs/git-credential), and [GitHub App installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

`gh-dev-auth` resolves one repository from `-R`/`--repo`, the positional `OWNER/REPOSITORY` accepted by `gh repo view`, `GH_REPO`, or the current Git origin. It consumes flag selectors, preserves the positional `repo view` selector, sets the child-only `GH_REPO` and `GH_TOKEN`, and invokes the configured upstream `gh`. Its admitted surface covers repository pull requests, Actions run observation, read-only workflow inspection, release downloads, and repository view. Authentication changes, user-level API calls, repository administration, issues, secrets, variables, workflow dispatch, repository cloning, and release publication fail before credential retrieval.

`dev-auth exec --profile NAME -- COMMAND ...` runs only an exact absolute executable path declared by that profile and supplies only its declared 1Password fields. It clears the ambient environment, restores a small cross-platform runtime allowlist, and never passes the Service Account token to the child.

`dev-auth agent --profile NAME` is the one cross-platform SSH isolation boundary. It retrieves only the two declared unencrypted Ed25519 keys, accepts the native OpenSSH or PKCS#8 representation returned by supported 1Password SSH Key items, and verifies their SHA-256 fingerprints before listening. It keeps the keys only in zeroizing process memory and implements only identity listing, signing, and explicit purge; it does not accept key additions or expose a general key store. Linux, WSL, macOS, and other Unix systems use a private current-user Unix socket; native Windows uses a per-configuration, remote-client-rejecting named pipe instead of Microsoft’s shared OpenSSH agent service. `dev-auth agent-endpoint` prints the nonsecret endpoint for process or service configuration. On Linux, a process launched without `XDG_RUNTIME_DIR` safely rejoins the current user-owned `/run/user/<uid>` runtime when it exists. `dev-auth ssh-load --profile NAME` is an exact readiness check for the running agent. `ssh-keygen-dev-auth` restricts Git signing to that agent, the `git` namespace, and the declared signing fingerprint, while delegating only Git's public `find-principals` and `verify` operations to the configured OpenSSH executable. Private keys are never written to a persistent file.

WSL is a native Linux deployment of `dev-auth`, not a bridge to the Windows process. Its configuration, Secret Service entry, runtime cache, Unix socket, and lifecycle are independent of native Windows. This preserves operation when Windows interoperability is disabled and prevents either environment from silently falling back to the other environment’s human credentials. A workstation authority may enroll the same bounded Service Account principal into both environments, but each enrollment remains intentional and each runtime ends with its own user session.

The Service Account should have immutable `read_items` access only to its declared machine-credential vault. Its token is an enrollment credential, not an interactive desktop session or a replacement for human 1Password access. See [1Password Service Accounts](https://developer.1password.com/docs/service-accounts/get-started/) and [1Password SSH-agent security](https://developer.1password.com/docs/ssh/agent/security/).

GitHub transport/API identity and commit authorship are separate. HTTPS Git and the bounded GitHub CLI wrapper authenticate as the configured GitHub App. Commits and tags use the declared automation signing key. Host authentication uses the other declared key. Higher-risk GitHub administration, workflow modification, public publishing, infrastructure apply, identity administration, and human-vault access remain outside this product.
