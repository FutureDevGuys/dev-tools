# dev-auth

The current general-purpose implementation and release gaps are tracked in [executable acceptance](dev-auth-acceptance.md). `dev-auth doctor [--json]` provides local observation without retrieving credentials or contacting the broker/provider; its invoked version helps distinguish a retained executable from the intended installation. `workload launch` has explicit noninteractive and separate result-file controls with the limits documented there.

The unreleased 0.4 source adds logical `secret read`, `secret public` and `secret exec` operations. These require existing admitted v3 authority; they do not enroll credentials or silently upgrade installed policy. `secret exec` selects projections explicitly with `--stdin RESOURCE`, `--fd FD=RESOURCE`, `--file VARIABLE=RESOURCE` or `--env VARIABLE=RESOURCE`, followed by `-- COMMAND ...`. Linux file-path delivery uses an anonymous sealed memory file exposed only through the child's descriptor path. Secret bytes and child streams never share stdout with control JSON; `--result-file` selects a separate protected value-free observation. See [logical delivery](adr/0040-dev-auth-logical-delivery-and-native-projections.md) and [native enrollment-authorized launch](adr/0041-dev-auth-enrollment-authorized-native-launch.md) for the source contracts and remaining native qualification.

The same unreleased source accepts explicit v3 authority through setup discovery and planning. `setup template administrator-policy-v3`, `setup template user-only-policy-v3` and `setup template user-config-v3` provide fictional examples requiring approval; the unversioned template names retain their v2 contents. V3 setup plans identify the authority schema and use separate versioned user-document paths. Named providers are checked independently and user-only policies can only narrow the administrator's resource, operation, admission and duration caps. This does not yet constitute production migration acceptance: retained policy/integration rollback and admission exclusion during replacement remain required under [the versioned setup contract](adr/0042-dev-auth-versioned-setup-authority.md).

`dev-auth --version` emits the stable product/version line, and `dev-auth build-info --json` emits the common `dev-tools-build-info-v1` document from build-time values without configuration, credential, broker or repository access. The existing no-argument `dev-auth build-info` output and library `BuildInfo` API retain their three-field release-verification format. That compatibility path remains until release/setup consumers use the common document and the last receipt-owned 0.3 rollback generation requiring the old shape has left its acceptance window; removal requires release and rollback tests against those consumers.

`dev-auth completion bash|zsh|fish|elvish|powershell` prints static shell code for implemented public commands without loading configuration or credentials, contacting the broker, or editing startup files. Private helper entrypoints and runtime profile names are not suggested. The command remains behind normal frontend identity checks; it is not an alternate entry into setup, workload or credential operations.

> The v0.3 branch is a standalone transparent workload-identity broker. The detailed v0.2 behavior below remains the rollback contract until Linux strong-mode acceptance and cutover are complete.

## Standalone v0.3 ownership

The signed dev-auth release owns authenticated stable-release selection, immutable versioned installation, product aliases, session-private Git/gh aliases, policy/config validation, credential enrollment, systemd and polkit assets, workload/desktop launchers, setup-plan v3, verification, repair, rollback, uninstall, and state purge. `dev-auth setup discover` checks fixed platform prerequisites and reports structured absent, unsafe, or unsupported blockers with common Arch, Debian, and Fedora package hints for native Git, GitHub CLI, 1Password CLI, OpenSSH, polkit, systemd, cgroup v2, and pidfd support. Supplying `--administrator-policy PATH` and one or more `--user-config USER=PATH` inputs makes the report use the policy's exact Git, gh, 1Password, SSH, sandbox, and workload executable authorities plus the generated desktop-entry locations. The complete nonsecret input shape is published as [deployment-v1.example.toml](../crates/dev-auth/deployment-v1.example.toml). Workload product names and paths are never built into dev-auth. Discovery never trusts caller `PATH` and never invokes a platform package manager. Dev Tools and Syscfg source checkouts are not runtime dependencies.

`dev-auth setup plan` normalizes deployment TOML and equivalent CLI inputs into one value-free desired-state plan. `dev-auth setup apply` revalidates the approved digest, release, documents, native accounts, current state, and credential inputs before mutation. It stages the inactive release first and accepts credentials only through standard input, a private file descriptor, or an approved private file. A missing required credential leaves the candidate inactive and returns structured `input_required`; rerunning the same approved plan resumes without installation churn. The first strong installation runs as an authenticated root bootstrap and installs a distinct receipt-owned setup helper. Later native-user applies may add `--authorize sudo`, which validates that helper and delegates exactly one approved root-custodied v3 transaction; it is not a password channel, sudo keepalive, shell runner, or reusable privileged service. `dev-auth setup verify --plan PATH --sha256 HEX --format json` non-mutatingly checks the complete approved postcondition, including release, policy, every native account integration, credential intent, and broker state. Setup activates receipt-owned same-name `git` and `gh` launchers only after the broker and credentials verify; outside an admitted workload those launchers replace themselves with the administrator-pinned native tool without interpreting its arguments, while admitted workloads also receive a private `git`/`gh` tool plane. Rollback stops the broker before atomically swapping the shared active/previous release and its authenticated product metadata. Uninstall removes only receipt-owned artifacts and preserves policy and credential state until a separate purge.

The strong Linux supervisor renews each 15-minute admission lease while it owns the complete transient systemd workload. A broker restart does not promote environment hints into authority: the root supervisor retries for a bounded 30-second window and can re-register only the same session, authority, root-owned cgroup, and still-live supervisor pidfd. Broker-backed operations fail closed during that window, and an unprovable boundary terminates the supervised workload before its authority can resume.

The generic `dev-tools-reconcile-v1` surface deliberately exposes only current-user configuration reconciliation:

```text
dev-auth reconcile plan --source PATH --output PLAN --format json
dev-auth reconcile apply --plan PLAN --sha256 HEX --format json
dev-auth reconcile verify --source PATH --format json
```

Each operation binds the installed release, native account, administrator/user-only policy, source document, installed destination, and exact precondition identities. It returns the common value-free result schema for `sync-configs`. When invoked through sudo, planning publishes the nonsecret mode-`0600` plan to the verified native sudo caller so the configuration client can approve its digest without gaining access to broker credentials. If the standalone installation, administrator policy, or strong broker is absent, planning returns a value-free structured deferred result. The reconciler cannot install releases, change administrator policy, manage broker services, activate launchers, or enroll credentials.

`dev-auth` is a cross-platform, system-agnostic, account-agnostic credential adapter for one bounded automation principal shared by processes running as the same operating-system user. It has no provider-state model, deployment behavior, arbitrary vault browser, human-credential fallback, or owner-specific policy.

The workstation authority writes `config.toml` under the native current-user application configuration directory and enrolls one 1Password Service Account token through `dev-auth enroll`. Enrollment reads standard input and writes directly to the configured native credential-store entry: Secret Service on Linux and WSL, Keychain on macOS, and Credential Manager on Windows. Each device requires one intentional enrollment because a credential cannot securely retrieve itself. The binary contains no vault name, account owner, GitHub owner, repository, installation ID, executable location, or operating-system account name.

Configuration declares the native credential-store service/account names, exact absolute executable paths, arbitrary `op://vault/item/field` references, GitHub App ID, expected installation `repository_selection` (`all` or `selected`), exact permissions, and one optional Git workspace policy. The Git policy is the sole authority for workspace roots, automation author name/email, and the declared SSH profile used for signing. Roots may be absolute or use the portable `~/path` form; `~/` resolves from the native current-user account rather than caller-controlled `HOME`, `USERPROFILE`, XDG, or application-data variables. The complete account-neutral [example configuration](../crates/dev-auth/config.example.toml) is the supported schema example. Bare executable names and relative paths are rejected for built-in tools and declared execution profiles so a shadowed `PATH` entry cannot receive the Service Account token, a GitHub installation token, profile secrets, or signing-agent access. The workstation provisioner resolves trusted platform executables and renders their absolute paths; WSL uses paths inside its Linux environment, while native Windows uses drive-qualified local paths. Dynamic mode asks GitHub’s authenticated `GET /repos/{owner}/{repo}/installation` endpoint for the requested repository, verifies the returned App ID, account, repository selection, permission map, and suspension state, and then mints a token narrowed back to that one repository. GitHub’s App installations are therefore the live account/repository authority; a workstation list does not need to change when an all-repositories installation receives a new repository. Static installation declarations must match the same selection contract, and configuration must choose exactly one discovery mode. The required permission map is Actions-read, Checks-read, Contents-write, Metadata-read, Pull-requests-write, and Statuses-read. Owner and repository matching is case-insensitive. See [GitHub’s repository-installation endpoint and installation-token contract](https://docs.github.com/en/rest/apps/apps#get-a-repository-installation-for-the-authenticated-app).

Offline validation, `workspace-status`, and `git-dev-auth` share one native-current-user configuration locator, and each invocation binds one immutable file snapshot: `$HOME/.config/dev-auth/config.toml` on Linux and WSL where `$HOME` denotes the home from the effective user's account record rather than the caller environment, `~/Library/Application Support/dev-auth/config.toml` on macOS under the same account-record rule, and the current-user Roaming AppData `dev-auth/config/config.toml` path on Windows. Caller `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, `APPDATA`, and `LOCALAPPDATA` values cannot redirect that authority. Other runtime and cache roots come from the operating system's protected per-user directories. Derived GitHub installation tokens live in the native credential store rather than plaintext cache files; the filesystem contains only scope-hash lock files for cross-process single-flight refresh. The GitHub App ID is part of every cache scope, and refresh, erase, and purge share lifecycle locks so revoked credentials cannot be recreated by an already-running refresh. Dynamic cache reuse requires a successful live repository-installation lookup and an exact match of App ID, installation ID, repository, permissions, selection contract, and expiry; a lookup failure fails closed even when a cached token has not expired. Successful erase and purge operations remove the corresponding scope receipts after deleting their credential-store entries. Unix builds enforce owner-only modes, ownership, link count, and no-follow file opening. Native Windows builds additionally require current-user protected ACLs, require credential-bearing executables to reside on fixed local volumes that preserve ACLs, reject reparse and remote paths, and apply a current-user descriptor to every named-pipe instance. A new build removes legacy file-backed token caches without reading or reporting their values.

`git-dev-auth` is the generic same-name Git dispatch boundary. It loads one native-current-user configuration snapshot, classifies the current directory plus every admitted repository selector, environment selector, and clone/init path, and delegates to the configured human Git only when every path is positively proven unmanaged. An unknown option, alternate configuration, repository indirection, symlink/reparse repository path, managed-root ancestor, unsafe or ambiguous init/clone destination, or outside-to-managed target fails closed; it never retries through human Git after a managed error. Caller `PATH` entries are canonicalized so ordinary search-path aliases outside managed roots do not block routing, while any entry resolving into a managed root still blocks unmanaged fallback; managed execution replaces the caller search path entirely. A missing managed clone leaf is accepted only when its existing in-root parent is held as safe authority and the boundary can create, restrict, and revalidate an empty mode-0700 leaf before credentials are reachable. `dev-auth workspace-status` exposes the same config-only policy as a value-free routing query: `managed` exits 0, `unmanaged` exits 3, and an error emits no classification and exits 2. Neither route classification nor unmanaged delegation reads 1Password, the credential store, token caches, or the SSH agent. Offline `dev-auth validate` applies the same workspace-root existence, canonical-path, ownership, permissions, link/reparse, and non-overlap rules without reading a secret.

Inside a managed root, `git-dev-auth` admits an exact value-free `--version` query plus bounded status, exact-file staging, path-only restore/checkout, full-object-ID history, signed commit/tag, literal-origin fetch/push, and explicit GitHub clone forms. The version query executes only the configured identity-guarded Git with a sanitized environment and does not create private runtime state or inspect repository authority. Add, restore, and checkout require explicit safe relative file paths after `--`; broad staging and pathspec magic are unsupported. Reference-bearing restore/checkout, branch, switch, and symbolic or abbreviated history operands are unsupported until their exact source and transition authority can be bound. Pull and init are unsupported. Fetch and push require the literal `origin` plus exactly one explicit typed, non-force, non-delete source-to-`refs/heads/...` or `refs/tags/...` refspec; every fetch is forced to use atomic reference updates, disables automatic tag following, and leaves `FETCH_HEAD` unchanged, while push does not admit automatic upstream mutation. Clone requires an explicit safe relative destination and exactly one `--no-checkout`; the boundary reserves that empty destination, binds its identity before the credential helper can run, and applies the same local-config and attribute validation after Git creates the repository. Commit is staged-only and requires exactly one `--no-status` plus one explicit inline message or standard-input message; before binding signing authority, it performs one isolated `write-tree` pass so Git's cache-only index normalization cannot invalidate the first real commit while the resulting staged tree remains bound. Tag likewise requires an explicit message and mandatory SSH signing. Managed execution requires Git 2.40 or newer on the reviewed major-2 line; older builds and an unreviewed future major fail closed before runtime or credential access. Before private authority is exposed, the boundary requires exactly one effective literal GitHub origin without includes or URL rewrites; rejects persistent alternate object databases and external local/worktree configuration authorities; and holds current-user, non-group/world-writable worktree, Git/common directories, any linked-worktree `commondir` selector, configuration, index, and relevant attribute authorities through the child. Root, indexed, Git-dir, and common-dir attributes are UTF-8, size-bounded, and retained in the authority digest. Filter, custom-diff, and merge-driver selectors remain inert because every local/worktree driver definition is rejected and system/global configuration is replaced by private empty inputs; tracked selectors can therefore coexist with managed Git without granting an executable surface. Content operations read attributes from bound `HEAD`, reject any requested file selected by a named filter/diff/merge driver, and commits reject a staged path selected in either `HEAD` or the resulting index. This lets ordinary nonsecret paths coexist with repositories that declare git-crypt or similar drivers without letting managed Git stage, restore, check out, or sign changes to those driver-managed files. Ignored or untracked nested attributes do not enter the authority digest: authority-bearing fetch, push, commit, tag, and no-checkout clone do not process worktree content, and content commands receive no credential or signing frontend. Local credential helpers, aliases, includes, hooks, fsmonitor, editors, pagers, SSH/proxy commands, custom merge/diff/filter programs, submodule update commands, alternate object databases, alternate URL/protocol rules, and per-URL HTTP policy are rejected.

Managed Git derives a least-authority plan from that exact grammar before reading token, cache, or agent state. Credential operations receive a fresh private path containing only the inert frontends and `git-credential-dev-auth`; signing operations receive only the inert frontends and `ssh-keygen-dev-auth`; content operations receive neither private authority. The child and its one private frontend are bound to the same native configuration digest, operation, capability, literal repository, effective local/worktree configuration, repository paths, attribute snapshots, and command-relevant HEAD, packed, and loose-reference authority, and the frontend revalidates that value-free binding immediately before token or signing-agent access. After the child exits, immutable references must remain identical; commit, tag, and fetch may change only the exact references their typed operation declares, and push may not change local reference authority. This detects repository or configuration drift and prevents hostile repository inputs from selecting human helpers or undeclared programs. It is not a sandbox against a malicious concurrent process running as the same operating-system user: such a process can attempt mutate-and-restore races and may already have direct access to that user's credential store or agent socket. The operating-system user remains the trust boundary.

The managed child receives private home/config/cache/data/temp roots, a private executable path containing only its capability-specific frontends, an empty system/global Git configuration, an empty external attributes file, and a fresh empty hooks directory. Highest-precedence command configuration always clears generic and exact GitHub credential helpers; credential operations then select only `git-credential-dev-auth`, while signing and content operations keep every credential helper disabled. The same configuration requires `credential.useHttpPath=true`, disables interactive fallback, rewrites standard GitHub SSH URLs to HTTPS, blocks every non-HTTPS protocol, pins generic and exact-repository TLS verification with no configured proxy, binds the literal resolved `origin`, fixes the automation author, enables the dedicated SSH signer only for commit/tag operations, and disables caller askpass, SSH, editor, pager, external-diff, lazy-fetch, replace-object, and configuration-count inputs. The credential helper parser accepts the protocol's blank-line or end-of-file termination, ignores unrecognized and multi-valued capability attributes, and rejects duplicate authority fields. A successful `get` returns a short-lived installation token and its expiry through the Git credential protocol. A failure returns `quit=true`, so Git cannot continue to a human credential helper or prompt. `store` discards input, and `erase` removes only the exact repository-scoped credential-store entry.

The four public frontend names are derived aliases of the same signed executable: `git-dev-auth`, `git-credential-dev-auth`, `gh-dev-auth`, and `ssh-keygen-dev-auth`. Unix provisioning may use links, while Windows provisioning may use `.exe` hardlinks or identical verified copies. The binary recognizes both native forms without changing their protocols. Installation order is security-sensitive: first verify the signed `dev-auth` artifact; then create and byte-verify all four aliases; then install the ordinary `git` and `gh` dispatchers that target those aliases; finally run offline `dev-auth validate`, exercise `workspace-status` in managed and unmanaged directories, and verify both managed routing and unmanaged system-tool fallback. Rollback reverses authority exposure: disable or remove both dispatchers first, verify no consumer still targets an alias, remove the four aliases second, and remove the core binary or configuration only last. A failed alias verification, validation, classification, or routing proof stops installation or rollback. See [Git credentials](https://git-scm.com/docs/gitcredentials), [Git credential protocol](https://git-scm.com/docs/git-credential), and [GitHub App installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

`gh-dev-auth` parses one bounded command and validates any explicit repository selector before loading configuration. An exact `-R`/`--repo OWNER/REPOSITORY`, the exact positional `OWNER/REPOSITORY` accepted by `gh repo view`, `GH_REPO`, or the literal local `remote.origin.url` may select the repository. Invalid explicit selectors and `GH_REPO` fail before configuration or runtime state is touched. When an explicit selector is absent, the origin fallback loads only the nonsecret public configuration, uses its guarded absolute Git executable to read exactly one literal local `remote.origin.url`, disables includes, and does not apply system, global, or `url.*.insteadOf` rewrite policy; it resolves before any 1Password reference, credential-store token, cache, or runtime mutation. URLs used as pull-request selectors, host-qualified repository selectors, conflicting selectors, compact or bundled short options, unknown flags, and option terminators fail closed. The parser removes repository selectors from the child arguments and supplies the single parsed result through private `GH_REPO`; `repo view` receives the same resolved repository as its normalized positional target. It invokes the configured upstream `gh` with child-only `GH_REPO` and `GH_TOKEN`, private HOME/XDG/Windows application-data/cache/temp roots, a private executable path, noninteractive UI settings, and update/telemetry suppression. Trusted internal pager, denial, and Git frontends prevent the token from reaching ambient home configuration, editors, browsers, pagers, or the configured Git subprocess. The Git frontend strips the installation token and admits only the exact non-networking, non-mutating ref, remote-description, branch-configuration, and commit-description reads reviewed from upstream `gh` 2.98.0 at source revision `a255baf71d13fe5947a4eb7ad521ffd412d64cee`; offline validation and every GitHub CLI operation fail closed unless the configured binary reports the exact official build output. It disables lazy object fetching, rejects repository status because tracked attributes can invoke filters, replaces system/global configuration and executable Git settings with private inert inputs, and rejects every other Git argument shape before invoking the configured absolute Git executable. Pull-request reads and mutations require one positive numeric target, so branch, URL, and current-worktree inference cannot redirect an operation after token selection. Pull-request close and merge reject branch deletion before the API call. Pull-request creation requires exactly one explicit already-pushed `--head`, one explicit `--base`, one explicit `--title`, and one `--body` or `--body-file -`; dry-run, fill, recovery, template, editor, browser, and implicit prompt or push paths fail before credential retrieval. Other pull-request mutations require explicit noninteractive action inputs, and every admitted body-file input is standard input rather than a caller-selected path. Run and release artifact downloads are outside the ordinary surface because they write caller-selected paths. Its admitted surface covers bounded repository pull requests, Actions run observation, read-only workflow inspection, release observation, and repository view through exact per-command flag grammars. External UI flags, authentication changes, user-level API calls, repository administration, issues, secrets, variables, workflow dispatch, repository cloning, terminal-escape opt-in, branch deletion, Git network/mutation, and release publication fail before credential retrieval.

`dev-auth validate` parses the private configuration and prints only counts. `dev-auth validate --online` additionally retrieves every unique declared `op://` field, validates the GitHub App private-key format and both declared SSH fingerprints, and prints no vault, item, field, profile, or value. Because configuration rejects unknown fields and the validator derives its read set only from the parsed configuration, it is not a vault browser and cannot probe undeclared references. This proves that the enrolled principal can read the configured fields; confirming that the Service Account has access to no additional vault still requires the 1Password administrative permission view because the item-read API cannot prove a negative outside its declared set.

The unreleased successor adds `validate --component all|configuration|tools|providers --json`. Use `validate --component providers --online --non-interactive --json` to check provider access independently of Git/gh compatibility and without unlocking enrollment. Offline checks do not retrieve enrollment or provider values. Results distinguish passed, failed, blocked and unperformed checks under `dev-auth-validation-v1`; aggregate mode retains independent failures. In an installed successor, online provider validation requires an admitted logical workload and reports separate authentication-slot, resource-retrieval and declared operation-key counts through its broker. It neither reads legacy configuration as a fallback nor exports operation-only keys. Key checks validate structure and declared identity without signing; actual workload operations and installed native acceptance remain separate requirements. See [ADR 0066](adr/0066-component-validation-and-admitted-provider-observation.md) for the authority and acceptance boundaries.

`dev-auth exec --profile NAME -- COMMAND ...` runs only an exact absolute executable path declared by that profile and supplies only its declared 1Password fields. Before retrieving those fields it creates and validates profile-specific private home, configuration, cache, data, temporary, and runtime directories plus a fresh empty per-invocation executable-path directory that is removed after the child exits. The child receives those inert roots, the fresh empty private `PATH`, and only locale or terminal display hints from the caller; it receives no ambient home, application-data, helper path, session bus, display server, shell, human credential, Service Account token, or signing agent. A declared executable must therefore be self-contained or resolve any helper through an internally fixed absolute path; implicit `PATH` helpers and `/usr/bin/env` shebangs are deliberately unsupported. Dev-auth does not project secrets into the sandbox filesystem, although the admitted executable remains responsible for any state it chooses to write there.

`dev-auth agent --profile NAME` is the one cross-platform SSH isolation boundary. It retrieves only the two declared unencrypted Ed25519 keys, accepts the native OpenSSH or PKCS#8 representation returned by supported 1Password SSH Key items, and verifies their SHA-256 fingerprints before listening. It keeps the keys only in zeroizing process memory and implements only identity listing, signing, and explicit purge; it does not accept key additions or expose a general key store. Linux, WSL, macOS, and other Unix systems use a private current-user Unix socket; native Windows uses a per-configuration, current-user-only and remote-client-rejecting named pipe instead of Microsoft’s shared OpenSSH agent service. `dev-auth agent-endpoint` prints the nonsecret endpoint for process or service configuration. On Linux, a process launched without `XDG_RUNTIME_DIR` safely rejoins the current user-owned `/run/user/<uid>` runtime when it exists. Secret Service access accepts only that private runtime and its current-user Unix session-bus socket; missing bus variables use the upstream zbus current-user fallback, while conflicting values fail closed. `dev-auth ssh-load --profile NAME` is an exact readiness check for the running agent. `dev-auth ssh-public --profile NAME --purpose authentication|signing` validates the complete public identity set against that profile and emits only the canonical public key selected by purpose, allowing host authorization and signing configuration without persisting or rereading private key material. `ssh-keygen-dev-auth` restricts Git signing to that agent, the `git` namespace, and the declared signing fingerprint, while delegating only Git's public `find-principals` and `verify` operations to the configured OpenSSH executable. Private keys are never written to a persistent file.

WSL is a native Linux deployment of `dev-auth`, not a bridge to the Windows process. Its configuration, Secret Service entry, runtime cache, Unix socket, and lifecycle are independent of native Windows. This preserves operation when Windows interoperability is disabled and prevents either environment from silently falling back to the other environment’s human credentials. A workstation authority may enroll the same bounded Service Account principal into both environments, but each enrollment remains intentional and each runtime ends with its own user session.

The Service Account should have immutable `read_items` access only to its declared machine-credential vault. Its token is an enrollment credential, not an interactive desktop session or a replacement for human 1Password access. See [1Password Service Accounts](https://developer.1password.com/docs/service-accounts/get-started/) and [1Password SSH-agent security](https://developer.1password.com/docs/ssh/agent/security/).

GitHub transport/API identity and commit authorship are separate. HTTPS Git and the bounded GitHub CLI wrapper authenticate as the configured GitHub App. Commits and tags use the declared automation signing key. Host authentication uses the other declared key. Higher-risk GitHub administration, workflow modification, public publishing, infrastructure apply, identity administration, and human-vault access remain outside this product.

## Retained setup recovery

Strong setup plans separately name accounts retiring from the replacement policy. Their native identities, both versioned configuration files and receipt-owned integrations remain part of the approved generation, and their owned launchers are deactivated before replacement. They are not enrolled or reactivated by the candidate. Recovery revalidates these identities against the retained old policy instead of forgetting them after the system policy changes; an absent or changed native account requires explicit identity recovery. See [ADR 0046](adr/0046-dev-auth-retiring-account-generation.md).

`dev-auth setup recover --mode user-only --format json` resumes a private retained setup using the exact approved candidate. It does not require the original plan file, policy/configuration sources or original executable download, and never selects a new release. It revalidates the retained approval, native accounts, program/workspace authority and binary installation before continuing. A pending first user-only installation can complete its exact binary transaction and absent product receipt. A user-only upgrade can complete its binary transaction when the current product receipt still matches the retained inactive prior release. Both paths can resume after binary recovery restores the retained prior endpoint. If the public alias is absent or still selects the prior release, invoke the retained candidate's versioned executable directly. When the candidate is not yet staged, invoke a matching approved copy named `dev-auth` or its supported release filename. That path requires no binary journal and either the complete retained prior installation or initial receipt/pointer absence; first-installation bin/versions directories and the installation lock may still be missing, but retained setup approval must exist. Unknown receipts and launcher files are preserved; missing upgrade receipts and incomplete strong installations remain outside these completion paths. See [ADR 0073](adr/0073-initial-staged-binary-forward-recovery.md), [ADR 0074](adr/0074-committed-upgrade-product-receipt-recovery.md), [ADR 0075](adr/0075-staged-user-upgrade-forward-recovery.md), [ADR 0076](adr/0076-unstaged-user-upgrade-forward-recovery.md) and [ADR 0077](adr/0077-unstaged-initial-user-installation-recovery.md). Missing credentials leave setup pending and return exit 3; supply only the retained plan's declared slots through `--credential-stdin SLOT`, repeatable `--credential-fd SLOT=FD` or `--credential-file SLOT=PATH`. Recovery preserves completed rotation and revocation actions. An already-accepted setup is verified without replaying its actions.

Direct policy/configuration install and update commands, including v1 migration, now share setup's native exclusion and reject retained full-generation state. Use a reviewed full `setup plan`/`setup apply` transaction to change that authority; do not remove its marker. Strong configuration maintenance requires the installation's native root owner. The broker remains a dedicated non-root service: authenticated control protocol 4 transfers the dispatcher's validated shared lease so a client exit cannot release the broker's exclusion. See [ADR 0084](adr/0084-native-setup-exclusion-across-broker-and-maintenance.md).

`dev-auth setup recover --mode strong --format json` requires the native root owner; the existing `setup apply --authorize sudo` helper still accepts only its exact apply operation. Recovery can complete initial or upgrade binary activation, an absent initial product receipt or replacement of the retained inactive prior receipt. Fixed services must be stopped and disabled with no native workload/broker domain or socket remaining. An exact uncommitted binary journal is first restored to its retained prior endpoint, then the approved candidate is conditionally installed. Before staging, an exact approved running copy with root-owned ordinary executable custody can supply the bytes without a binary journal; initial bin/versions directories and the binary lock may still be absent, but retained setup approval must exist. A fresh proof can use the immutable candidate after commit even if the original source has disappeared. Recovery completes the fixed privileged launcher, five compiled system definitions and ordinary helper/sidecar from absent or exact prior/candidate states, preserving unrelated files. Missing fixed system-definition parents are conditionally published with root ownership and mode 0755; existing directories retain their permissions, and a parent appearing after observation requires fresh validation. Launcher replacement clears privilege on the held old inode, publishes verified candidate bytes at ordinary permissions and only then grants that candidate release's required mode; legacy bytes never inherit successor privilege. Each mutation rechecks the selected generation; a late collision preserves any already-established change and requires fresh validation. A necessary manager reload must establish loaded stopped/disabled units before product receipt publication. Legacy private strong receipts are conditionally replaced with the successor's public receipt mode. Binary/asset completion does not start, stop or enable services. See [ADR 0081](adr/0081-retained-strong-launcher-completion.md), [ADR 0082](adr/0082-retained-strong-binary-forward-recovery.md) and [ADR 0083](adr/0083-conditional-document-directory-preparation.md). Signed strong-mode acceptance and non-Linux native recovery remain separate gates under [ADR 0044](adr/0044-dev-auth-installed-candidate-recovery.md).

`dev-auth setup restore --mode user-only --format json` restores a retained prior user-only installation and configuration with integrations inactive. Linux `--mode strong` provides the corresponding native-root restoration of fixed services, helpers, configuration and activation. For an approved initial installation, either mode restores original activation and configuration absence while keeping the immutable candidate and recovery generation. Restoration requires the native installation owner, intact retention, no active workload sessions and the exact retained candidate executable. Owner edits outside the prior/candidate configuration pair fail closed. Neither credential values nor completed rotation/revocation receipts are restored. Retry using the result's `retry_executable` with `setup restore --mode MODE --format json`, preserving the selected mode: the public alias may point to an older release without this command or be absent after initial-installation restoration. A successful repeat is unchanged; activation requires a different newly approved setup plan. Non-Linux restoration remains blocked. See [ADR 0049](adr/0049-dev-auth-user-generation-restoration.md), [ADR 0052](adr/0052-dev-auth-initial-installation-restoration.md) and [ADR 0085](adr/0085-linux-workload-lifecycle-and-public-restoration.md) for custody, interruption handling and acceptance limits.

Legacy `setup repair`, `setup rollback` and `setup uninstall` are blocked when a full-setup transition exists, including an accepted transition. On Linux they also require the native owner's exclusive setup lease and refuse while workloads or setup hold that lock. These legacy operations do not recover, restore or remove the full retained policy and integration generation. Use `setup recover` for supported installed-candidate continuation or `setup restore` for retained user-generation restoration and keep the transition intact; deleting it is not a supported maintenance procedure. Remaining full-generation maintenance and non-Linux native coordination are implementation gates; see [ADR 0045](adr/0045-dev-auth-legacy-rollback-exclusion.md).

## Platform contract

The configuration model and security boundaries are designed for Linux, WSL, native Windows, and macOS, but a build or cross-compile does not establish runtime support. Linux x86-64 is the currently supported runtime. WSL must prove its independent Secret Service session, Unix agent lifecycle, native-current-user routing policy, and no Windows fallback; native Windows must prove current-user Credential Manager, protected private ACLs, current-user-owned workspace-root identity, fixed-drive and reparse/junction rejection, held path identity, named-pipe isolation, Git/gh routing, and OpenSSH interoperability; macOS must prove Keychain, native-user configuration routing, launchd lifecycle, socket isolation, and Git/gh routing. Until those native acceptance matrices pass, WSL and Windows remain acceptance-pending and macOS remains unclaimed.
