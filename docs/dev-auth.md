# dev-auth

`dev-auth` is a cross-platform, system-agnostic, account-agnostic credential adapter for one bounded automation principal shared by processes running as the same operating-system user. It has no provider-state model, deployment behavior, arbitrary vault browser, human-credential fallback, or owner-specific policy.

The workstation authority writes `config.toml` under the native current-user application configuration directory and enrolls one 1Password Service Account token through `dev-auth enroll`. Enrollment reads standard input and writes directly to the configured native credential-store entry: Secret Service on Linux and WSL, Keychain on macOS, and Credential Manager on Windows. Each device requires one intentional enrollment because a credential cannot securely retrieve itself. The binary contains no vault name, account owner, GitHub owner, repository, installation ID, executable location, or operating-system account name.

Configuration declares the native credential-store service/account names, exact absolute executable paths, arbitrary `op://vault/item/field` references, GitHub App ID, expected installation `repository_selection` (`all` or `selected`), exact permissions, and one optional Git workspace policy. The Git policy is the sole authority for workspace roots, automation author name/email, and the declared SSH profile used for signing. Roots may be absolute or use the portable `~/path` form; `~/` resolves from the native current-user account rather than caller-controlled `HOME`, `USERPROFILE`, XDG, or application-data variables. The complete account-neutral [example configuration](../crates/dev-auth/config.example.toml) is the supported schema example. Bare executable names and relative paths are rejected for built-in tools and declared execution profiles so a shadowed `PATH` entry cannot receive the Service Account token, a GitHub installation token, profile secrets, or signing-agent access. The workstation provisioner resolves trusted platform executables and renders their absolute paths; WSL uses paths inside its Linux environment, while native Windows uses drive-qualified local paths. Dynamic mode asks GitHub’s authenticated `GET /repos/{owner}/{repo}/installation` endpoint for the requested repository, verifies the returned App ID, account, repository selection, permission map, and suspension state, and then mints a token narrowed back to that one repository. GitHub’s App installations are therefore the live account/repository authority; a workstation list does not need to change when an all-repositories installation receives a new repository. Static installation declarations must match the same selection contract, and configuration must choose exactly one discovery mode. The required permission map is Actions-read, Checks-read, Contents-write, Metadata-read, Pull-requests-write, and Statuses-read. Owner and repository matching is case-insensitive. See [GitHub’s repository-installation endpoint and installation-token contract](https://docs.github.com/en/rest/apps/apps#get-a-repository-installation-for-the-authenticated-app).

Offline validation, `workspace-status`, and `git-dev-auth` share one native-current-user configuration locator, and each invocation binds one immutable file snapshot: `$HOME/.config/dev-auth/config.toml` on Linux and WSL where `$HOME` denotes the home from the effective user's account record rather than the caller environment, `~/Library/Application Support/dev-auth/config.toml` on macOS under the same account-record rule, and the current-user Roaming AppData `dev-auth/config/config.toml` path on Windows. Caller `HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, `APPDATA`, and `LOCALAPPDATA` values cannot redirect that authority. Other runtime and cache roots come from the operating system's protected per-user directories. Derived GitHub installation tokens live in the native credential store rather than plaintext cache files; the filesystem contains only scope-hash lock files for cross-process single-flight refresh. The GitHub App ID is part of every cache scope, and refresh, erase, and purge share lifecycle locks so revoked credentials cannot be recreated by an already-running refresh. Dynamic cache reuse requires a successful live repository-installation lookup and an exact match of App ID, installation ID, repository, permissions, selection contract, and expiry; a lookup failure fails closed even when a cached token has not expired. Successful erase and purge operations remove the corresponding scope receipts after deleting their credential-store entries. Unix builds enforce owner-only modes, ownership, link count, and no-follow file opening. Native Windows builds additionally require current-user protected ACLs, require credential-bearing executables to reside on fixed local volumes that preserve ACLs, reject reparse and remote paths, and apply a current-user descriptor to every named-pipe instance. A new build removes legacy file-backed token caches without reading or reporting their values.

`git-dev-auth` is the generic same-name Git dispatch boundary. It loads one native-current-user configuration snapshot, classifies the current directory plus every admitted repository selector, environment selector, and clone/init path, and delegates to the configured human Git only when every path is positively proven unmanaged. An unknown option, alternate configuration, repository indirection, symlink/reparse repository path, managed-root ancestor, unsafe or ambiguous init/clone destination, or outside-to-managed target fails closed; it never retries through human Git after a managed error. Caller `PATH` entries are canonicalized so ordinary search-path aliases outside managed roots do not block routing, while any entry resolving into a managed root still blocks unmanaged fallback; managed execution replaces the caller search path entirely. A missing managed clone leaf is accepted only when its existing in-root parent is held as safe authority and the boundary can create, restrict, and revalidate an empty mode-0700 leaf before credentials are reachable. `dev-auth workspace-status` exposes the same config-only policy as a value-free routing query: `managed` exits 0, `unmanaged` exits 3, and an error emits no classification and exits 2. Neither route classification nor unmanaged delegation reads 1Password, the credential store, token caches, or the SSH agent. Offline `dev-auth validate` applies the same workspace-root existence, canonical-path, ownership, permissions, link/reparse, and non-overlap rules without reading a secret.

Inside a managed root, `git-dev-auth` admits only bounded status, staging, path-only restore/checkout, full-object-ID history, signed commit/tag, literal-origin fetch/push, and explicit GitHub clone forms. Reference-bearing restore/checkout, branch, switch, and symbolic or abbreviated history operands are unsupported until their exact source and transition authority can be bound. Pull and init are unsupported. Fetch and push require the literal `origin` plus exactly one explicit typed, non-force, non-delete source-to-`refs/heads/...` or `refs/tags/...` refspec; every fetch is forced to use atomic reference updates, disables automatic tag following, and leaves `FETCH_HEAD` unchanged, while push does not admit automatic upstream mutation. Clone requires an explicit safe relative destination and exactly one `--no-checkout`; the boundary reserves that empty destination, binds its identity before the credential helper can run, and applies the same local-config and attribute validation after Git creates the repository. Commit is staged-only and requires exactly one `--no-status` plus one explicit inline message or standard-input message; tag likewise requires an explicit message and mandatory SSH signing. Managed execution requires Git 2.40 or newer on the reviewed major-2 line; older builds and an unreviewed future major fail closed before runtime or credential access. Before private authority is exposed, the boundary requires exactly one effective literal GitHub origin without includes or URL rewrites; rejects persistent alternate object databases and external local/worktree configuration authorities; and holds current-user, non-group/world-writable worktree, Git/common directories, any linked-worktree `commondir` selector, configuration, index, and relevant attribute authorities through the child. Root, indexed, Git-dir, and common-dir attributes are bounded and reject filter, custom diff, or merge drivers. Ignored or untracked nested attributes do not enter the authority digest: authority-bearing fetch, push, commit, tag, and no-checkout clone do not process worktree content, content commands receive no credential or signing frontend, local/worktree driver definitions are rejected, and system/global driver configuration is replaced by empty private inputs. Local credential helpers, aliases, includes, hooks, fsmonitor, editors, pagers, SSH/proxy commands, custom merge/diff/filter programs, submodule update commands, alternate object databases, alternate URL/protocol rules, and per-URL HTTP policy are rejected.

Managed Git derives a least-authority plan from that exact grammar before reading token, cache, or agent state. Credential operations receive a fresh private path containing only the inert frontends and `git-credential-dev-auth`; signing operations receive only the inert frontends and `ssh-keygen-dev-auth`; content operations receive neither private authority. The child and its one private frontend are bound to the same native configuration digest, operation, capability, literal repository, effective local/worktree configuration, repository paths, attribute snapshots, and command-relevant HEAD, packed, and loose-reference authority, and the frontend revalidates that value-free binding immediately before token or signing-agent access. After the child exits, immutable references must remain identical; commit, tag, and fetch may change only the exact references their typed operation declares, and push may not change local reference authority. This detects repository or configuration drift and prevents hostile repository inputs from selecting human helpers or undeclared programs. It is not a sandbox against a malicious concurrent process running as the same operating-system user: such a process can attempt mutate-and-restore races and may already have direct access to that user's credential store or agent socket. The operating-system user remains the trust boundary.

The managed child receives private home/config/cache/data/temp roots, a private executable path containing only its capability-specific frontends, an empty system/global Git configuration, an empty external attributes file, and a fresh empty hooks directory. Highest-precedence command configuration always clears generic and exact GitHub credential helpers; credential operations then select only `git-credential-dev-auth`, while signing and content operations keep every credential helper disabled. The same configuration requires `credential.useHttpPath=true`, disables interactive fallback, rewrites standard GitHub SSH URLs to HTTPS, blocks every non-HTTPS protocol, pins generic and exact-repository TLS verification with no configured proxy, binds the literal resolved `origin`, fixes the automation author, enables the dedicated SSH signer only for commit/tag operations, and disables caller askpass, SSH, editor, pager, external-diff, lazy-fetch, replace-object, and configuration-count inputs. The credential helper parser accepts the protocol's blank-line or end-of-file termination, ignores unrecognized and multi-valued capability attributes, and rejects duplicate authority fields. A successful `get` returns a short-lived installation token and its expiry through the Git credential protocol. A failure returns `quit=true`, so Git cannot continue to a human credential helper or prompt. `store` discards input, and `erase` removes only the exact repository-scoped credential-store entry.

The four public frontend names are derived aliases of the same signed executable: `git-dev-auth`, `git-credential-dev-auth`, `gh-dev-auth`, and `ssh-keygen-dev-auth`. Unix provisioning may use links, while Windows provisioning may use `.exe` hardlinks or identical verified copies. The binary recognizes both native forms without changing their protocols. Installation order is security-sensitive: first verify the signed `dev-auth` artifact; then create and byte-verify all four aliases; then install the ordinary `git` and `gh` dispatchers that target those aliases; finally run offline `dev-auth validate`, exercise `workspace-status` in managed and unmanaged directories, and verify both managed routing and unmanaged system-tool fallback. Rollback reverses authority exposure: disable or remove both dispatchers first, verify no consumer still targets an alias, remove the four aliases second, and remove the core binary or configuration only last. A failed alias verification, validation, classification, or routing proof stops installation or rollback. See [Git credentials](https://git-scm.com/docs/gitcredentials), [Git credential protocol](https://git-scm.com/docs/git-credential), and [GitHub App installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

`gh-dev-auth` parses one bounded command and validates any explicit repository selector before loading configuration. An exact `-R`/`--repo OWNER/REPOSITORY`, the exact positional `OWNER/REPOSITORY` accepted by `gh repo view`, `GH_REPO`, or the literal local `remote.origin.url` may select the repository. Invalid explicit selectors and `GH_REPO` fail before configuration or runtime state is touched. When an explicit selector is absent, the origin fallback loads only the nonsecret public configuration, uses its guarded absolute Git executable to read exactly one literal local `remote.origin.url`, disables includes, and does not apply system, global, or `url.*.insteadOf` rewrite policy; it resolves before any 1Password reference, credential-store token, cache, or runtime mutation. URLs used as pull-request selectors, host-qualified repository selectors, conflicting selectors, compact or bundled short options, unknown flags, and option terminators fail closed. The parser removes repository selectors from the child arguments and supplies the single parsed result through private `GH_REPO`; `repo view` receives the same resolved repository as its normalized positional target. It invokes the configured upstream `gh` with child-only `GH_REPO` and `GH_TOKEN`, private HOME/XDG/Windows application-data/cache/temp roots, a private executable path, noninteractive UI settings, and update/telemetry suppression. Trusted internal pager, denial, and Git frontends prevent the token from reaching ambient home configuration, editors, browsers, pagers, or the configured Git subprocess. The Git frontend strips the installation token and admits only the exact non-networking, non-mutating ref, remote-description, branch-configuration, and commit-description reads reviewed from upstream `gh` 2.98.0 at source revision `a255baf71d13fe5947a4eb7ad521ffd412d64cee`; offline validation and every GitHub CLI operation fail closed unless the configured binary reports the exact official build output. It disables lazy object fetching, rejects repository status because tracked attributes can invoke filters, replaces system/global configuration and executable Git settings with private inert inputs, and rejects every other Git argument shape before invoking the configured absolute Git executable. Pull-request reads and mutations require one positive numeric target, so branch, URL, and current-worktree inference cannot redirect an operation after token selection. Pull-request close and merge reject branch deletion before the API call. Pull-request creation requires exactly one explicit already-pushed `--head`, one explicit `--base`, one explicit `--title`, and one `--body` or `--body-file -`; dry-run, fill, recovery, template, editor, browser, and implicit prompt or push paths fail before credential retrieval. Other pull-request mutations require explicit noninteractive action inputs, and every admitted body-file input is standard input rather than a caller-selected path. Run and release artifact downloads are outside the ordinary surface because they write caller-selected paths. Its admitted surface covers bounded repository pull requests, Actions run observation, read-only workflow inspection, release observation, and repository view through exact per-command flag grammars. External UI flags, authentication changes, user-level API calls, repository administration, issues, secrets, variables, workflow dispatch, repository cloning, terminal-escape opt-in, branch deletion, Git network/mutation, and release publication fail before credential retrieval.

`dev-auth validate` parses the private configuration and prints only counts. `dev-auth validate --online` additionally retrieves every unique declared `op://` field, validates the GitHub App private-key format and both declared SSH fingerprints, and prints no vault, item, field, profile, or value. Because configuration rejects unknown fields and the validator derives its read set only from the parsed configuration, it is not a vault browser and cannot probe undeclared references. This proves that the enrolled principal can read the configured fields; confirming that the Service Account has access to no additional vault still requires the 1Password administrative permission view because the item-read API cannot prove a negative outside its declared set.

`dev-auth exec --profile NAME -- COMMAND ...` runs only an exact absolute executable path declared by that profile and supplies only its declared 1Password fields. Before retrieving those fields it creates and validates profile-specific private home, configuration, cache, data, temporary, and runtime directories plus a fresh empty per-invocation executable-path directory that is removed after the child exits. The child receives those inert roots, the fresh empty private `PATH`, and only locale or terminal display hints from the caller; it receives no ambient home, application-data, helper path, session bus, display server, shell, human credential, Service Account token, or signing agent. A declared executable must therefore be self-contained or resolve any helper through an internally fixed absolute path; implicit `PATH` helpers and `/usr/bin/env` shebangs are deliberately unsupported. Dev-auth does not project secrets into the sandbox filesystem, although the admitted executable remains responsible for any state it chooses to write there.

`dev-auth agent --profile NAME` is the one cross-platform SSH isolation boundary. It retrieves only the two declared unencrypted Ed25519 keys, accepts the native OpenSSH or PKCS#8 representation returned by supported 1Password SSH Key items, and verifies their SHA-256 fingerprints before listening. It keeps the keys only in zeroizing process memory and implements only identity listing, signing, and explicit purge; it does not accept key additions or expose a general key store. Linux, WSL, macOS, and other Unix systems use a private current-user Unix socket; native Windows uses a per-configuration, current-user-only and remote-client-rejecting named pipe instead of Microsoft’s shared OpenSSH agent service. `dev-auth agent-endpoint` prints the nonsecret endpoint for process or service configuration. On Linux, a process launched without `XDG_RUNTIME_DIR` safely rejoins the current user-owned `/run/user/<uid>` runtime when it exists. Secret Service access accepts only that private runtime and its current-user Unix session-bus socket; missing bus variables use the upstream zbus current-user fallback, while conflicting values fail closed. `dev-auth ssh-load --profile NAME` is an exact readiness check for the running agent. `dev-auth ssh-public --profile NAME --purpose authentication|signing` validates the complete public identity set against that profile and emits only the canonical public key selected by purpose, allowing host authorization and signing configuration without persisting or rereading private key material. `ssh-keygen-dev-auth` restricts Git signing to that agent, the `git` namespace, and the declared signing fingerprint, while delegating only Git's public `find-principals` and `verify` operations to the configured OpenSSH executable. Private keys are never written to a persistent file.

WSL is a native Linux deployment of `dev-auth`, not a bridge to the Windows process. Its configuration, Secret Service entry, runtime cache, Unix socket, and lifecycle are independent of native Windows. This preserves operation when Windows interoperability is disabled and prevents either environment from silently falling back to the other environment’s human credentials. A workstation authority may enroll the same bounded Service Account principal into both environments, but each enrollment remains intentional and each runtime ends with its own user session.

The Service Account should have immutable `read_items` access only to its declared machine-credential vault. Its token is an enrollment credential, not an interactive desktop session or a replacement for human 1Password access. See [1Password Service Accounts](https://developer.1password.com/docs/service-accounts/get-started/) and [1Password SSH-agent security](https://developer.1password.com/docs/ssh/agent/security/).

GitHub transport/API identity and commit authorship are separate. HTTPS Git and the bounded GitHub CLI wrapper authenticate as the configured GitHub App. Commits and tags use the declared automation signing key. Host authentication uses the other declared key. Higher-risk GitHub administration, workflow modification, public publishing, infrastructure apply, identity administration, and human-vault access remain outside this product.

## Platform contract

The configuration model and security boundaries are designed for Linux, WSL, native Windows, and macOS, but a build or cross-compile does not establish runtime support. Linux x86-64 is the currently supported runtime. WSL must prove its independent Secret Service session, Unix agent lifecycle, native-current-user routing policy, and no Windows fallback; native Windows must prove current-user Credential Manager, protected private ACLs, current-user-owned workspace-root identity, fixed-drive and reparse/junction rejection, held path identity, named-pipe isolation, Git/gh routing, and OpenSSH interoperability; macOS must prove Keychain, native-user configuration routing, launchd lifecycle, socket isolation, and Git/gh routing. Until those native acceptance matrices pass, WSL and Windows remain acceptance-pending and macOS remains unclaimed.
