# One-shot privilege authorization

`dev-tools-privilege` is the product-neutral boundary for running one exact privileged helper. It deliberately does not implement a sudo keepalive, password transport, shell command template, ambient `PATH` lookup, or reusable root daemon. Products retain domain planning, receipts, idempotence, and rollback; this crate owns only authorization-process construction and terminal lifecycle.

The portable contract carries an absolute helper path, native argument vector, optional deadline, standard-stream policy, and whether user interaction is allowed. A backend returns a typed terminal outcome. `Denied` is reserved for platforms that can prove authorization ended before helper execution, and `Cancelled` requires positive attribution to the authorization surface rather than a raw process signal. Unix sudo preserves ordinary codes and signals as `Exited` because it cannot distinguish its own status from an arbitrary helper using the same termination.

The Unix sudo backend clears its environment, starts from `/`, preserves native argument boundaries, and never reads or writes a password. Noninteractive operation invokes `sudo -n -- ABSOLUTE_HELPER ARGS...`; interactive operation invokes `sudo -- ABSOLUTE_HELPER ARGS...`, inherits standard streams, and remains in the terminal's foreground process group so the operating system owns the visible prompt. Both modes require no caller deadline. Modern sudo may create a pty, monitor, new session, and separate command child even without a prompt, so the caller waits for sudo to become terminal instead of killing only its direct process or original process group and falsely claiming that the root helper stopped. Sudo policy owns the authentication-prompt timeout. Products needing a bounded transaction must enforce it inside their exact receipt-owned helper or a stronger operating-system boundary; they must not synthesize a sudo keepalive or parent-only kill.

An exact helper is a non-symlink executable selected through product policy and, where applicable, an installation receipt. The generic crate rejects relative, non-normalized, symlink-containing, nonregular, and nonexecutable paths. The owning product must additionally prove that the entire accepted hierarchy is not attacker-writable, bind immutable content identity through its installation receipt, and define the helper's typed transaction protocol; an absolute path by itself is not authority.

Dev Auth should consume this boundary through a separate receipt-owned setup helper that accepts only one approved setup-plan transaction and bounded private credential input. Workload admission remains a different authority and must not be widened into a generic privileged command runner. Native Windows elevation requires a future `ShellExecuteExW`/private named-pipe backend, and native macOS requires a future SMAppService/launchd/XPC helper with an Authorization Services right. Neither platform is supported merely because the portable trait exists.
