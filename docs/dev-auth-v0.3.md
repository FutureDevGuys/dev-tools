# dev-auth v0.3 architecture

Dev-auth v0.3 is a standalone workload-identity broker. It installs transparent same-name `git` and `gh` launchers, forwards native human invocations without interpreting their command grammar, and adds narrowly scoped automation authority only for a workload session admitted by the operating system. Dev Tools and Syscfg checkouts are not runtime dependencies; Syscfg may select and invoke the signed standalone installer as an optional deployment client.

## Trust and routing

An ordinary process outside a verified workload session is replaced by the exact native Git or GitHub CLI recorded in the installation receipt. Arguments, working directory, standard streams, terminal state, environment, signals, and exit behavior belong to the native tool. Dev-auth does not parse editor, pager, alias, or upstream command strings on this route. This includes multiword values such as `GIT_EDITOR="code-insiders --wait"` and future upstream subcommands.

A process inside an admitted workload boundary connects to the broker. Missing admission uses native passthrough, while an expired, invalid, ambiguous, or unauthorized claimed session fails closed and never retries with human credentials. Workspaces narrow filesystem and provider resources but never identify a workload.

Strong Linux admission requires a root-owned nondelegated transient systemd service, race-free Unix peer credentials including `SO_PEERPIDFD`, a retained cgroup identity, an active renewable broker registration, and a product-owned supervisor lifecycle. Setup installs a dedicated receipt-bound hardlink for privileged workload dispatch and a polkit action that allows an active local session to invoke only that dispatcher without a routine password prompt; the same executable identity cannot expose setup or other administrative operations through that alias. Every dispatch still resolves the caller's root-capped policy and exact trusted launcher before starting a service. The native launcher transfers its filtered public environment over a one-use private Unix socket; the supervisor authenticates the launcher's UID, PID, and pidfd before reading it, then unlinks the socket. `KillMode=control-group` and a nondelegated service cgroup make supervisor exit terminal for descendants. Environment variables, socket paths, PIDs, working directories, and repository paths remain routing inputs rather than proof of an active broker session. The strong backend does not claim protection against a hostile same-user debugger or injector unless a separately accepted sandbox or operating-system identity provides that boundary.

User-only mode is an explicitly degraded fallback. It uses native per-user credential storage and reports that arbitrary same-user processes remain inside its trust boundary. It must not be labeled strong and it must not silently replace a failed strong session.

## Policy

`/etc/dev-auth/policy.toml` is administrator authority in strong mode. It caps users, exact upstream programs, trusted workload launchers, GitHub Apps and installation permissions, per-profile 1Password references, filesystem roots with read-only or read-write access, and accepted sandbox adapters. The native user's `~/.config/dev-auth/config-v2.toml` may select and narrow those caps but cannot widen them. Neither document contains a credential value. The account-neutral [strong administrator-policy example](../crates/dev-auth/policy-v2.example.toml), [weaker user-only policy example](../crates/dev-auth/policy-v2-user-only.example.toml), and [user-configuration example](../crates/dev-auth/config-v2.example.toml) show the complete two-layer shape. User-only policy is stored privately at `~/.config/dev-auth/policy-v2.toml`; it may trust current-user-owned launchers and provider programs because malicious same-user processes are explicitly inside that fallback's trust boundary. When deployment supplies both an administrator policy and a per-user fallback policy, setup proves the latter is a structural subset across users, pinned programs, launchers, adapters, provider scopes, credential slots, secret references, and filesystem authority before installing either document.

Workloads are generic named configurations consisting of one trusted launcher, one authority profile, zero or more capped workspace roots, and an optional sandbox preference. A nonempty root set gates the workload's canonical launch directory; it does not by itself confine later filesystem access, and read-only or read-write mount enforcement requires an adapter with platform acceptance. Installing an approved user configuration reconciles same-name workload launchers in the native user's `~/.local/bin`; those launchers admit the outer process once, while a nested invocation inside an already verified session directly executes the configured downstream launcher without escaping or widening that session. Codex, Claude, editors, and future agents are instances of this model rather than product-specific code.

## Provider and secret boundary

Strong enrollment accepts the scoped 1Password Service Account token once through standard input and encrypts it as an operating-system system credential. Only the protected broker receives the decrypted credential. The broker invokes exact administrator-pinned provider programs with a sanitized environment and reads only references admitted by the resolved profile.

Credential lifecycle is explicit and value-blind. `setup enroll-system` and `setup enroll-user` refuse an existing credential; `setup rotate-system` and `setup rotate-user` require one; `setup revoke-system` and `setup revoke-user` remove it. Strong rotation and revocation require the broker stopped and same-name launchers deactivated. Credential bytes are accepted only on standard input and are never written to a plan, configuration, receipt, command line, or diagnostic.

Git uses the standard credential-helper protocol with `credential.useHttpPath=true`; the helper canonicalizes Git's protocol, host, owner, and repository before requesting a scoped token. An admitted Git process keeps ordinary upstream syntax and normal safe Git configuration, including aliases, editors, and pagers, while highest-precedence command-scoped configuration removes inherited credential, token, askpass, SSH-agent, HTTP-header, proxy, and signing authority and inserts only the broker capabilities granted to that workload. A broker denial sets Git's terminal credential-helper result so lower-precedence human helpers and prompts cannot run. GitHub CLI receives a short-lived token only in its direct child environment and a session-local configuration directory. Human account configuration is not mutated. Signing and SSH are separate operation capabilities: the broker exposes distinct signing-only and authentication-only SSH-agent sockets, verifies every returned signature against the policy-bound public key, and never exposes a raw private key.

An admitted workload can intentionally reveal a derived bearer token. Its containment comes from repository scope, provider permissions, short lifetime, workload lifetime, audit, and revocation rather than a command allowlist. The durable 1Password token, GitHub App private key, and raw SSH or signing keys are never returned to the workload. The workload root environment also disables ambient Git system/global credential configuration, prompts, askpass, and the native GitHub CLI account directory, so an accidental absolute native-tool invocation or a fresh shell that resets `PATH` cannot fall back to a human identity; the verified same-name launchers replace those inert defaults only with the broker-scoped authority for the direct child.

## Setup and migration

The signed binary owns discovery, approval plans, installation receipts, versioned binaries, product aliases, same-name launchers, workload launchers and desktop entries, policy and user-configuration installation and compare-and-swap updates, system service assets, enrollment and rotation, activation, verification, diagnostics, repair, migration, rollback, and uninstall. Discovery checks fixed platform candidates and never blindly trusts caller `PATH`. `dev-auth build-info` emits machine-readable product, version, and embedded source commit; the signed stable manifest carries the same exact source commit alongside the artifact digest.

Setup installs and verifies a candidate in parallel before changing ordinary command resolution. Product aliases are installed first; administrator policy, user configuration, credential enrollment, and broker readiness are separate explicit gates; same-name `git` and `gh` launchers are activated last and removed first. The noninteractive `plan-release`/`apply` interface binds installation to an authenticated signed release, exact source commit, manifest generation, and approved plan digest, while `discover` reports fixed candidate programs, workload launchers, desktop entries, and strong-backend availability without reading secrets. `dev-auth setup readiness --mode strong|user-only` performs a read-only value-free check and names exactly one next operation. Its final gate proves that `git` and `gh` resolve through the installed aliases before native tools in the current absolute `PATH`; setup reports `fix_launcher_path_precedence` instead of editing shell startup files or overwriting an unowned command. `dev-auth status --broker` also reports authenticated-release, policy-resolution, workload-launcher, desktop-entry, capability, and launcher-resolution readiness.

Version changes require same-name launchers to be deactivated. A strong update additionally requires both broker sockets absent; a user-only update requires no live per-workload session directory. This prevents a newly installed launcher from speaking to an old broker or silently changing installation mode. Authenticated installs retain the trusted-root generation, manifest generation, source commit, and artifact digest; apply re-verifies the signed root, manifest, and artifact paths from the approved plan, rejects generation rollback or identity reuse, and cannot replace an authenticated install with an unsigned update. Repair and reinstall preserve only receipt-owned artifacts and reject symlink, ownership, permission, digest, alias, desktop-entry, or system-asset drift.

A v1 migration begins with `setup migrate-v1-preview`, which is read-only and omits secret references. `setup migrate-v1` requires the approved digests of both the current v1 document and an explicit v2 user configuration, proves the v2 resolution does not widen v1 programs, workspaces, GitHub scope, author identity, secret references, or SSH operation keys, writes an exact owner-private backup under `~/.config/dev-auth/migrations/v1/<sha256>/config.toml`, and only then installs v2. The original v1 file remains unchanged for rollback. The installed v0.2 release and its configuration remain reversible until v0.3 clean-device and rollback acceptance complete.

Normal uninstall preserves policy and credential enrollment throughout the rollback window. After the installation and all receipted launchers are absent, the separate `setup purge-system-state` or `setup purge-user-state` operation removes only safe owner-bound v2 policy/configuration and the matching broker credential; it never removes the v1 configuration or migration backup. This split keeps ordinary rollback reversible and makes permanent credential removal deliberate and idempotent.

## Sandboxes and platforms

Admission occurs outside an optional sandbox, and the sandbox remains inside the admitted operating-system boundary. Firejail, Bubblewrap, and container launchers are generic administrator-pinned adapters rather than hard-coded product cases. The adapter starts an internal probe before the workload: reaching that probe proves executable and broker-socket visibility, the broker reauthenticates the sandbox peer, strong mode rechecks the exact retained cgroup, and the probe re-resolves the configured workload and launcher before execution. A hidden socket, escaped cgroup, ambiguous UID mapping, inaccessible launcher, or incompatible namespace fails closed before the workload starts. Network and mount policy remain explicit administrator-owned adapter arguments and must receive platform-specific acceptance coverage before that adapter is advertised. Sensitive dependencies are resolved by administrator-pinned paths, never through caller `PATH` or `firecfg` replacements.

The broker emits structured value-free lifecycle and capability audit records. Public resource selectors are represented only by hashes; credential values, tokens, private references, payloads, signatures, owners, and repositories are not serialized. A background reaper invalidates dead or expired supervised sessions and invokes provider revocation even when no later client request arrives.

Linux is the first strong backend. Windows Job Objects, named pipes, and Credential Manager; macOS audit tokens, XPC, and Keychain; and WSL each remain behind platform interfaces without a support claim until native acceptance passes.

## Release acceptance

Release acceptance includes semantic passthrough, unknown future Git and GitHub CLI commands, the multiword VS Code `GIT_EDITOR` regression, admitted credentials and API access, denied resources, no human fallback, subagents and fresh shells, concurrent workloads, broker restart, daemonization, teardown, token refresh and revocation, credential absence from process and persistent surfaces, sandbox positive and negative probes, standalone clean-machine installation, Syscfg-as-client installation, rollback, and hot-path performance. No normal command may reintroduce per-command Python, artifact hashing, repository traversal, or a maintained upstream command grammar.
