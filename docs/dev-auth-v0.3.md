# dev-auth v0.3 architecture

Dev-auth v0.3 is a standalone workload-identity broker. It installs receipt-owned same-name `git` and `gh` launchers ahead of administrator-pinned native tools, forwards invocations without interpreting command grammar, and adds narrowly scoped automation authority only for a workload session admitted by the operating system. Outside a verified workload the launchers replace themselves with native Git or GitHub CLI, so human behavior remains native. Admitted workloads additionally receive a private session tool plane that cannot be displaced by a child resetting `PATH`. Dev Tools and Syscfg checkouts are not runtime dependencies; Syscfg may invoke the signed standalone installer as an optional deployment client.

## Trust and routing

An ordinary process outside a verified workload session traverses only the small same-name launcher, which obtains the receipt-bound native executable and uses Unix `execve` replacement without parsing or rewriting arguments. Arguments, working directory, standard streams, terminal state, environment, signals, and exit behavior therefore belong to the native tool. Dev-auth does not parse editor, pager, alias, or upstream command strings on this route. This includes multiword values such as `GIT_EDITOR="code-insiders --wait"` and future upstream subcommands.

A process inside an admitted workload boundary connects to the broker. Missing admission uses native passthrough, while an expired, invalid, ambiguous, or unauthorized claimed session fails closed and never retries with human credentials. Workspaces narrow filesystem and provider resources but never identify a workload.

Strong Linux admission requires a root-owned nondelegated transient systemd service, a full identity-mapped private user namespace that preserves the complete native UID/GID range, race-free Unix peer credentials including `SO_PEERPIDFD`, a retained cgroup identity, an active renewable broker registration, and a product-owned supervisor lifecycle. Setup installs a dedicated receipt-bound copy for privileged workload dispatch and a polkit action that requires the native user to authenticate once when starting each outer workload; Git, gh, subagents, and nested shells remain prompt-free for that admitted workload's lifetime. The action authorizes only that dispatcher, and the same executable identity cannot expose setup or other administrative operations through the privileged alias. Every dispatch still resolves the caller's root-capped policy and exact trusted launcher before starting a service. The native launcher transfers its filtered public environment to the root dispatcher over a one-use root-created socket published with mode `0600` to the exact native UID/GID. The dispatcher retains the connecting supervisor's pidfd and hands over the environment only after authenticating the exact UID, primary and supplementary groups, PID, and cgroup. The same duplex handoff carries an authenticated exit-or-signal receipt back to the native launcher, because `systemd-run --wait` does not itself preserve signal termination. `KillMode=control-group` and a nondelegated service cgroup make supervisor exit terminal for descendants. Environment variables, socket paths, working directories, and repository paths remain routing inputs rather than proof of an active broker session; a numeric PID is accepted only together with its retained pidfd and kernel-observed boundary evidence. The workload deliberately retains the native account UID so it can use the user's approved workspaces without unsafe recursive ownership changes or bespoke id-mapped mounts; the privileged broker and exact cgroup, rather than a distinct filesystem UID, protect durable credentials. The explicit polkit authentication prevents an unrelated same-user process from silently starting an authority-bearing workload; after admission, an unrelated process still cannot request authority directly. Dev-auth does not claim protection against a same-user process that can observe the user's authentication, control an admitted interactive workload, or ptrace or inject into it. A separately accepted sandbox or OS identity is required for that stronger claim.

User-only mode is an explicitly degraded fallback. It uses native per-user credential storage and reports that arbitrary same-user processes remain inside its trust boundary. It must not be labeled strong and it must not silently replace a failed strong session.

## Policy

`/etc/dev-auth/policy.toml` is administrator authority in strong mode. It caps users, exact upstream programs, trusted workload launchers, GitHub Apps and installation permissions, per-profile 1Password references, filesystem roots with read-only or read-write access, and accepted sandbox adapters. The native user's `~/.config/dev-auth/config-v2.toml` may select and narrow those caps but cannot widen them. Neither document contains a credential value. The account-neutral [strong administrator-policy example](../crates/dev-auth/policy-v2.example.toml), [weaker user-only policy example](../crates/dev-auth/policy-v2-user-only.example.toml), and [user-configuration example](../crates/dev-auth/config-v2.example.toml) show the complete two-layer shape. User-only policy is stored privately at `~/.config/dev-auth/policy-v2.toml`; it may trust current-user-owned launchers and provider programs because malicious same-user processes are explicitly inside that fallback's trust boundary. When deployment supplies both an administrator policy and a per-user fallback policy, setup proves the latter is a structural subset across users, pinned programs, launchers, adapters, provider scopes, credential slots, secret references, and filesystem authority before installing either document.

Workloads are generic named configurations consisting of one trusted launcher, one authority profile, zero or more capped workspace roots, and an optional sandbox preference. A nonempty root set gates the workload's canonical launch directory; it does not by itself confine later filesystem access, and read-only or read-write mount enforcement requires an adapter with platform acceptance. Installing an approved user configuration reconciles same-name workload launchers in the native user's `~/.local/bin`; those launchers admit the outer process once, while a nested invocation inside an already verified session directly executes the configured downstream launcher without escaping or widening that session. Codex, Claude, editors, and future agents are instances of this model rather than product-specific code.

## Provider and secret boundary

Strong enrollment accepts the scoped 1Password Service Account token once through standard input and encrypts it as an operating-system system credential. Only the protected broker receives the decrypted credential. The broker invokes exact administrator-pinned provider programs with a sanitized environment and reads only references admitted by the resolved profile.

Credential lifecycle is explicit and value-blind. `setup enroll-system` and `setup enroll-user` refuse an existing credential; `setup rotate-system` and `setup rotate-user` require one; `setup revoke-system` and `setup revoke-user` remove it. Strong rotation and revocation require the broker stopped and same-name launchers deactivated. Credential bytes are accepted only on standard input and are never written to a plan, configuration, receipt, command line, or diagnostic.

Git uses the standard credential-helper protocol with `credential.useHttpPath=true`; the helper canonicalizes Git's protocol, host, owner, and repository before requesting a scoped token. An admitted Git process keeps ordinary upstream syntax, caller editor and pager values, and repository-local behavior, while its system and human-global Git configuration is replaced with empty inputs and highest-precedence command-scoped configuration inserts only the broker capabilities granted to that workload. Dev-auth forwards those values without parsing them. A broker denial sets Git's terminal credential-helper result so lower-precedence human helpers and prompts cannot run. GitHub CLI receives a short-lived token only in its direct child environment and a session-local configuration directory. A profile with an exact repository list receives precisely that set; a profile deliberately capped to one owner with an empty repository list asks GitHub for that owner's exact App installation and omits the repository selector when minting, so GitHub returns only the installation's current selected-repository set without dev-auth parsing present or future `gh` syntax. The broker verifies the App, owner, selection mode, permission map, suspension state, and every returned repository owner before issuing the token. Human account configuration is not mutated. Signing and SSH are separate operation capabilities: the broker exposes distinct signing-only and authentication-only SSH-agent sockets, verifies every returned signature against the policy-bound public key, and never exposes a raw private key.

An admitted workload can intentionally reveal a derived bearer token. Its containment comes from repository scope, provider permissions, short lifetime, workload lifetime, audit, and revocation rather than a command allowlist. The durable 1Password token, GitHub App private key, and raw SSH or signing keys are never returned to the workload. The workload root environment also disables ambient Git system/global credential configuration, prompts, askpass, and the native GitHub CLI account directory, so an accidental absolute native-tool invocation or a fresh shell that resets `PATH` cannot fall back to a human identity. The session-private tool plane contains only `git` and `gh` aliases to the receipt-bound dev-auth executable and precedes the inherited tool path only inside that workload.

## Setup and migration

The signed binary owns embedded configuration templates, discovery, approval plans, installation receipts, versioned binaries, product aliases, same-name launchers, workload launchers and desktop entries, policy and user-configuration installation and compare-and-swap updates, system service assets, enrollment and rotation, activation, verification, diagnostics, repair, migration, rollback, and uninstall. `dev-auth setup template deployment|administrator-policy|user-only-policy|user-config` prints a version-matched nonsecret starting document, so a source checkout is never needed to begin setup. Discovery checks fixed platform candidates and never blindly trusts caller `PATH`. `dev-auth build-info` emits machine-readable product, version, and embedded source commit; the signed stable manifest carries the same exact source commit alongside the artifact digest.

The account-neutral [deployment example](../crates/dev-auth/deployment-v1.example.toml) is the complete nonsecret setup input. On a new Linux machine, an authenticated compatible bootstrap and the source documents are sufficient; neither a Dev Tools nor Syscfg checkout participates at runtime. The operator first runs configuration-aware discovery, then approves one canonical plan, supplies any required credential through a private channel, and verifies that exact plan:

```text
dev-auth setup template deployment > /absolute/source/deployment.toml
dev-auth setup template administrator-policy > /absolute/source/policy.toml
dev-auth setup template user-config > /absolute/source/config-v2.toml
dev-auth setup discover --mode strong --administrator-policy /absolute/source/policy.toml --user-config account-name=/absolute/source/config-v2.toml
sudo dev-auth setup plan --deployment /absolute/source/deployment.toml --output /run/dev-auth-setup-plan.json --format json
sudo dev-auth setup apply --plan /run/dev-auth-setup-plan.json --sha256 APPROVED_DIGEST --credential-file automation=/run/dev-auth-private/service-token --format json
sudo dev-auth setup verify --plan /run/dev-auth-setup-plan.json --sha256 APPROVED_DIGEST --format json
```

The credential pathname is illustrative: strong setup accepts it only when it is an owner-only, single-link regular file on an approved memory-backed filesystem, and setup never reads an unnecessary `enroll-if-absent` source. A second plan/apply against the same deployment must return `changed=false`. `setup rollback` removes normal same-name routing before switching the retained release, and `setup uninstall` removes only receipt-owned product artifacts. Dev-auth diagnoses missing native Git, GitHub CLI, 1Password CLI, OpenSSH, systemd, polkit, or configured sandbox programs with package hints; it never calls a platform package manager.

For operator acceptance of a standalone-installed build, the repo also carries [`scripts/dev-auth-setup-acceptance.sh`](../scripts/dev-auth-setup-acceptance.sh). It runs the real standalone `discover`, `setup plan`, `setup apply`, and `setup verify` sequence against a supplied deployment document, keeps a private temp log and plan, authenticates sudo once for strong mode, and by default requires the second `setup apply` pass to report `changed=false`. Strong setup executes only the canonical root-owned installed binary as root; the repository harness remains unprivileged. The harness accepts credential files or one standard-input slot but intentionally leaves already-open file-descriptor transport to direct `setup apply`, because sudo may close caller file descriptors. It rejects a raw Cargo-built binary outside the immutable `.../versions/<version>/dev-auth` layout; that source path remains covered by Rust tests. The script is tracked acceptance tooling, while the supported end-user interface remains `dev-auth setup ...`.

Setup installs and verifies a candidate without changing ordinary human command resolution until every prerequisite is ready. Product aliases are installed first; administrator policy, user configuration, credential enrollment, broker readiness, workload launchers, and desktop entries are separate explicit gates. The historical `git-dev-auth` and `gh-dev-auth` names are compatibility entry points for an installed v0.2 rollback line and are not the v0.3 routing interface; normal v0.3 traffic uses only same-name `git` and `gh`. Global same-name launchers are activated last; session-private aliases are created after workload admission and removed when that workload ends. Missing credential input leaves services stopped and both global and workload same-name launchers absent. The noninteractive plan/apply interface binds installation to an authenticated signed release, exact source commit, manifest generation, and approved plan digest, while `discover` reports fixed candidate programs, workload launchers, desktop entries, and strong-backend availability without reading secrets. `dev-auth setup readiness --mode strong|user-only` performs a read-only value-free check and names exactly one next operation.

Version changes first remove any legacy global same-name launchers. A strong update additionally requires both broker sockets absent; a user-only update requires no live per-workload session directory. This prevents a new executable from speaking to an old broker or silently changing installation mode. Authenticated installs retain the trusted-root generation, manifest generation, source commit, and artifact digest; apply re-verifies the signed root, manifest, and artifact paths from the approved plan, rejects generation rollback or identity reuse, and cannot replace an authenticated install with an unsigned update. Strong upgrades verify the installed service files against the prior receipt before replacing them, map systemd-activated sockets by their exact descriptor names rather than dependency order, and retry bounded transient broker unavailability before activation. If an interrupted strong setup left the exact approved user document root-owned, resume reassigns only that nofollow-opened, single-link artifact to the native account before continuing. Repair and reinstall preserve only receipt-owned artifacts and reject symlink, ownership, permission, digest, alias, desktop-entry, or system-asset drift.

A v1 migration begins with `setup migrate-v1-preview`, which is read-only and omits secret references. `setup migrate-v1` requires the approved digests of both the current v1 document and an explicit v2 user configuration, proves the v2 resolution does not widen v1 programs, workspaces, GitHub scope, author identity, secret references, or SSH operation keys, writes an exact owner-private backup under `~/.config/dev-auth/migrations/v1/<sha256>/config.toml`, and only then installs v2. The original v1 file remains unchanged for rollback. The installed v0.2 release and its configuration remain reversible until v0.3 clean-device and rollback acceptance complete.

Normal uninstall preserves policy and credential enrollment throughout the rollback window. After the installation and all receipted launchers are absent, the separate `setup purge-system-state` or `setup purge-user-state` operation removes only safe owner-bound v2 policy/configuration and the matching broker credential; it never removes the v1 configuration or migration backup. This split keeps ordinary rollback reversible and makes permanent credential removal deliberate and idempotent.

## Sandboxes and platforms

Admission occurs outside an optional sandbox, and the sandbox remains inside the admitted operating-system boundary. Firejail, Bubblewrap, and container launchers are generic administrator-pinned adapters rather than hard-coded product cases. Each adapter declares required launcher and broker-socket visibility, peer-identity preservation, retained cgroup and descendant containment, inherited or isolated networking, and direct-argv read-only/read-write mount templates. Dev-auth expands only the policy-approved canonical workspace roots into those templates; it does not evaluate shell text. The adapter starts an internal probe before the workload: reaching that probe proves executable and broker-socket visibility, the broker reauthenticates the sandbox peer, strong mode rechecks the exact retained cgroup, and the probe verifies the declared network namespace plus every canonical workspace mount and its effective read/write state before re-resolving the workload and launcher. A hidden socket, escaped cgroup, ambiguous UID mapping, inaccessible launcher, incorrect mount access, or incompatible namespace fails closed before the workload starts. Sensitive dependencies are resolved by administrator-pinned paths, never through caller `PATH` or `firecfg` replacements.

The broker emits structured value-free lifecycle and capability audit records. Public resource selectors are represented only by hashes; credential values, tokens, private references, payloads, signatures, owners, and repositories are not serialized. A background reaper invalidates dead or expired supervised sessions and invokes provider revocation even when no later client request arrives.

Linux is the first strong backend. Windows Job Objects, named pipes, and Credential Manager; macOS audit tokens, XPC, and Keychain; and WSL each remain behind platform interfaces without a support claim until native acceptance passes.

## Release acceptance

Release acceptance includes semantic passthrough, unknown future Git and GitHub CLI commands, the multiword VS Code `GIT_EDITOR` regression, admitted credentials and API access, denied resources, no human fallback, subagents and fresh shells, concurrent workloads, broker restart, daemonization, teardown, token refresh and revocation, credential absence from process and persistent surfaces, sandbox positive and negative probes, standalone clean-machine installation, Syscfg-as-client installation, rollback, and hot-path performance. No normal command may reintroduce per-command Python, artifact hashing, repository traversal, or a maintained upstream command grammar.
