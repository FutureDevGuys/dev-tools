# Shared Rust crates

Dev Tools exposes narrowly scoped Rust foundations for products and downstream consumers. Each crate is independently versioned and publishable to crates.io; a released product compiles the required implementation into its own binary and has no runtime dependency on another Dev Tools product.

The public package set is `dev-tools-command`, `dev-tools-product`, `dev-tools-installation`, `dev-tools-privilege`, `dev-tools-reconcile-protocol`, `dev-tools-release`, and `dev-tools-update`. Their initial public API line is `0.1.x`. Within this workspace, internal dependencies use both a local path and a compatible SemVer requirement. Outside the workspace, consumers use only the registry version and commit its registry checksum in `Cargo.lock`.

Package readiness is distinct from registry publication. Native `release-admin crate-set package` requires a clean exact checkout containing only regular tracked files, makes two private non-local clones of that commit, runs retained Git and Cargo identities with Cargo offline, rejects symlinks and submodules, and publishes only byte-identical package results. `crate-set build` constructs an operation-only signed `dev-tools-crate-set-v1` authorization inventory binding the fixed crates.io registry, declared source commit, and exact name, stable version, length, and SHA-256 of every package; `crate-set verify` authenticates the root, inventory, embedded package identity, clean VCS snapshot, and local package bytes without network access. Cargo explicitly does not treat its embedded VCS snapshot as proof of provenance, so the independent construction gate is mandatory before signing. Packages are processed in dependency-order batches so each non-path dependency is already anonymously visible from the registry before its dependent package is constructed. The first version uses the bounded Linux-only `crate-set bootstrap-publish` path with an explicit stdin token that never enters Cargo configuration, argv, environment variables, or persistent storage; Cargo receives it only after its package checksum matches the signed inventory. After upload, `crate-set verify-registry` anonymously requires the exact version and checksum in the crates.io sparse index, rejects yanked or ambiguous records, downloads only from the fixed crates.io artifact authority, and verifies exact signed bytes. Subsequent releases use short-lived crates.io Trusted Publishing authority. Downstream production cutover remains blocked until the initial versions and Trusted Publisher bindings are accepted. A downstream must not substitute a Git revision or neighboring checkout while waiting. Cutover requires the exact registry version, its lockfile checksum, reproducible construction evidence, and the signed crate-set matching anonymously downloaded registry bytes.
