# Artifact Update

`doctor --json` emits `dev-tools-operation-result-v1` on success and configuration/invocation rejection. Its `scope: configuration` limits `healthy` to catalog validity; it does not verify installed artifacts or release authenticity. `changed` and `network_accessed` are false. Missing or invalid configuration returns exit 2 with a fixed error kind and no configuration content. This intentionally replaces the planned product's earlier `artifact-update-doctor-v1` output; source consumers must update their schema checks. Human success output is unchanged. [ADR 0016](adr/0016-artifact-update-common-doctor-result.md) records the compatibility boundary and release acceptance still required.

`artifact-update` is a standalone, configuration-driven updater for independently packaged applications and assets. It compiles the same `dev-tools-update` library that public Dev Tools products use; products do not invoke the sibling CLI for normal update behavior.

The `artifact-update-config-v1` document is local authority. Each artifact has a stable identifier, package kind, source, version convention, verification policy, and ordered target selectors. Exact names, anchored globs, and Rust linear-time regular expressions are deterministic; a selector matching multiple assets fails as ambiguous instead of guessing. Named captures are limited to version, channel, operating system, architecture, libc, runtime, and variant.

`artifact-update list`, `status`, and `doctor` are local-only operations. `status` reports available and receipt-owned installed versions when local evidence supports them, but never assumes an installation is current. `check` explicitly queries GitHub, GitLab, Forgejo, Gitea, npm distribution tags, the crates.io sparse index, Maven metadata, Sparkle appcasts, zsync control files, header-only direct/final URLs, static HTML inventories or locally mapped generic JSON/XML release metadata through the shared native HTTPS transport and applies the configured version and asset selection. On Linux it persists successful conditional provider checks in owner-checked atomic cache entries and accepts static signed-manifest metadata through a separately initialized durable ledger. The initial Linux `install ID` (including `--offline`) and network-free `rollback ID` and `recover ID` paths accept only explicitly configured native-target signed binary layouts. Local `config inspect` and `config apply` provide digest-guarded whole-document editing on Linux. Ownership-safe abandoned-staging recovery, native storage backends and native-platform acceptance remain gated rollout work; the declared source catalog does not imply additional providers.

The configuration parser is strict, one-megabyte bounded, rejects unknown fields and duplicate identifiers, and compiles selectors once per load. A catalog accepts at most 256 selectors overall and 64 per artifact. Each expression has a 1,024-byte source limit, a 64-KiB compiled-program limit, and a 64-KiB DFA-cache limit. Selection accepts at most 4,096 candidates and requires the entire filename to match, including when a regex contains alternation. Named `os` and `architecture` captures must equal the requested target; other captures remain inert metadata. Explicit selector target constraints apply as well.

`artifact-update completion bash|zsh|fish|elvish|powershell` prints the selected shell's completion script to stdout without loading configuration, invoking a shell, contacting a provider, or installing anything. Suggestions describe implemented commands and their options; artifact IDs remain user-supplied rather than triggering discovery during completion. The generated scripts may use the shell's normal filename completion for path arguments. Startup-file installation remains an explicit user action. Output is generated by the workspace's existing `clap_complete` backend from product-owned static metadata; it does not replace the current command parser or advertise the unfinished common self-update interface.

An artifact may declare an optional local `installation` table with `type = "versioned-binary"`, `data_root`, `bin_dir`, `artifact_name`, and `aliases`. This first layout applies only to `native-binary`, `go-binary`, and `app-image` kinds. Roots must be distinct, non-overlapping, absolute normalized paths in the current platform's native syntax, bounded to 4,096 bytes; Windows device/UNC and alternate-data-stream forms are not admitted. Filenames are bounded ASCII single components; aliases contain 1–32 names without case-insensitive duplicates or Windows reserved device names. Paths, aliases, commands and privilege are never supplied by release metadata. Parsing performs no filesystem access, and omitted installation policy remains unconfigured. A desired layout is not receipt ownership or release authentication; check-only sources remain check-only.

Candidate URLs use the existing HTTP URI parser and require HTTPS with a nonempty authority, no user information, no fragment, and a valid port when supplied. Candidate filenames reject path separators, control characters, and dot-directory names. This syntactic check is not network authorization: future fetching also enforces locally declared host, redirect, and size policy. Install-capable verification is separate from version discovery; `check-only` sources never authorize mutation. Signed-manifest configuration pins a local hexadecimal Ed25519 `trusted_root_public_key` alongside its root-document URL; a remote root URL alone supplies no trust anchor.

For example, a check-only catalog can describe an unrelated packaged executable without knowing its implementation language:

```toml
schema = "artifact-update-config-v1"

[[artifacts]]
id = "example"
kind = "native-binary"
source = { type = "github", owner = "ExampleOrg", repository = "example" }
version = { type = "semver-tag", prefix = "v" }
verification = { type = "check-only" }
selectors = [{ type = "glob", pattern = "example-*-linux-x86_64", os = "linux", architecture = "x86_64" }]
```

Inspect it with `artifact-update list --config /absolute/path/config.toml --json` or `artifact-update status --config /absolute/path/config.toml --json`. Query releases with `artifact-update check example --config /absolute/path/config.toml --json`; `check --all` checks the catalog, and `--os` plus `--architecture` can select an explicit discovery target instead of the current native target. Static signed-manifest checks use only their locally configured exact target and reject these overrides before retrieval. These checks do not download or execute artifacts, invoke Git/gh/curl, or authorize installation. The output labels provider release observations as unverified and never treats a provider error as current. Linux status reads cached metadata for the current native target and displays available versions only within the 24-hour freshness window; installation observations require separate receipt custody. Missing, expired, or future-dated metadata is never evidence that an installation is current.

GitHub discovery reads at most ten pages of one hundred releases with a two-megabyte limit per response and one sixty-second request budget per artifact. A full final page is an incomplete-inventory error rather than a claim of exhaustive selection. Duplicate release tags, equal ordered-version precedence, and multiple matching assets fail as ambiguous. Drafts and prereleases are excluded. Selection chooses the newest matching target under the configured rule; it does not infer commands or installation hooks from assets.

For GitLab, replace the example source with `source = { type = "gitlab", api = "https://gitlab.example/api/v4", project = "group/subgroup/example" }`. The API base is explicit HTTPS, ends in `/api/v4`, and contains no credentials, query, fragment, percent escapes or dot-directory components. The unencoded project is a numeric ID or slash-separated path with at most sixteen bounded ASCII components and 1,024 total bytes; traversal and pre-encoded separators are rejected. Requests encode those project separators and use locally generated offset pages, sorted by release date descending. Retrieval admits only the configured host, at most two redirects and the same ten-page, hundred-release, two-MiB and sixty-second bounds as GitHub. This initial adapter is anonymous; it does not discover tokens or support private-project authentication.

GitLab discovery consumes named HTTPS `assets.links` entries from the [project release API](https://docs.gitlab.com/api/releases/), not source archives, release-evidence URLs or executable instructions. Releases marked upcoming are excluded; stable SemVer filtering and duplicate/ambiguous selection use the same local rules as GitHub. Checks and target overrides remain metadata-only. A provider observation never authorizes installation, regardless of asset filename or evidence fields.

For Forgejo, use `source = { type = "forgejo", api = "https://forge.example/api/v1", owner = "ExampleOrg", repository = "example" }`. The explicit HTTPS API base ends in `/api/v1` and rejects credentials, query, fragment, percent escapes and dot-directory components. Owner and repository are literal bounded ASCII components, not paths or pre-encoded values. Discovery reads named HTTPS release attachments, excludes drafts and prereleases, and ignores archive URLs and release-body instructions. It is anonymous and admits redirects only within the configured host; private authentication is not claimed. Gitea uses its own explicit source type below.

Forgejo's [pagination policy](https://forgejo.org/docs/latest/user/api/usage/) permits instance-specific page-size limits. The adapter requests up to one hundred releases per page but continues after short nonempty pages and requires an empty terminal page. Ten requests, two MiB per response and one sixty-second budget bound each complete check, including that terminal request. Reaching the bound without completion fails instead of returning a partial inventory. `check_forgejo_release_cached` and `ForgejoMetadataCache` retain the complete page sequence in the distinct `dev-tools-forgejo-metadata-cache-v1` schema under the same 32-MiB codec bound. Missing terminal pages, extra pages, resource mismatches and failed refreshes cannot produce a successful cached check; local status reselects without writes or retrieval. Forgejo observations remain unverified and cannot authorize installation.

For Gitea, use `source = { type = "gitea", api = "https://gitea.example/api/v1", owner = "ExampleOrg", repository = "example" }`. The local API-base and literal owner/repository restrictions match Forgejo's. The adapter uses the [Gitea 1.25 release-list contract](https://docs.gitea.com/api/1.25/operations/repo-list-releases/), reading `tag_name`, draft/prerelease flags and named HTTPS attachment download URLs. The shared page parser does not select source archives, evaluate release-body instructions, look up credentials or authenticate artifact bytes. Compatibility concerns this release API shape, not all Gitea operations or server versions.

Gitea retains its own `GiteaMetadataCache`, `check_gitea_release_cached` and `dev-tools-gitea-metadata-cache-v1` schema. Checks request locally generated pages until an empty terminal page, under the same ten-request, hundred-record-per-page, two-MiB-per-response, sixty-second and two-same-host-redirect bounds as Forgejo. A short nonempty page cannot establish completeness, and cached pages must match the exact current resource sequence including its terminal page. The 32-MiB cache codec, local reselection, failure-preserving conditional refresh and check-only installation boundary apply independently. Existing Forgejo APIs and persisted bytes remain unchanged.

For a complete single-document JSON feed, use `source = { type = "generic-json", url = "https://updates.example/catalog.json", mapping = { releases = "/releases", tag = "/version", assets = "/assets", name = "/name", url = "/url" } }`. The `releases` pointer starts at the document root; `tag`, `assets`, and optional `draft`/`prerelease` pointers start at each release; `name` and `url` start at each asset. Mappings are local JSON Pointer strings, not scripts or query expressions. Empty pointers select the current root; `~1` and `~0` encode literal slash and tilde. Each pointer is bounded to 512 UTF-8 bytes and sixteen segments and rejects control characters and malformed escapes. URI-fragment pointer syntax is not accepted.

The mapped releases value must be an array of at most 1,000 entries. Every release has a string tag, and any configured draft/prerelease pointer must resolve to a boolean; omitted flags default to false. Included, parseable releases require an assets array of at most 4,096 entries with string names and HTTPS URLs. Duplicate object members anywhere in the JSON document, missing or mistyped mapped values, and ambiguous selection fail closed. Drafts, prereleases and locally unparseable versions are excluded under the shared selection rules. Parsing retains the JSON decoder's recursion bound.

Generic JSON retrieves only the explicitly configured HTTPS resource, with at most two same-host redirects, a two-MiB response bound and a sixty-second budget. It does not follow remote pagination or interpret remote mappings, commands or destinations. Selection is complete only within that response: configure a complete unpaginated feed when comparing all releases, not one page of a larger inventory. It performs no ambient credential lookup. `check_generic_json_release_cached` and `GenericJsonMetadataCache` retain exactly one resource in the distinct `dev-tools-generic-json-metadata-cache-v1` schema with the 32-MiB codec bound. Conditional reuse and local observation reparse the original bytes under current local mappings and selectors; failed checks preserve the prior cache without reporting it as a successful refresh. These observations remain unverified and never authorize installation.

For npm metadata, use `source = { type = "npm", registry = "https://registry.npmjs.org", package = "@scope/tool", tag = "latest" }` with `kind = "node-package"` and typically `version = { type = "semver-tag", prefix = "" }`. The registry is an explicit HTTPS base without a query, credentials or pre-encoded path; package names are bounded to 214 ASCII bytes, with lowercase alphanumeric-leading literal components and optional `@scope/`. Distribution tags are bounded alphanumeric-leading components beginning with a letter and cannot be SemVer ranges. No registry, scope, token or credentials are inferred from `.npmrc`, environment variables or the npm CLI.

The adapter requests one `/{encoded-package}/{tag}` version document and requires its `name` to match the configured package and its `version` to be strict SemVer. Prereleases are excluded independently of the local version rule. The only candidate is `dist.tarball`, which must be HTTPS; its final raw URL path segment supplies the filename, without query text or percent-decoding. Current local version and asset rules may exclude it. This reports the selected distribution tag, not the highest published version, dependency resolution or the engine/platform compatibility decisions of `npm install`. Remote scripts, destinations, engine constraints, dependency declarations, integrity fields and signature fields provide no execution or authentication authority. No package bytes are downloaded or executed.

Npm retrieval explicitly requests JSON through `fetch_conditional_json_https` and uses the existing two-MiB response limit, sixty-second budget and two same-host redirects. Duplicate JSON members anywhere are rejected. `NpmMetadataCache` and `check_npm_release_cached` retain exactly one resource in `dev-tools-npm-metadata-cache-v1`, with the 32-MiB codec bound, conditional reuse and current-local-rule reselection. Failed refreshes preserve prior cache bytes without claiming success; these observations remain check-only. See the [npm registry API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md) and [distribution-tag semantics](https://docs.npmjs.com/cli/v8/commands/npm-dist-tag/).

For crates.io archives, use `source = { type = "crates-io", package = "base64" }`, `kind = "tar"`, `version = { type = "semver-tag", prefix = "" }` and a selector such as `pattern = "base64-*.crate"` with `type = "glob"`. Package names are literal ASCII identifiers of at most 64 bytes, beginning with a letter and containing only letters, digits, hyphens or underscores. This provider fixes the public sparse index and static download host; it neither reads Cargo configuration/credentials nor accepts a custom registry. The index path lowercases the name using Cargo's length-dependent directory layout; each record must retain the exact configured package identity.

The adapter parses one UTF-8 newline-delimited JSON index document, bounded to two MiB and 1,000 records. It rejects empty/blank records, duplicate JSON members, malformed strict SemVer, missing boolean `yanked` fields, unsupported schema versions (only omitted, 1 or 2 are admitted), and duplicate versions even when they differ only in build metadata. Yanked releases and prereleases are excluded independently of local ranking. The candidate filename and URL are derived as `{package}-{version}.crate` and `https://static.crates.io/crates/{package}/{package}-{version}.crate`; remote dependencies, URLs, checksums and build metadata cannot supply commands, destinations or verification authority. This does not resolve dependencies, check compiler compatibility, compile or install a crate. Use SemVer ranking for highest-version selection; provider-order preserves index order and is not a latest-version query.

`CratesIoMetadataCache` and `check_crates_io_release_cached` retain exactly one resource in `dev-tools-crates-io-metadata-cache-v1`, using the existing 32-MiB codec bound, sixty-second request budget and two same-host redirects. Conditional reuse and local observation reselect original bytes under current local rules, and failed refreshes preserve prior cache bytes without fallback success. These observations remain unverified and check-only. The public sparse index is the recommended access path for a small number of crates: see [crates.io data access](https://crates.io/data-access) and the [Cargo registry index specification](https://doc.rust-lang.org/cargo/reference/registry-index.html).

For Maven, use `source = { type = "maven", repository = "https://repo.maven.apache.org/maven2", group = "org.apache.commons", artifact = "commons-lang3", extension = "jar" }`; optional `classifier = "sources"` selects a derived classifier path. The repository is explicit HTTPS without credentials, queries, percent escapes or dot-directory components. Coordinate components are bounded ASCII, begin with an alphanumeric character and otherwise admit letters, digits, hyphens, underscores and dots. The group is at most 1,024 bytes and sixteen nonempty dot-separated components; individual components, artifact and classifier are at most 128 bytes, and the nonempty dot-separated extension is at most 32 bytes. No Maven settings, credentials, POMs, plugins or dependency resolution are consulted.

Discovery retrieves only `{repository}/{group-with-dots-as-slashes}/{artifact}/maven-metadata.xml`. It requires exact `groupId` and `artifactId`, one `versioning/versions` inventory and at most 1,000 versions. It ignores `latest` and `release` for ranking: Maven defines these as the last version added, not the highest version. Versions ending in `-SNAPSHOT`, case-insensitively, are excluded. Other versions use the configured local ordering and selector rules; no Maven `ComparableVersion` compatibility is claimed. Version strings are bounded to 128 ASCII bytes, begin with an alphanumeric character and otherwise admit alphanumerics, dots, hyphens, underscores and plus signs. Candidate URLs follow the [Maven repository layout](https://maven.apache.org/repositories/layout.html), using only the local extension/classifier and validated version. The inventory confirms a version, not existence of every classifier/extension combination; the derived URL is not fetched or authenticated by a check. See the [Maven metadata model](https://maven.apache.org/ref/3-LATEST/maven-repository-metadata/repository-metadata.html).

The accepted XML subset is UTF-8 XML 1.0, with either no element namespace or the literal `http://maven.apache.org/METADATA/1.1.0` namespace consistently throughout. Element and attribute names use bounded ASCII qualified names. Text, CDATA, comments and standard XML character/entity references are accepted; DTDs, custom entities and processing instructions are rejected, and nothing resolves an external entity. The streaming parser bounds nesting to 64 levels, total events to 16,384, attributes per element and in-scope namespace bindings to 64, and captured scalar text to 1,024 bytes. Duplicate required fields, duplicate expanded attribute names, multiple roots, mismatched/unclosed tags, nested scalar elements and invalid XML characters fail closed. The existing two-MiB response limit, sixty-second budget and two same-host redirects apply. `MavenMetadataCache` and `check_maven_release_cached` retain one resource in `dev-tools-maven-metadata-cache-v1` under the 32-MiB codec bound, reselect current local coordinates/rules on reuse, and preserve prior bytes after a failed refresh. Observations remain unverified and cannot authorize installation.

For Sparkle appcasts, use `source = { type = "sparkle", url = "https://updates.example/appcast.xml", version_field = "bundle-version" }`. The version field is required: `bundle-version` reads Sparkle's internal version, while `short-version` reads its display version. Choose a corresponding local version rule, such as `numeric` for numeric build numbers or `semver-tag` for strict semantic display versions. The adapter accepts the selected field as a direct item element or legacy direct-enclosure attribute, following [Sparkle's publishing format](https://sparkle-project.org/documentation/publishing/); repeated element fields or conflicting values fail closed rather than choosing one. There is no automatic fallback between version fields.

This adapter accepts one unnamespaced RSS 2.0 root and channel, with at most 1,000 direct items. Sparkle fields are matched by the exact `http://www.andymatuschak.org/xml-namespaces/sparkle` namespace, independently of prefix. Each item requires the selected version field, including excluded items; nonempty named channels are excluded. Only direct item enclosures become candidates, with at most 4,096 per item. Each URL must be absolute HTTPS without credentials or fragments, and its final raw path segment supplies the inert filename. Delta enclosures, release-note links, descriptions, signatures and other fields do not confer artifact or execution authority. Items without enclosures contribute no asset. Existing local ranking and selector ambiguity rules apply; neither Sparkle's native comparator nor OS/hardware, rollout, major-upgrade or informational-update policies are implemented. An observed candidate is not a device-compatibility decision or permission to install.

Sparkle reuses Maven's private bounded XML event reader without Maven's element-namespace restriction. The same UTF-8/XML 1.0, depth, event, attribute, scalar and transport limits apply; unknown namespaced metadata remains inert. DTDs, custom entities and processing instructions remain prohibited. `SparkleMetadataCache` and `check_sparkle_release_cached` preserve one exact resource in `dev-tools-sparkle-metadata-cache-v1` under the 32-MiB cache bound. Cached observation reselects under current local rules without networking or refreshing time, and failed conditional refresh preserves prior bytes. This adds no archive retrieval, extraction, signature verification or installation authority.

For a direct artifact URL or an endpoint that redirects to a versioned filename, use a header-only URL source:

```toml
source = { type = "url", url = "https://updates.example/latest", redirect_hosts = ["cdn.example"] }
version = { type = "numeric" }
selectors = [{ type = "regex", pattern = '^app-(?P<version>[0-9]+)\.zip$', os = "linux", architecture = "x86_64" }]
```

`check` sends only [HTTP HEAD requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2), requires a final HTTP 200 response and never falls back to GET or consumes the response body. Servers that reject HEAD return a failed check. At most two redirects and one sixty-second request budget apply, with the transport's 64-KiB response-header bound. The initial host is admitted automatically; optional `redirect_hosts` explicitly adds up to sixteen distinct canonical lowercase host strings or normalized bracketed IPv6 addresses, each at most 253 bytes. Schemes, paths, ports, credentials and wildcards are not host entries. Each redirect is checked before connection, and remote responses never add hosts to that policy.

The final URL's last raw path segment is the candidate filename; query strings, `Content-Disposition` and `Content-Location` do not supply filenames or application versions. As with zsync, ordered version rules require a named `version` capture in every local selector, while explicitly unordered rules may use the entire filename. A stable opaque filename cannot establish content changes, and a successful HEAD response does not authenticate or prove future availability of artifact bytes. `UrlMetadataCache` retains only original and final URLs in the 64-KiB `dev-tools-url-metadata-cache-v1` document. Status re-applies the current host policy and selectors without network access; checks do not reuse conditional validators, and failed probes preserve prior observation bytes. Existing check-only installation refusal remains unchanged.

For zsync control metadata, configure an explicit HTTPS URL and extract the application version through an existing filename selector:

```toml
source = { type = "zsync", url = "https://updates.example/latest.zsync" }
version = { type = "numeric" }
selectors = [{ type = "regex", pattern = '^app-(?P<version>[0-9]+)\.AppImage$', os = "linux", architecture = "x86_64" }]
```

Every selector used with an ordered zsync version rule must declare a named `version` capture. Optional captures that are absent in a matched filename fail rather than supplying a made-up version. With explicitly selected `opaque-check-only` or `provider-order`, a selector without that capture uses the filename as an unordered identifier; a constant filename cannot establish whether application contents changed. The `zsync` header identifies the generator, not the application's version. This adapter does not inspect an installed AppImage's ELF update-information section or run an AppImage, AppImageUpdate or zsync command.

The [zsync control format](https://github.com/cph6/zsync/blob/master/SPEC.md) has textual headers followed by binary block-checksum records. This metadata adapter requires a filename, positive target length, power-of-two block size and at least one full-file URL. It accepts LF or CRLF headers, rejects duplicate non-URL fields and legacy `Z-Map2`/0.0.4 control formats, and checks the exact checksum-section length using `Hash-Lengths` or the documented defaults. Recognized strong-hash labels are MD4, MD5, SHA-224 and SHA-256; no digest is calculated or used as authentication. MTime, whole-file digests, safe-field hints and unknown textual fields remain inert. Header bounds are 64 KiB total, 128 lines, 8,192 bytes per line and 64 URLs; the full control response remains bounded to two MiB.

Relative full-file URLs resolve against the final admitted metadata request URL, not the originally configured redirect URL. References may identify a different HTTPS host as inert candidates, but are never fetched by `check`; metadata redirects remain limited to two within the configured host and one sixty-second budget. Filenames remain inert validated names, not destinations. Multiple matching mirror candidates fail as ambiguous rather than assuming their contents agree. `ZsyncMetadataCache` retains original bytes, original resource identity and final location in `dev-tools-zsync-metadata-cache-v1`, sharing existing bounded page and validator validation without changing other provider cache formats. Cached observation reselects local rules without network access; redirected resources retain no original-URL validators, and failed checks preserve prior cache bytes. Check-only observations do not implement delta reconstruction, verify an AppImage signature, prove platform compatibility or grant installation authority.

For RSS, Atom or custom XML inventories, `generic-xml` uses exact local field mappings, not XPath or executable expressions. For example, an RSS feed whose item titles are numeric release versions can use:

```toml
source = { type = "generic-xml", url = "https://updates.example/feed.xml", mapping = { inventory = [{ name = "rss" }, { name = "channel" }], release = { name = "item" }, version = { path = [{ name = "title" }] }, assets = [{ name = "enclosure" }], url = { path = [], attribute = { name = "url" } } } }
```

`inventory` includes the root and must resolve to exactly one container. `release` selects its direct children. `version`, `assets`, `url` and optional `name` use relative direct-child paths; an empty path means the current element. Scalar mappings select either leaf text or an explicit attribute, trim surrounding whitespace and require exactly one element and value. Omit `name` to use the final raw URL path segment. Optional `asset_filter = { attribute = { name = "rel" }, equals = "enclosure" }` admits only assets whose attribute exactly matches; missing attributes exclude that asset. Element and attribute names use optional `namespace` URIs, never prefix strings. Each path has at most 16 steps, and names are bounded literal ASCII XML names without wildcard syntax.

For an [Atom feed](https://www.rfc-editor.org/rfc/rfc4287.html), map `feed`, `entry` and `link` with `namespace = "http://www.w3.org/2005/Atom"`, map the asset URL to the unnamespaced `href` attribute and use the `rel` filter above. Select the version field explicitly: neither Atom nor [RSS](https://www.rssboard.org/rss-specification) supplies a universal application-release version convention. A title is usable only when the publisher's convention matches the configured local version rule. This adapter maps data rather than claiming complete RSS/Atom validation or global latestness beyond the configured document.

Generic XML validates the entire UTF-8/XML 1.0 document through the existing bounded reader before selection. Limits are two MiB, depth 64, at most 16,384 reader events, 64 attributes per element, eight MiB of retained expanded names/attributes/text, 1,000 releases and 4,096 candidate elements per release before filtering. DTDs, custom entities, processing instructions, ambiguous scalar paths and nested scalar text fail closed. HTTPS URLs must be absolute and credential/fragment-free; `xml:base`, pagination, scripts and remote policy fields are never followed or executed. The single-resource `dev-tools-generic-xml-metadata-cache-v1` cache reselects original bytes under current local mappings, supports conditional checks with failure-preserving replacement, and grants no authentication or installation authority.

For a static HTML download index, use `source = { type = "html", url = "https://updates.example/releases/" }` with local filename selectors. Ordered version rules require a named `version` capture in every selector, for example `version = { type = "numeric" }` and `selectors = [{ type = "regex", pattern = '^app-(?P<version>[0-9]+)\.zip$' }]`. Matching filenames supply versions; visible text, document titles, `download` attributes and scripts do not. Ranking uses the existing local version rule. Duplicate matching candidates, including repeated links to the same version, fail as ambiguous. Explicitly unordered rules may use complete filenames; `provider-order` preserves link order in the response, not publication chronology.

The initial HTML adapter uses the [html5gum tokenizer](https://docs.rs/html5gum/0.8.4/html5gum/) without a DOM, JavaScript engine or CSS selector language. It accepts UTF-8, quoted/unquoted HTML attributes, case-insensitive tag/attribute names and HTML character references, while rejecting tokenizer errors such as duplicate attributes. Raw-text/RCDATA handling keeps script, style, title and textarea contents from contributing links. SVG, MathML, `template` and `noscript` contexts are rejected because their interpretation requires document-tree or scripting state; full browser-grade parsing is not claimed. End-tag balancing and browser error recovery are not implemented. A page requiring client-side rendering is not a static inventory.

Only `a` elements with `href` contribute candidates. Relative references resolve against the final admitted page URL, while `base` elements are ignored. Empty and fragment-only references, directory paths, and references that do not resolve to admitted HTTPS candidate syntax are omitted; candidates on other hosts remain inert and are never fetched. The final raw path segment supplies the filename, without percent-decoding. Limits are two MiB of input, 16,384 emitted tokens, 128 bytes per start-tag name, 64 attributes per start tag, 4,096 anchor elements before filtering, 4,096 bytes per anchor reference and 1,000 matching release candidates. Completeness concerns that one response only; there is no pagination or linked-page traversal.

The HTML metadata request admits only its configured host, with two redirects and one sixty-second budget. `HtmlMetadataCache` retains original bytes and final location in the distinct 32-MiB-bounded `dev-tools-html-metadata-cache-v1` schema. Current local selectors, target and host policy are reapplied during network-free observation and conditional reuse. Redirected resources retain no original-resource validators; malformed or failed refreshes preserve prior cache bytes without fallback success. HTML observations are unverified and never authorize installation, execution or arbitrary destinations.

`semver-tag` uses the exact local prefix and stable SemVer precedence, excluding prerelease tags even if provider flags are wrong. `numeric` compares up to thirty-two dot-separated decimal components without machine-integer overflow; leading zeroes and absent trailing zero components do not change precedence. `calendar` accepts exact Gregorian `YYYY-MM-DD` dates with leap-year validation. `provider-order` and `opaque-check-only` preserve the provider's first matching release and never invent a lexical ordering for opaque versions.

`calendar-tag` adds an explicit literal `prefix` (empty when omitted) and a required `format`: `yyyy-mm-dd`, `yyyy.mm.dd`, `yyyymmdd`, `yyyy-mm`, or `yyyy.mm`. For example, `version = { type = "calendar-tag", prefix = "release/", format = "yyyy.mm.dd" }` selects tags such as `release/2024.02.29`. Prefixes are bounded to 64 UTF-8 bytes and reject control characters. Dates require exact zero-padded ASCII components, years 0001–9999 and valid Gregorian months/days; year-month formats compare release periods without claiming a day. The available version omits the prefix but retains the configured date spelling. There is no format guessing, locale, timezone, two-digit year, free-form formatting language or automatic numeric suffix. Invalid dates and nonmatching prefixes are excluded from discovery; explicit comparisons reject them. Cache observations reselect original metadata under the current local format. Existing `calendar` remains exactly `YYYY-MM-DD`. Version and verification rules reject unknown fields, including unit-style rules such as `calendar` and `check-only`.

The shared `compare_release_tags` operation compares an available full tag against a caller-owned installed full tag with those same rules, without invoking a program or contacting a provider. Ordered versions report newer, older, or equivalent; opaque and provider-ordered tags report only equivalent or changed. Invalid, empty, control-bearing, or oversized tags are errors, not evidence of a current installation. Comparison does not authenticate the tags or grant installation authority. Product receipt adapters must supply the installed identity; the current CLI reports installed and available evidence separately without yet applying this comparison to classify currentness.

The shared release transport exposes conditional metadata responses through `fetch_conditional_https`: bounded ETag/Last-Modified validators are sent only to their initial resource, and a 304 without that request's validators is rejected. Validators returned by a redirected resource are not retained for later replay against the original URL; such resources require a full fetch on the next check. A successful 304 carries no artifact or signature authority; the caller must bind it to its exact cached resource and configuration before reuse. The existing unconditional release API retains its fail-closed 304 behavior.

`check_github_release_cached` retains at most ten bounded metadata pages in a caller-owned `GithubMetadataCache`. It keys validators by exact generated resource URL, re-parses reused bytes under the current local selection rules, and replaces the page set only after the complete check succeeds. Provider failure, malformed metadata, or ambiguity returns an error without substituting a previous observation. This in-memory object is not authenticated release evidence; product adapters own durable storage and freshness.

The cache's strict `dev-tools-github-metadata-cache-v1` codec exports original response bytes as Base64 and accepts at most 32 MiB of serialized metadata. Decoding rejects unknown fields, malformed validators, changed resource URLs, extra or missing pages, and invalid metadata, then repeats selection under current local configuration. `observe` is a network-free operation on those bytes. The codec reuses the workspace's existing Base64 implementation and adds no new locked package.

`check_gitlab_release_cached` and `GitlabMetadataCache` provide the same bounded conditional-check and local reselection contract with a distinct `dev-tools-gitlab-metadata-cache-v1` schema. They share codec validation and exact-resource validator handling, not GitHub resource identity. A schema or project mismatch fails closed, and a failed refresh never replaces the previous page set or yields it as a successful check. Linux persistence selects the codec from current local source configuration and preserves the existing cache-header format and freshness rules.

The Linux product adapter stores entries beneath the native application cache root's `metadata-v1` directory. Its private 0700 directory and 0600 files use shared installation primitives, a nonblocking mutation lock, and atomic compare-before-replace publication for cooperating writers. A bounded single-line `artifact-update-cache-entry-v1` JSON header precedes the metadata codec document; it binds a SHA-256 key over length-delimited configuration bytes, artifact ID, OS and architecture, plus the successful check time. Symlinked or unsafe ancestor custody rejects; root-owned sticky temporary ancestors are allowed. Local status neither creates directories nor locks or refreshes files. Other native storage backends remain unimplemented; this Linux implementation is not an all-platform acceptance claim.

A nonempty relative `XDG_CACHE_HOME` is rejected rather than silently selecting a different home-directory cache. Cache authority must be an absolute native path.

Signed-manifest configuration requires explicit local `root` (HTTPS root-document URL), `trusted_root_public_key`, `product`, `target`, and `artifact_url` fields. A public key alone does not authorize an arbitrary signed product or download destination. The signed product identity is independent of the catalog's local `id`. This initial policy admits a single-target, source-commit-bound `dev-tools-product-v2` manifest with engine protocol 1 and an exact artifact URL; it requires a SemVer version rule. Other manifest formats and URL mappings are not inferred. This tightens the unreleased configuration foundation; existing incomplete signed-manifest declarations must supply those fields. The `release_authority` library method translates validated local policy only; it does not perform a check, accept a release generation, or authorize installation.

`verify_static_manifest_metadata` authenticates supplied static root/manifest bytes through `dev-tools-release` using that local authority. It returns fixed value-free authentication errors for invalid signatures or mismatched identities, and refuses check-only policy and other source types. Its tests use deterministic synthetic Ed25519 keys and real signed envelopes. This network-free seam does not advance anti-rollback state, authenticate downloaded artifact bytes, or establish that a release is latest; the product-bound durable acceptance transaction remains required before reporting accepted metadata.

The library's explicit `check_static_manifest` retrieves only the configured root and manifest, with a 512-KiB bound per document and one 60-second retrieval budget. Each resource permits at most two redirects within its own configured host; allowed-host spelling uses the shared transport's normalization, including uppercase DNS names and IPv6. It returns authenticated metadata and the original documents for a separate durable acceptance transaction, never downloads the artifact, and has no fallback on retrieval failure. The Linux CLI requires an existing ledger before retrieval and reports `verification: signed-metadata` only after the acceptance transaction commits. `installation_authorized` remains false.

`ManifestLedger` provides the authority-bound acceptance state machine and strict 4-KiB `dev-tools-manifest-ledger-v1` codec. It binds product, target and normalized pinned root key independently of catalog nicknames and retrieval URLs. Each transition authenticates the original metadata before applying shared rollback/equivocation checks; rejection leaves state unchanged. This is local state, not a signature or proof of retained artifact custody. The product owns filesystem validation, locking, atomic publication and missing-ledger detection, and does not put this ledger in an evictable metadata cache. Explicit first-use initialization cannot prove historical latestness.

The Linux ledger store requires explicit first use or an exact existing document identity, uses nonblocking locking and atomic compare-and-swap writes, and refuses an existing directory whose ledger is missing. A contended lock or stale document identity fails before the acceptance callback runs and leaves the current document unchanged. First use stages a complete empty ledger directory before atomically publishing it without replacement: an interruption before publication leaves the final path absent, and an interruption after publication leaves a complete directory. A concurrent initializer cannot be silently adopted. Cache and ledger directories share the same ancestor-custody checks but retain distinct lifecycles. Process termination can leave an unpublished staging directory; automatic orphan recovery is not implemented. A publication durability error requires inspecting the final state before retrying.

For a new signed authority, run `artifact-update trust initialize example --config /absolute/path/config.toml --json`. This local command is an explicit first-use decision, not an automatic repair or a release check. It stores state under absolute `XDG_STATE_HOME`, falling back only when that variable is unset or empty to an absolute home directory's `.local/state`. The product suffix is `artifact-update/release-ledgers-v1/<authority-id>`. Nonempty relative roots are rejected. Initialization returns `initialized` on creation, `already-initialized` with exit 3 for an existing valid ledger, or `authority-unavailable` with exit 4 for custody or publication failure. It does not replace existing state. Other platforms return `unsupported-platform` with exit 3. Signed checks with missing state stop before network access; do not initialize again merely to hide lost state, because initialization cannot reconstruct previous accepted generations. Restore trusted state when recovering an established authority.

Successful Linux signed checks retain the original root and manifest documents under the native cache root's `signed-metadata-v1` directory, after durable ledger acceptance. Each owner-only atomic entry uses an `artifact-update-signed-metadata-v1` header bounded to 4 KiB and two documents bounded to 512 KiB each; the length-delimited configuration/ID/domain key isolates this cache from GitHub observations. Cache publication failure reports a failed check but cannot undo the ledger commit. Repeating a check may refresh the cache timestamp without changing the ledger; `ledger_changed` reports only ledger mutation.

The signed-metadata part of local status reads without writes or locks, reauthenticates those original documents under current configuration, and requires an unchanged transition against the loaded ledger. Valid signatures alone are insufficient: newer-but-unaccepted, rolled-back, or forged evidence fails closed. Missing cache leaves status unknown without altering trust. Missing ledger reports `requires-initialization` without creating state; invalid custody or a cache/ledger mismatch reports `authority-unavailable` with exit 4. Fresh evidence can expose `available_version` and `manifest_generation`, but the overall outcome remains `unknown` and `installation_authorized` remains false. Evidence older than 24 hours or dated in the future exposes no available version.

When a binary installation layout is configured on Linux, status also inspects receipt-owned state with private `0700` data directories and a separately owned `0755` command directory. This read-only adapter checks ancestor custody and uses only an existing nonblocking installation lock; it never creates directories, recreates a lock, recovers a journal, repairs a link or executes an artifact. A valid matching receipt and bounded content verification expose `installation_state: managed`, `installed_version`, and `installed_verification: receipt-content`. The per-artifact read bound is 256 MiB, including any retained previous artifact. Receipt content is not signed release authentication, so these fields cannot authorize installation or establish that the release is current. Without a receipt, any configured alias entry is reported as `external`; otherwise installation state remains `unknown`. Missing or conflicting receipt-owned links, pending recovery, lock contention or unsafe custody produce `authority-unavailable` with exit 4, without repair.

Use `artifact-update trust status example --config /absolute/path/config.toml --json` to inspect ledger presence without network, directory creation, locks or file refresh. `present` means only that an authority-bound ledger passes local custody and decoding checks; it does not prove a latest release, artifact custody, or installation. `absent` is also a successful inspection, not approval to reset lost history. An initialization failure reports `changed: null` because a late durability error may occur after publication; inspect with this status command before deciding recovery, and do not treat presence alone as proof that a failed storage sync succeeded. Read-only status always reports `changed: false`.

`artifact-update trust recover example --config /absolute/path/config.toml --json` explicitly reconciles only that authority's initial-directory publication journal. It neither reads nor rewrites the final ledger, initializes lost state, restores history, verifies a release or authorizes installation. An absent journal is `unchanged` without creating state or locks. Successful journal-owned cleanup is `recovered`; `changed` describes that cleanup, not a ledger change. Errors use `authority-unavailable`, exit 4 and unknown change state once recovery is attempted. The `artifact-update-trust-v1` result remains network-free. A second successful recovery is unchanged. This operation is separate from signed installation-journal `recover ID`.

Retained signed evidence, when present under the configured data root's `release-evidence-v1` directory, is separate from the disposable discovery cache. Entries use the bounded signed-document codec and a domain-separated version/length/digest key. Status reauthenticates those documents against the initialized ledger's exact accepted root and binds the verified version, length and SHA-256 to the already content-verified receipt. Success exposes `installed_verification: signed-manifest-and-receipt-content`; it does not establish freshness, currentness or mutation permission. Missing evidence preserves the weaker receipt-content observation without creating storage. Present invalid evidence, absent acceptance state or a superseded root fails with exit 4. The timestamp is irrelevant to historical artifact authentication. Status does not refresh retained roots; the explicit installation path owns publication and refresh.

## Local configuration editing

`artifact-update config inspect --config /absolute/private/config.toml --json` reads the current configuration without creating directories or locks. It returns `absent` when missing, `valid` with `sha256` and `artifact_count` for a valid catalog, or `invalid-configuration` with the digest for a nonempty malformed document. The digest describes exact bytes, including comments; it is neither release authentication nor permission to perform an installation.

Create a configuration explicitly with `artifact-update config apply --from /absolute/path/proposal.toml --expect absent --config /absolute/private/config.toml --json`. To replace an existing document, pass its inspected lowercase SHA-256 digest instead of `absent`. There is no implicit overwrite or force option. Expected absence rejects every existing document, including identical content. A matching digest with identical proposed bytes returns an unchanged no-op; a stale digest or missing expected file returns `conflict` with exit 3. A malformed existing nonempty document can be repaired only with its exact inspected digest and a valid replacement.

The proposal is read as a bounded regular file and fully parsed before any destination directory, lock or publication is created. Accepted bytes are copied verbatim, preserving comments and formatting. The Linux target requires a private owner-owned `0700` parent directory with trusted nonsymlink ancestors, and an existing target must be a nonempty single-link `0600` regular file owned by the caller. An absent parent is published with the complete validated document without replacing a collision. Existing directory or file permissions are not changed to adopt a collision. The reserved `.artifact-update-config.lock` name cannot be used as the configuration filename.

Within an existing private directory, a nonblocking native `.artifact-update-config.lock` serializes participating configuration writers through expected-state recheck and atomic publication. A held lock returns `busy` with exit 3; inspection remains lock-free. The small lock file remains, including after a conflict or unchanged operation. This protocol does not isolate arbitrary concurrent same-owner editors that ignore the lock, nor infer authorization from filenames. No editor, shell, interpreter, provider request, installation operation, ledger initialization or cache refresh runs as part of an edit.

JSON uses `artifact-update-config-operation-v1`, with `operation`, fixed `outcome`, `network_accessed: false`, and `changed`. Apply success outcomes are `initialized`, `replaced`, or `unchanged`; `sha256` identifies the resulting exact document and `artifact_count` describes the validated catalog. For apply, `changed` concerns configuration content, not incidental lock files or directories. Invalid proposed syntax returns exit 2 before mutation, source read/bound failures use exit 1, and unsafe target custody uses exit 4. Once publication is attempted, failure uses `publication-failed`, exit 1 and `changed: null`, because publication may precede a durability error; inspect before deciding a retry. Other platforms return `unsupported-platform` with exit 3 without reading the proposal or mutating files. Native crash and platform qualification remain required before a release-support claim.

`artifact-update config recover --config /absolute/private/config.toml --json` explicitly reconciles only initial publication of that configuration directory and exact filename. It accepts no proposal or expected-content argument, does not read or alter the final configuration document and does not claim catalog validity. It uses the same result schema with `recovered` or `unchanged`, a cleanup-specific `changed` boolean and null `sha256`. An absent journal creates no directories or locks. Custody or recovery failure uses exit 4, with `changed: null` after entering the potentially mutating boundary. Read-only `config inspect` and `doctor` never perform this cleanup.

## Initial signed installation

`artifact-update install example --config /absolute/path/config.toml --json` explicitly resolves and installs a configured Linux binary. The signed target must exactly match `linux-<native architecture>`; there is no target override. Missing trust initialization, an unconfigured layout, an external alias, or check-only authority blocks before retrieval. Receipt drift and pending recovery fail without repair. Existing managed content requires receipt-bound signed evidence for every version that will remain retained. Installation cannot silently downgrade an installed version or replace an equivalent version with different bytes. Exact SemVer build metadata is retained in version names; layout versions exceeding 128 bytes are rejected before artifact retrieval or ledger mutation.

Metadata retrieval and the bounded streaming artifact download happen before ledger and installation locks. Downloads use a private reserved payload beneath the native cache root's `artifact-staging-v1`, a 256-MiB artifact bound, exact signed length and SHA-256, at most two same-configured-host redirects, and a 120-second HTTP budget. A staging-only native lease remains held across download and activation. The file is synced and independently rehashed before ledger acceptance. Neither candidate nor installed binaries are executed, and no privilege or sibling command is invoked.

After durable acceptance, installation holds the unchanged ledger through local publication and activation, acquiring the ledger lock before the installation lock and retained-evidence lock. The complete observed receipt must still match under the installation lock, including when concurrent callers use separate staging roots. Original candidate documents and refreshed retained proofs are atomically saved before receipt activation; retained manifests are reverified with the accepted signed root, so revocation cannot be bypassed by retaining an old root. A failed publication can leave accepted ledger state or an inactive immutable candidate, but it cannot authorize an alias or receipt without its proof.

Each staging reservation is keyed by a domain-separated length-delimited digest of the local artifact ID, data root, binary root, artifact filename, owner and sorted aliases, independent of release version and unrelated configuration bytes. An immutable bounded ownership record must match that target before its stable nonblocking lease is acquired. A busy target blocks with `staging-busy` and exit 3 without another artifact transfer. After acquiring the lease, the next install can remove only that reservation's abandoned private single-link regular payload; it never infers ownership from an old temporary filename, timestamp or PID. Unknown entries, modified reservations and linked payloads fail closed. A successful install explicitly removes and syncs its payload, retaining the small reservation and lock. An earlier failed transfer or activation releases the lease but deliberately leaves its payload for a later explicit install to recover. A post-activation cleanup failure returns `staging-cleanup-failed` with exit 1 and preserves the known durable `changed` result; it does not undo installation or delete unknown files. Older unmarked temporary files, interrupted cache-publication files and unpublished initial-directory temporaries are outside this cleanup protocol and remain unresolved work. Status and journal recovery do not clean staging reservations.

JSON uses `artifact-update-install-v1`, with the selected `id`, fixed `outcome`, `network_accessed`, and `changed`. Success reports the receipt-owned installed version and signed verification. `changed` covers durable ledger, retained proof and installation changes; null on a late failure means durable acceptance or publication may already have occurred. `metadata_cache_changed` and `artifact_cache_changed` separately report disposable signed-discovery and artifact-cache publication, with null when a failed publication may have changed that cache. An identical accepted install can return `unchanged` while refreshing discovery evidence or repopulating evicted artifact bytes. A cache failure after activation cannot undo the installation. Transport and staging-write failures use exit 1, while failed signatures or content identity use exit 4. Other platforms are blocked, not treated as Linux-compatible installations. These implementation contracts do not replace signed-release, crash-recovery or native-platform acceptance.

## Offline signed installation

After successful online activation, verified installed bytes are streamed into private `0600` entries beneath the native cache root's `artifacts-v1` directory, using exact digest/length filenames inside a `0700` directory. Publication syncs private staged bytes, refuses to overwrite an existing entry and syncs the directory. Reuse verifies the complete existing bytes and custody; corrupt entries are reported rather than silently repaired. A concurrent publication collision can return a cache error after installation succeeded; inspect final state instead of assuming nothing changed. This disposable content store contains no release authority and remains independent of the durable acceptance ledger and retained installation proofs.

New artifact-cache copies use explicit per-content reservations beneath `artifacts-v1/.publication-staging-v1`. Each reservation binds its cache root, owner and exact content identity and retains an exclusive native lease across bounded copy, identity verification and no-replace rename. Different content identities have independent leases. A failed copy leaves its reserved payload for the next explicit online save to recover; a successful publication moves the same private single-link file into its final location and syncs both directories. Busy leases and unsafe or unknown reservation entries fail without overwriting concurrent work. Read-only or offline reuse never cleans cache reservations. The small reservation records and locks remain; their eviction, older unmarked cache files, metadata-publication temporaries and unpublished initial-directory temporaries still need separate recovery policy.

New disposable provider and signed-discovery metadata publications likewise use target-bound reservations beneath their own cache root's `.publication-staging-v1`, retaining the existing cache format and stable cache writer lock. The next explicit save can recover a reserved interrupted payload and that reservation's initial-publication journal, while an unchanged save preserves the destination bytes and timestamp. Replacement requires the observed current content identity; busy reservations, unknown entries and custody failures do not authorize cleanup or overwriting. Loads, status and offline cache reads leave reservation state untouched. Durable retained signed release evidence keeps its separate existing publication path. This covers future reserved metadata payloads and journal-owned initial directories, not older unmarked temporaries or reservation eviction.

`artifact-update install example --offline --config /absolute/path/config.toml --json` uses only cached original signed metadata keyed to the current complete configuration and artifact ID. It reauthenticates under current local product/target/root/URL policy and requires an unchanged acceptance transition against the initialized ledger. Cached metadata cannot advance accepted generations, including from an initialized-but-empty ledger. Matching artifact bytes are copied through the bounded custody/identity verifier into private quarantine before the same guarded managed activation. Missing metadata or artifact bytes blocks with exit 3; mismatched authority, signatures, custody or bytes fails with exit 4. Existing receipt drift and pending recovery retain their normal fail-closed behavior.

Offline installation does not retrieve anything, rewrite the ledger, publish disposable cache entries or refresh the metadata timestamp. It can reuse older check timestamps because explicit offline installation authenticates a retained accepted candidate, not its latestness; stale evidence still cannot make status claim a current installation. Local configuration changes require separately matching cached metadata, never reinterpret a cache filename as authority. A signed check refreshes metadata only and does not prefetch artifact bytes. Native signed-release offline acceptance remains required before release.

## Authenticated retained rollback

`artifact-update rollback example --config /absolute/path/config.toml --json` swaps the active and retained previous versions without network access, executable invocation, metadata-cache writes or ledger rewind. Both versions require receipt-bound signed proof verified under the exact currently accepted root; missing or superseded evidence blocks without fetching replacements. The configured aliases must match the receipt. The ledger stays locked while proofs are checked and the conditional installation rollback compares the complete observed receipt, verifies owned bytes and activates under the installation lock. Pending journals and link drift require explicit recovery or repair; rollback never performs either implicitly. Repeating rollback swaps the two retained versions again, rather than being an idempotent no-op.

JSON uses `artifact-update-rollback-v1`, with `network_accessed: false`, fixed outcomes, and `changed`. Success returns `rolled-back` and the signed receipt-owned `installed_version`. Preflight rejection leaves `changed: false`; an activation failure may return null because a journaled transition may have begun. Check-only sources, absent retained versions, unconfigured layouts and unsupported platforms are blocked with exit 3; invalid proof or custody fails with exit 4. The command takes no `--offline` flag because rollback is always network-free.

## Authenticated interrupted-installation recovery

`artifact-update recover example --config /absolute/path/config.toml --json` explicitly resolves a pending installation journal without network access, execution, discovery-cache writes or ledger changes. It requires the configured native Linux binary layout and initialized ledger. Both journal receipts, including their retained versions, must have original signed proof under the exact currently accepted root and match the configured aliases. Bounded artifact content and directory custody are verified before restoration. Missing or superseded proof, tampered content, an unrelated receipt or a legacy-adoption journal fails closed.

A committed receipt with a leftover journal is verified before journal removal. An interrupted transition with its prior receipt still published restores the journal-owned prior links; an interrupted first installation with no receipt removes only the journal-owned links. Inactive version directories and orphaned staging files are not deleted by this command. With no journal, current receipt state is verified without repairing missing links. A second successful recovery is an unchanged no-op.

JSON uses `artifact-update-recover-v1`, `network_accessed: false`, and outcomes `recovered` or `unchanged` on success. A retained receipt includes its signed `installed_version`; successful first-install cleanup reports unknown installation state rather than claiming a managed installation. `changed` is false for early policy rejection, null once the potentially mutating recovery API is entered and fails, and a boolean on success. Invalid proof or custody uses exit 4; check-only sources, unconfigured layouts and unsupported platforms use exit 3. Recovery takes no `--offline` flag because it is always network-free. Local journal tests do not replace native signed-release crash acceptance.

Missing configuration/ledger directories and new installation/cache staging reservations use [journal-owned initial publication](adr/0018-journal-owned-initial-directory-publication.md). A publication retry recovers only the exact unpublished directory named by its durable inode-bound journal under the same nonblocking lock. It preserves unmarked legacy entries and rejects unknown inventory or changed custody. A final directory published before a later failure is never replaced or adopted by a fresh initializer. Explicit configuration/trust recovery can clear the leftover journal without changing that final directory. Installation staging and explicit cache publication also reconcile their own initial journals before acquisition, including after the reservation itself was published. Stable coordination locks remain; general unmarked temporary-file deletion and reservation retirement are not implemented.

Other native cache-storage backends, bounded concurrent checks, and native platform qualification remain rollout work. The current executable is not a release-ready installer or a native-platform support claim.
