# Administrator grants: unreleased 0.5 implementation

This is the candidate administrator-grant implementation, not an installed or released administrator facility. [ADR 0086](adr/0086-native-administrator-grants-and-separate-execution-ownership.md) owns its integration and native acceptance gate. The complete product delivery contract remains in [the delivery plan](../context/docs/dev-auth-delivery-plan.md).

## Public command surface

The candidate provides `dev-auth privilege request`, `status`, `inspect`, `exec`, `delegate`, `revoke`, and `leave`. Requests select `--scope user|workload`, `--authority administrator|exact-plan|typed`, and a finite `--duration`, such as `30m`, `12h`, or `2d`. A new grant always needs fresh native approval. `--non-interactive` returns `approval_required` without opening an approval surface. A missing service returns `requires_setup`; the command does not install one implicitly.

`dev-auth setup template privilege-policy` emits a standalone JSON policy with no authorized subjects and no credential/provider prerequisites. Account-wide authority is a separately configured scope, not a fallback for denied workload authority. No idle cutoff applies unless the request or administrator policy specifies one. The hard deadline includes suspension and cannot be refreshed by activity, observation, delegation, or native sudo timestamps. Credential and ordinary workload limits remain independent.

For an interactive terminal request, native PolicyKit `pkttyagent` is bound to the requesting process and its start time and writes only to the controlling terminal. It supplies authentication UI for isolated workloads without a desktop session agent, does not replace another process/session's agent, and is terminated and reaped when the request ends. Process registration is direct because PolicyKit does not select a fallback agent for a process without a login session. Its readiness is bounded at five seconds; an unavailable agent never becomes approval. Explicit noninteractive requests never start it.

Control output uses `dev-auth-privilege-result-v1`, fixed value-free failures, and common exit categories. `changed` is false before effects, true after established authority/use/routing/execution progress, and null if entered mutation has uncertain progress. `exec` preserves child streams and native status; `--result-file PATH` selects a separate metadata destination and is required with `--format json`. JSON is never mixed into child stdout.

The Linux transport preserves native arguments and supplies a controlling PTY for terminal input. It keeps redirected streams separate, forwards signals, propagates window changes, and restores terminal mode on orderly completion and transport failure. Exact-plan and typed names must exist before approval. Human policy uses Unicode strings directly, with explicit `unix_bytes` or `windows_utf16` arrays only for otherwise unrepresentable native values.

Approved graphs are invoked with `privilege exec --plan-sha256 DIGEST` or `privilege exec --operation NAME`, without an additional command after `--`. The coordinator selects the configured graph under the grant's authority and charges one use for the complete graph. A sealed plan descriptor feeds a private worker inside the owned execution cgroup. The graph supports up to 64 nodes and 63 binary stdin/stdout pipes, with `last`, `all`, and `pipefail` exit policies. Unconnected streams inherit the invocation's streams; concurrent nodes may interleave them. Failed graphs terminate remaining owned descendants before completion is reported. [ADR 0088](adr/0088-approved-command-graphs-in-owned-execution.md) defines ownership and qualification limits.

The candidate's strong-workload launch path accepts `dev-auth workload launch NAME --privilege-scope workload|user --privilege-duration 12h -- ARGS`. Both options are required together and request unrestricted administrator authority; narrower authorities remain available through the separate privilege-request CLI. A new outer workload requests approval only after its native registration, before releasing its configured command. A nested invocation requests approval within its already-registered workload scope. An unsuccessful startup attempts to revoke only the newly issued grant; after launch, normal scope lifetime applies, including persistence of an explicitly approved user-wide grant. Credential admission, workload durations and sandbox policy are unchanged. This combined launch requires the registered strong installation; its installed/native acceptance remains distinct from the direct privilege fixture. `--non-interactive` returns prompt-free `approval_required`, and static completion includes the new options.

## Privilege-only setup candidate

`setup template privilege-deployment` emits an inactive, provider-free deployment. It selects `purpose = "privilege_only"`, strong ownership and the explicitly supplied privilege policy. Equivalent CLI planning uses `setup plan --purpose privilege-only --mode strong --channel stable --activation inactive --administrator-policy POLICY --output PLAN`; normal signed release selection and root-owned planning still apply. The binary plan deliberately has no Git/gh authority and the full plan has no user configuration or credential actions. This path cannot replace an existing credential installation.

`setup template credential-privilege-deployment` shows the combined strong deployment for an existing credential installation. Supply the existing administrator policy and user configuration together with a separate root-owned `privilege_policy` document, then keep each desired credential at `intent = "preserve"`. The equivalent `setup plan` CLI adds `--privilege-policy POLICY` to the credential deployment arguments. This keeps the credential installation purpose and native Git/gh selection, with one retained full-generation plan covering both components. A disposable native-systemd fixture has passed recovery, unchanged retry, credential preservation, and inactive restoration for this combined path; signed upgrade and installed-system acceptance remain required before use on a host.

The component's library, native service/action, private policy and sudo integration belong to the existing retained setup generation. Interrupted work uses `setup recover --mode strong`; `setup restore --mode strong` restores its retained state with integration inactive. `--activation transparent` explicitly selects native sudo/coordinator activation. Unknown integration ownership and an independent sudo group plugin are conflicts, not overwrite permission. [ADR 0089](adr/0089-privilege-component-in-retained-setup.md) describes the source and qualification limits.

Once the receipt-owned setup helper exists, `setup apply --authorize polkit --plan PLAN --sha256 DIGEST` requests independent OS authorization. It never routes setup through an administrator grant; setup inside the grant domain is rejected before mutation. Credential stdin is not forwarded through PolicyKit's authentication surface. A fresh helper bootstrap still runs the selected verified candidate through native root approval; none of these paths require an active grant.

## Native sudo and process ownership

The private `dev-auth-sudo` cdylib is part of this product, not a separate installed product or public SDK. `just build` embeds its exact version-, target-, and source-matched bytes into the Dev Auth executable. Plain development Cargo builds may omit this payload and cannot supply complete sudo installation. Neither development build is signed release evidence.

Audit preflight selects native or managed routing before sudo policy/authentication. A conditional external group selects `!authenticate`/`NOPASSWD` only for that managed invocation. Final approval checks the selected grant and attaches native sudo to an owned execution group before it can start a command; the front-end audit rejects a managed execution that missed admission. No persistent group membership or expiring sudoers file supplies authority.

Sudo's plugin API distinguishes `0` (disable the plugin) from `-1` (initialization failure). Managed denial returns failure, never disable-and-continue. The helper targets API 1.22/group API 1.0. The checked upstream [sudo.c](https://github.com/sudo-project/sudo/blob/v1.9.17p2/src/sudo.c) opens audit before policy, and [check.c](https://github.com/sudo-project/sudo/blob/v1.9.17p2/plugins/sudoers/check.c) does not open/update timestamps on its authentication-exempt branch. These source facts do not replace warm-ticket native acceptance.

Each helper message supplies kernel-checked effective UID/GID credentials matching the connection identity. Linux's automatic `SCM_CREDENTIALS` uses real IDs, which differ in native setuid sudo; relying on that default would fail the coordinator's strict identity comparison. The message never supplies a caller-selected identity or relaxes the retained PID/UID/GID checks.

A supported private workload namespace relays its original invocation through an unprivileged frontend. The already-authorized coordinator executes a retained host sudo ELF descriptor with the original real UID, primary and supplementary groups, cwd and mount context, and explicitly established host effective root UID. It does not rely on a setuid transition across mount/user-namespace ownership and does not remove `PrivateUsers=full` from the ordinary workload. Final native admission retains the same selected grant; its prepaid use binds the directly owned sudo child and is claimable once. Other sudo descendants require another admission.

Relay continuation additionally requires a short-lived preflight record bound to the original native sudo process's live pidfd, unchanged namespace/cwd/workload identity, and the coordinator-matched product executable after privilege drop. A copied grant ID or a manually invoked hidden relay command cannot enter this path. The existing top-level dispatcher confines setuid/setgid invocation to its fixed enrolled-workload entrypoint before ordinary command selection; the new frontends preserve that boundary.

Privileged descendants occupy root-owned cgroup-v2 boundaries separate from ordinary workloads. Persistent eventfd gates deny prepared spawns after revocation, and a BOOTTIME deadline guard runs independently of the request actor. The service verifies its main-process identity, `ExitType=main`, no remaining-active-after-exit behavior, non-delegation, whole-control-group forced teardown, and a stop timeout no greater than five seconds. Pending admissions and owned process groups must settle before terminal cleanup is reported.

Selected routing survives expiry and coordinator restart as denial state only. Explicit `privilege leave` removes it after cleanup and grants no replacement authority. Account-wide grants recognize active/online interactive user sessions, not lingering managers, greeters or background sessions. Delegation depth is bounded at 16 in this candidate. Root/admin-equivalent commands can disable enforcement or cause effects revocation cannot undo; native approval discloses that limitation.

## Verification and remaining gates

`just ci` runs format, strict lint, noninteractive tests and a complete candidate build without hosted CI. `just ci-target TARGET` compiles target source/test surfaces; it does not establish runtime support. `just accept-sudo-abi` compares the plugin records with the installed upstream C header.

The local format, lint, test and target gates include the changed installation and one-shot authorization foundations alongside Dev Auth, its native helper, command execution and privilege sessions. Native and interactive acceptance remain explicit commands, not silently successful skips in the portable tests.

`tests/native_privilege/preflight-once.sh` provides a narrower fixed batch for one native approval: current cgroup enforcement, the setid dispatch guard, differing-real/effective-ID message credentials, an empty-policy coordinator, denied grant requests and noninteractive native sudo passthrough. It stages a Dev Auth binary, the `linux_native` test executable and the `dev-auth-sudo` library test executable in a unique `mktemp -d /tmp/dev-auth-preflight-stage.XXXXXXXX` directory; its `stage PRODUCT NATIVE_TEST SUDO_TEST STAGE` mode writes the manifest, and `root STAGE MANIFEST_SHA256 FRESH_NONCE` runs only through a visible native `pkexec` authorization. Every retry uses a fresh stage and 32-hex nonce. The batch creates no administrator grant or PolicyKit action and changes no installed configuration. Only fixed post-authorization probes are logged to `native-sudo.log` and `native-setid.log`, with 30- and 15-second probe timeouts respectively and five-second forced-stop bounds; authentication input is never captured. Its `result.json` reports the credential probe separately as `native_setid_credentials` and is evidence for this preflight only, not reusable-grant acceptance.

`just accept-native` uses the candidate in `target/debug/dev-auth`; an explicit binary path may be supplied. It is interactive and requires a visible native terminal with the operator available. The fixture stages public inputs, publishes a previously absent PolicyKit action, starts uniquely named transient services, and uses private mount-namespace sudo configuration and a private timestamp store. It covers user/workload scopes, fresh 12-hour approval, ordinary/absolute sudo, public Ansible become, explicit execution, revocation, short hard expiry, warm timestamps, explicit leave, and an ordinary non-root sentinel. Cleanup stops the owned services and removes only its unchanged action. Artifacts/results remain in its unique `/run/dev-auth-privilege-accept-*` directory until reboot. The fixture does not update the installed product, normal sudo configuration/timestamps, credentials, or private consumer state.

`just accept-overnight BINARY` is the separate, explicitly invoked 12-hour native fixture. It requests one user-scope grant through the same visible PolicyKit boundary, observes hard-deadline countdown without an idle timeout, and checks that a privileged child stops at expiry while an ordinary non-root child remains alive. The private coordinator unit has a 13-hour maximum runtime so a broken expiry cannot leave it indefinitely active. The fixture has not yet been run and does not substitute for installed or signed-release acceptance.

The public direct user- and workload-scope fixtures have passed on development candidates, including native approval, binary command graphs, one-use typed delegation, exhausted-budget denial without broader-grant fallback, sudo/relay, Ansible become, cached-ticket preservation, revocation and expiry. The root cgroup fixture also exercises distinct real/effective UID and retained inherited descriptors alongside the held executable. Installed launch-with-grant, receipt-owned setup/recovery, additional shutdown/race cases and overnight qualification still gate activation and release. The cgroup-mechanism and header-ABI tests are narrower evidence, not full product acceptance.

`tests/native_privilege/installed-linux.sh run PRODUCT LIBRARY_TEST IMAGE_ID` stages an explicitly selected development binary, its library-test executable, and a local native systemd test image. The Fedora image must contain systemd, `systemd-pam` (`pam_systemd.so`), D-Bus, PolicyKit, shadow-utils/passwd, login, Bubblewrap, Git/gh/SSH, sudo, jq, and the dictionary data selected by its native password-quality stack. The launch-grant scenario checks container-side jq and the native PAM module before interactive preparation, so a missing prerequisite cannot waste an account-password step. A visible native root approval imports the image into a private `/var/tmp/dev-auth-installed-store-*` image store, with runtime state and public results under `/run/dev-auth-installed-*`. The image store must be disk-backed: automatic systemd credential encryption correctly rejects a temporary host-key filesystem when no TPM2 is available. The resulting rootful container has private PID/cgroup/IPC/UTS namespaces, no network, no host bind mounts, no privileged host mode, a 2-GiB memory limit, 2,048-task limit and an independent 15-minute runtime limit. SYS_ADMIN and SYS_PTRACE are explicit test prerequisites for native namespace setup and cross-UID process evidence; set-ID execution is the test subject, so a no-new-privileges or non-root application-image policy would invalidate this qualification.

The opted-in `native_disposable_prepare_installed_launch_with_grant` test prepares a synthetic retained setup generation and verifies an ordinary credential workload before leaving it installed for interactive testing. Use an optimized development candidate for this installed gate: repeated custody hashing of a large unoptimized product/helper payload can exhaust the existing 90-second recovery-command bound before activation. An optional native strace diagnostic in the preparer records only process/file/locking calls around fixed pre-password recovery, never read/write payloads or interactive execution; the diagnostic runner needs strace in the test image. Privilege service/policy files are fixture-owned, not an implementation of receipt-owned privilege setup. Native passwd then lets the operator choose a temporary password for the disposable account without exposing it to the runner, and native login establishes the interactive session. Both-scope combined launch and a missing-interpreter startup counterexample run on that visible terminal; their output is not captured behind the forwarded workload PTY. Only value-free progress/results and fixed noninteractive preparation output are retained. The outer runner removes the container's writable filesystem, including the temporary account, on completion or error. This gate does not prove signed release intake, privilege installation/recovery, or full product delivery.

While native login is active, the root-owned fixture copies only its fixed value-free phase document to the host atomically, allowing an assisting operator to announce each approval phase without reading terminal I/O. Cleanup also retains the separate value-free workload, user-grant and failed-start result documents when present; it does not capture password or approval input.

The installed-login fixture requests a native `user-light` tty login session and checks logind immediately after login and again after the workload-scope launch, retaining only session classification and boolean results. A missing session stops before user-wide approval. `login-session-probe` runs the same preparation, then exercises native PAM session registration through a root-initiated password-free login only as a diagnostic; it does not qualify password authentication, native grants or installed acceptance. Combined-launch failures print the fixed privilege failure category on the visible terminal; no native prompt or credential input is captured. User-scope admission checks the authenticated account UID, including when a native bridge has different effective credentials, not the bridge process UID.

For the Fedora test image, the runner retains `service.d/10-timeout-abort.conf` under `/fixture/` instead of applying it to the fixture's product units, following the already documented adjustment in [ADR 0057](adr/0057-retained-native-service-shutdown.md). Production service ownership still rejects unretained distribution or operator drop-ins. This isolated test does not establish support for a host that retains those overrides; no host file is moved or changed.

`just accept-installed PRODUCT LIBRARY_TEST IMAGE_ID` selects the runner's separate `privilege-setup` scenario. It uses the existing receipt-owned privilege-only generation through public recovery and restore, removes the original executable/policy sources before the corresponding retained retries, and checks unchanged repeats, native unbound sudo passthrough, exact sudo.conf restoration and removal of owned privilege and shared system definitions. The library-test executable must contain the same embedded helper as the selected optimized product. This scenario requires the visible host approval but has no password, login, enrollment or grant phase. Append `privilege-setup-interrupted` to select the partial-withdrawal case: it reproduces stopped-service definition removal before daemon-reload and then invokes public restore. Append `privilege-combined` to exercise the retained upgrade of a credential installation, including credential preservation, unchanged recovery and inactive restoration, again without a password phase. These disposable scenarios do not establish signed intake, actual grant behavior or complete native acceptance.

Append `tty-probe` only to diagnose the rootful installed fixture's nested terminal path. It requests the visible host approval, then checks a controlling `/dev/tty` and that stdin stays open for five seconds inside the isolated container, without creating an account, asking for a password or starting a grant. A passing probe establishes terminal transport only; it does not replace the interactive installed-launch gate.

Append `password-diagnostic` only after the basic terminal probe passes but native `passwd` still fails. It runs the same noninteractive installed preparation, then invokes native `passwd` on the visible terminal under a 120-second bound while tracing only process, file and wait syscalls—not read/write payloads. It records the native exit category and password-status metadata, removes the container and stops before login or grants. A completed diagnostic is not an installed-launch acceptance result.

Receipt-owned privilege setup, installed launch-with-grant qualification, signed installation/update/rollback, overnight acceptance and the other platform implementations remain incomplete. This candidate is not a complete supported administrator product while those gates remain open.
