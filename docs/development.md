# Development and validation

Rust validation uses formatting, Clippy with warnings denied, workspace tests, and the product integration tests. Python validation remains for support scripts and the retained Python compatibility surfaces, not release administration. Release validation additionally audits source and Git objects, dependencies and licenses, fixtures, metadata, documentation, archives, signatures, links, and platform claims. Native release parity and the retired implementation's test mapping are recorded in [the cutover evidence](native-release-parity.md).

Cross-product work follows the [Dev Tools product standard](product-standard.md) and the applicable [repository architecture decisions](adr/README.md). The complete public gate must succeed from an isolated source tree with private downstream repositories unavailable; public fixtures are synthetic and public product code never discovers a neighboring checkout.

No release or platform support claim is made from compilation or unit tests alone when a native runtime acceptance gate is documented.

The legacy directory-fence gate below now uses the production `retire_atomic_document` API to capture state while the published checker has a prepared rename, then confirms its failure and unchanged retained bytes. Installation crate tests separately qualify process-exit recovery, last-writer capture and hostile custody. See [ADR 0024](adr/0024-linux-atomic-document-retirement.md); authenticated product-history import remains a separate gate.

Linux regular-file public stdout has an explicit upstream-style Node acceptance gate: `cargo test -p dev-tools-command --locked --test public_file_stdout public_file_stdout_preserves_node_early_exit_json -- --ignored`. It requires `/usr/bin/node` and checks complete synthetic JSON despite immediate process exit. Ordinary crate tests separately exercise the kernel file-size bound without a monitor, immutable final capture, native command preservation and owned-process cleanup. This opt-in public-output mode restricts all child regular-file extension; real observers must qualify incidental writes independently before selecting it. See [ADR 0022](adr/0022-linux-public-regular-file-stdout.md).

Update All's legacy writer characterization is an explicit online Linux x86-64 GNU gate: select the authenticated `update-all/v0.1.8` artifact through `DEV_TOOLS_LEGACY_UPDATE_ALL`, then run `cargo test -p update-all --locked --test legacy_writer_acceptance -- --ignored --test-threads=1`. The test requires `/usr/bin/strace` with syscall-entry delay and `--kill-on-exit`, and public GitHub HTTPS access. It verifies the exact published artifact digest before copying and running it in disposable homes. While holding the installation lock, it observes an already-started checker overwrite a successor-shaped state document, and separately fail to rename over a directory at the state path. The staged state file is an interleaving handshake, never deletion authority. A missed injection window fails the test. These are incumbent behavior and filesystem constraints; they do not establish crash-safe state retirement, accepted-history import, installation-protocol cutover or retained rollback. No live installation or caller policy is changed.

The same fixture also provides a local-only installation-protocol gate: `cargo test -p update-all --locked --test legacy_writer_acceptance legacy_installer_is_excluded_by_pending_and_committed_protocol_upgrade -- --ignored --exact`. With `DEV_TOOLS_LEGACY_UPDATE_ALL` selected as above, it first proves the frozen engine can roll back the fixture, then checks that pending and committed v2 protocol fences reject that mutation while preserving the receipt, state and active target. Its synthetic current candidate is only a health fixture. This gate needs neither network access nor strace and does not replace full signed product cutover acceptance. See [ADR 0023](adr/0023-explicit-installation-protocol-cutover.md).

Retained ordinary operation has a separate local-only traced gate: `cargo test -p update-all --locked --test legacy_writer_acceptance retained_legacy_ordinary_run_survives_pending_and_committed_cutover -- --ignored --exact`. It uses the same digest-pinned `DEV_TOOLS_LEGACY_UPDATE_ALL` artifact, installed at its public command path in a disposable home, with the frozen default automatic-update setting enabled. After production state retirement, both pending and committed installation upgrades must let its selected local task execute despite the automatic-update warning. The test rejects IP networking and changes to the receipt, journal, active target or captured state. This qualifies the frozen binary's ordinary task path under the fences, not new-adapter recovery, signed successor activation, or every retained command.

Linux atomic-document durability has an additional native syscall gate: `cargo test -p dev-tools-installation --locked --test atomic_durability atomic_document_publication_ -- --ignored`. It requires `/usr/bin/strace` with `--kill-on-exit`, syscall fault injection and permitted child tracing. It observes production publication, final permissions, ancestor syncs, byte-identical retry and read-only observation, and injects a failed post-publication sync. These tests are explicitly ignored in the ordinary portable suite because tracing is not available on every test host; execute this gate for Linux publication changes. The trace is a bounded temporary fixture, not a hardware power-loss simulation.

Linux cutover observation has the companion gate `cargo test -p dev-tools-installation --locked --test atomic_durability cutover_observation_has_no_write_sync_or_lock_syscalls -- --ignored --exact`. It traces the production retained-history, v2 receipt-metadata and pending-recovery readers and rejects write-capable opens, mutation, storage synchronization and locking. Run it when those read-only boundaries change; it does not establish installation or release authentication.

The bounded v0.2 `gh-dev-auth` compatibility frontend remains release-frozen while the v0.3 workload broker is under acceptance. Its child grammar is reviewed against one exact upstream GitHub CLI source revision and build output. The v0.3 same-name workload frontend does not parse GitHub CLI grammar: an admitted session passes argv to the administrator-pinned native executable and supplies only the broker-derived child environment.

The managed v0.2 `git-dev-auth` grammar remains a rollback security boundary and accepts no new syntax. Dev-auth v0.3 instead forwards all Git argv within an admitted workload and narrows authority through the operating-system session, resolved resource entitlement, provider permissions, command-scoped credential/signing configuration, and terminal denial without human fallback. Platform claims require native routing and child tests; a Windows cross-compile or Wine run is useful implementation evidence but cannot replace current-user ACL, path identity, process isolation, Credential Manager, and named-pipe acceptance on native Windows.

The local validation surface is:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo deny check
python -m pytest tests
```

Full workspace test builds can retain substantial debug and incremental output. Check available build-filesystem capacity before a broad gate; on constrained development hosts, `CARGO_PROFILE_TEST_DEBUG=0 CARGO_INCREMENTAL=0 cargo test --workspace --locked -j 2` keeps the test assertions while omitting debug symbols and incremental output. This is an implementation test mode, not a release-performance measurement. Keep any custom Unix `TMPDIR` short and owner-controlled: socket fixtures append session directories and socket names, and an overlong full pathname fails at socket creation before the intended test assertion.

Those resource limits do not require replacing `PATH`. Ordinary developer builds retain the user's configured command lookup, including an optional Dev Cache Cargo intercept; forcing `/usr/bin:/bin` selects the system Cargo directly and bypasses that intercept. Dev Cache preserves final artifacts in Cargo's normal target location while routing supported disposable intermediates to its configured root. The isolated release constructor is different: its exact executable and explicit output directory are part of the source-bound reproducibility contract, not an ordinary development-build recommendation.

Release Admin's synthetic Git fixtures use a cleared environment, explicit system Git, no global/system configuration and disabled fixture hooks/signing. These disposable commits are test data, not authenticated release source. This isolation does not change the real repository's signing policy or authorize unsigned publication.

Dev Auth's release-filename CLI fixture creates and exercises its copied executable in an exact single-test subprocess. On Linux, a concurrent pre-exec child of a multithreaded test harness can inherit a writable copy descriptor even when it is close-on-exec; until that child executes, launching the copied file can fail with `ETXTBSY` after the writer thread has closed its own descriptor. Process isolation keeps the original build-info and setup-plan assertions without production retries or suite-wide serialization. A targeted diagnostic can run this fixture beside `internal_provider_child_reads_only_a_sealed_fd_and_executes_the_held_provider`, with `strace` delaying only `execve` calls for the built Dev Auth executable; the fixture must still complete while that unrelated pre-exec child is held.

Sync Configs' shared-authentication hook fixture uses the same exact single-test subprocess isolation. Its synthetic sudo executable previously failed at the noninteractive cached check with `ExecutableFileBusy` / OS code `26`, before any authentication decision. The isolated child creates its own executable after the concurrent parent harness has finished spawning it and preserves the original one-authentication, exact-argv and pre/post-hook assertions. Its execution has a 30-second bound and a 64 KiB output bound. Production authentication retains its existing no-retry behavior; fixed stage, process-category and exit/signal diagnostics remain available for distinct failures. Repeated parallel runs qualify the fixture change, not native sudo policy or privileged deployment.

Run the authenticated release-set recipe only from the exact clean revision intended for publication. The recipe embeds the full source commit and a clean-tree marker in every Rust artifact, remaps checkout and user paths out of compiler metadata, and produces no private-key material; release acceptance compares the metadata and installed digest with the signed artifact before support is claimed.
