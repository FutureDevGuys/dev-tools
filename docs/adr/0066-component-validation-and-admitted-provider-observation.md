# ADR 0066: Component validation and admitted provider observation

status: proposed
verification: pending

## Decision

`validate --component all|configuration|tools|providers [--online] [--non-interactive] [--json]` separates configuration, executable readiness, enrollment, provider retrieval and key-material checks. The command's Clap definition also supplies help and completion metadata. JSON returns one `dev-auth-validation-v1` document with fixed categories, counts and common exit categories, without values, provider references or captured subprocess diagnostics. Doctor remains local and network-free. Offline validation does not read enrollment or invoke a provider. A provider-only check never invokes Git or GitHub CLI; aggregate checks continue after independent failures.

The retained v1 path reads native-account configuration and declared references. Explicit noninteractive enrollment uses the prompt-free Linux reader in ADR 0065 and is blocked on platforms without a qualified prompt-free adapter. One absolute provider-operation budget covers authenticated health and all resource reads; successfully retrieved material is dropped after inspection. RSA and declared SSH-key checks are reported separately from retrieval. Git and gh diagnostic subprocesses use bounded execution. The exact gh banner restriction remains only in the retained legacy path; it is not added to the successor's native passthrough authority.

The 1Password adapter's health operation invokes only `op user get --me --format json`, the current-account query recommended in the vendor's [Service Account setup documentation](https://www.1password.dev/service-accounts/use-with-1password-cli). A successful bounded response must identify an active service account before health is reported as healthy; executable custody alone is not authentication. The Linux sealed-credential child adds one parameterless `--current-account` operation alongside its existing validated reference read, with no arbitrary provider arguments, user selection or shell interpretation. Other native adapters share the fixed argument definition and bounded process runner. Raw provider output remains zeroizing and never enters diagnostics. Local `metadata` still describes adapter capability for a syntactically valid reference; neither that declaration nor health establishes resource existence. Explicit retrieval supplies that separate evidence.

Installed online provider checks use the authenticated workload broker and cannot fall back to legacy configuration or another credential source. The internal protocol adds a parameterless `validate_providers` operation under the unreleased identity 3. The broker re-resolves the admitted native owner's narrowed logical resource selection against current administrator authority and checks only those references through their selected provider and enrollment slot. Authenticated health is checked once per selected credential slot; a failed health observation does not suppress independent resource retrieval unless cancellation, deadline or failed cleanup requires termination. All checks share one operation budget. Operation-only bytes stay inside the broker and are discarded; the response contains only successful and total authentication-slot and resource counts. A successful read proves retrieval, not key validity, operation success or general provider metadata discovery. Unperformed observations remain `not_checked`. Session cancellation, hard-deadline checks and post-operation publication guards remain mandatory. Calling validation does not grant, renew or extend a workload session.

The broker separately checks selected operation-key declarations against retrieved material: RSA private-key structure and internal consistency for GitHub, private/public identity and fingerprint for SSH and Git signing, and raw Ed25519 private/public identity for release signing. SSH and release validation reuse the identity-bound parsers used by signing, without producing signatures. The response adds successful, failed and total operation-key check counts. An unread key remains unperformed rather than invalid; an observed mismatch is an integrity failure. Counts describe declarations, so two separately declared operations can check the same material. No check proves a GitHub App identity, API permission, successful workload operation or acceptable cryptographic strength merely from key parsing.

RSA validation uses a direct dependency on the existing locked RustCrypto `rsa` 0.9.10 implementation already used by the JWT and SSH dependencies (MIT OR Apache-2.0, RustCrypto/RSA provenance). The direct edge requests only `pem` and `std`, already enabled in the product dependency graph, and introduces no second cryptographic implementation. The JWT PEM-envelope loader alone accepts structurally incomplete private keys; the RSA parser supplies the missing key-structure and consistency checks. Both legacy and installed validation use that check.

This additive operation does not establish a stable external broker API. Retained protocol identity 2 remains rejected, and stopped-broker migration, exact 0.3.11 release verification compatibility and admission rules remain unchanged.

## Evidence and remaining acceptance

CLI fixtures cover prompt-free missing enrollment, provider independence from native developer tools, aggregate continuation, invalid-invocation JSON and static completion. The existing PowerShell renderer provides option names but not possible-value candidates; complete five-shell grammar acceptance remains pending. Protocol and broker tests cover caller-field rejection, bounded count representation including key-count overflow, logical-admission denial, partial-result handling and hard-deadline denial. Production-loop tests exercise exact provider/slot selection, once-per-slot health, independent denial continuation, cancellation and failed-cleanup stopping, and unread, invalid and valid operation keys. Provider fixtures distinguish authenticated current-account health from executable presence and resource retrieval. Key fixtures cover malformed RSA envelopes and SSH identity mismatches without signing. Native installed admission, cross-slot live provider execution, installed operation-key validation and whole-workload cleanup remain separate gates.

Explicit source-binary Linux checks using existing enrollment authenticated the active service account, retrieved all three declared legacy references and validated all three expected keys without invoking Git or gh or printing credential values. This is vendor-store and provider evidence for the standalone source path, not evidence for a signed release, installed successor, admitted logical workload or another platform.

An isolated Linux installed-runtime fixture uses public installation primitives, receipt-owned workload aliases and native user-only admission to launch an independent shell program through the installed CLI. An activation-disabled disposable session bus serves two synthetic enrollment slots through the encrypted Secret Service protocol. Separate provider executables require their exact synthetic tokens. The workload obtains authentication 2/2, retrieval 2/2 and release-key identity 1/1 observations through the broker, reads one explicitly exportable resource and leaves no session socket or directory; stale hints cannot trigger further provider work. Developer-tool fixtures fail if invoked. This establishes the user-only source-built runtime composition, not signed release, journaled setup-v3, strong-mode full-identity custody or live cross-slot provider acceptance.
