# ADR 0116: Retained grant setup and explicit empty native files

status: proposed
verification: pending

## Decision

The administrator grant authority in [ADR 0115](0115-native-administrator-grants-with-maintenance-compatibility.md) is an explicitly selected component of the existing strong setup transaction. It does not replace the bounded maintenance authority in ADRs 0094–0096, introduce another installation root, or borrow a reusable grant to modify its own enforcement. Existing maintenance helper publication, sidecar ownership, policy drift checks, admission exclusion, whole-domain quiescence, recovery and inactive restoration remain mandatory.

`SetupPurpose::Credentials` is the default and is omitted from canonical credential installation requests, receipts and deployment intents. Credential-only deployment/intent v1, binary setup-plan-v2 and full setup-plan-v3 preserve their existing canonical bytes and v2/v3 administrator-policy destinations. An explicit `privilege_only` purpose uses deployment/intent v2, binary setup-binary-plan-v3 and full setup-plan-v4. It requires Linux system ownership, an authenticated compatible runtime, empty native Git/gh selections and no credential or user-configuration actions. It never discovers those tools or reads a provider. A credential deployment instead adds a separately selected `grant_policy` under strong ownership and uses full setup-plan-v4 while preserving its credential installation purpose, native programs, accounts, policy version and credential action authority. The templates default to inactive integration and a grant policy with no subjects.

The new policy is `dev-auth-administrator-grant-policy-v1` at `/etc/dev-auth/administrator-grants-v1.json`. It is distinct from the existing capability-shaped `dev-auth-privilege-policy-v1` and `/etc/dev-auth/privilege-policy-v1.json`; no relabeling, migration by field omission or implicit privilege widening is permitted. CLI `--grant-policy` supplies this separate policy for Credentials. For PrivilegeOnly it normalizes to the single internal `administrator_policy` source. Duplicate selections must agree. Changing an installation purpose in place is rejected; adding grants to an existing credential installation is a preserving combined transition.

The existing `dev-auth-install-v2`, retained-setup-generation-v1 and setup-transition-v1 envelopes remain the owners. Their readers distinguish the approved inner plan versions rather than accepting an unknown schema or rewriting an old digest. Setup retains the selected policy source, current native service observation, exact embedded library/declarative payload identities, exact prior sudo block and before-state of the fixed library, private policy, PolicyKit action, service, sudoers fragment and `/etc/sudo.conf`. The maintenance objects and shared strong system definitions remain in the same generation even for privilege-only setup. A credential-only replan cannot silently omit an accepted grant component. Existing enrollment effects are never reversed by configuration restoration.

The coordinator is `dev-auth-grants.service`, with a separate `/run/dev-auth-grants` runtime. New grant publication/startup and command admission use a short shared setup lease and require an actual Accepted marker plus intact retained-generation bytes. Missing, Pending, Restoring or RestoredInactive state denies admission. This does not change pre-marker workload compatibility. Running grants do not keep the setup writer out for their entire duration; the exclusive owner stops the coordinator, then proves the dedicated cgroup empty through the existing descriptor-bound native cgroup observer. Existing maintenance cgroup absence remains a separate requirement. Recovery stops the grant coordinator before completing binary activation. Setup and recovery reject execution inside either the grant or maintenance domain.

Publication observes every retained before/candidate pair, stops the coordinator and requires native-domain emptiness before changing its enforcement. The sudo renderer preserves unrelated bytes and the native file mode. Marker text alone grants no ownership; replacement or removal requires the exact retained block. Native compatibility inspection refuses an unrelated group plugin. Transparent integration is an explicit selected action, activated after configuration and credential integration; full product postcondition verification precedes acceptance. Inactive selection publishes no passwordless sudo rule and verifies a stopped, disabled, empty coordinator.

Restoration publishes its one-way direction, withdraws the grant component first, then restores retained core, maintenance, credential and user state with integrations inactive. Privilege-only restoration still restores shared strong service/sysusers/tmpfiles definitions and maintenance documents before withdrawing helpers. Retry verifies the same inactive terminal state and exact retained bytes; it cannot restore credential values or turn an old approval into a new grant.

Strong setup can request an independent exact native helper invocation through a bounded `PkexecAuthorizer` in the focused one-shot privilege foundation. The product checks its helper receipt and root-owned authorization executable before spawning. Credential stdin is rejected before authorization; explicit protected files remain available. Native streams are inherited, caller argv is literal, and ambiguous helper status remains a native status. Prompt-free or complete-helper deadline claims that this backend cannot enforce fail before process creation. The existing sudo one-shot route and all finite maintenance contracts remain available.

## Explicit empty-file primitive

An existing native `/etc/sudo.conf` may be a legitimate zero-byte regular file. The installation foundation adds explicitly named file APIs that permit empty contents while preserving opened-object identity, no-follow/type/owner/mode/single-link/size checks, descriptor-bound directory publication, digest/CAS authority and removal durability. Existing document APIs continue to reject empty content. Dev Auth uses the file APIs for retained native sudo configuration and component file reconciliation; an empty file is never parsed as a valid policy, receipt, plan or journal. A recognized marker cannot substitute for retained exact bytes.

## Source evidence and remaining gates

This isolated integration contains source regressions for unchanged credential canonical encoding, provider-free privilege normalization, conflicting sources and ownership denial, combined preservation, short Accepted-only leases and missing retention, native service identity/teardown, owned sudo merging, independent PolicyKit input/argv/status behavior, and privilege-only/combined retained recovery and inactive restoration in explicitly disposable native fixtures. All existing maintenance restoration and drift regressions remain present.

Only static consistency inspection and Rust formatting were performed for this integration slice. The Rust tests, compiler, lint, native fixtures, real approval, installed sudo/Ansible behavior, signed fresh/combined upgrade, interruption/repair/rollback/owned uninstall, overnight lifetime and non-Linux acceptance are not run. Source presence does not establish an independently installable release or runtime support. The next qualification must exercise both old bounded maintenance and new grants under the same installed setup, including coordinator crash and pending-sudo quiescence across cutover. Binding activation, copied pins and setup-owned update workers remain separate subsequent slices.
