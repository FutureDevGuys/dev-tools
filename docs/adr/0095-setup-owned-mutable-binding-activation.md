# ADR 0095: Setup-owned mutable binding activation

status: proposed
verification: pending

## Decision

Dev Auth's Linux candidate admits an explicitly mutable normal-command binding only through a full setup generation. A v3 deployment names each native account, v3 binding-plan file and exact lowercase digest. The full setup plan uses v5 when this authority is selected, reads each canonical binding plan as a retained source document, proves its current binding receipt precondition, and requires its target to be the configured workload launcher. Alias collisions with a workload name, self-routing into the product, and known proxy layers fail before mutation. A v3 deployment with an empty binding list explicitly removes prior bindings; a v1/v2 deployment cannot silently abandon an existing binding generation.

The existing setup lock, source capture, retained previous generation and restoration direction remain the only transition authority. Setup deactivates old workload integrations, installs and verifies the candidate binary and policy, publishes an owner/mode-checked binding-set receipt bound to the installed executable, then activates only receipt-owned aliases. Strong receipts are root-owned readable documents under the product data root; user-only receipts are private to the native account. An alias routes through the installed Dev Auth executable, the alias receipt, the binding receipt and the configured workload name. It never treats an alias path, copied environment hint or arbitrary PID as admission authority. Structured fixed arguments are inserted into native caller arguments without shell parsing; workload policy still owns cwd, environment, credential admission, process lifetime and containment.

Mutable mode deliberately approves the configured executable location including later edits. Runtime checks the installed executable and binding receipt, the exact owned alias, the selected workload's current launcher path and native launcher custody; it does not silently rehash a mutable target or extend its admission. Refresh/rebind planning reads the current receipt, requires a new digest-bound plan, and conserves one prior generation. [ADR 0102](0102-strong-root-pinned-binding-generations.md) now owns a separate source candidate for strong root-owned pinned bytes; user-only and user-writable pins remain closed, and the strong path is not accepted until its native gates pass. Discovery and planning alone never activate a binding.

Setup-plan admission checks the native launcher custody that execution will enforce. User-only accepts its documented same-user or root path. [ADR 0097](0097-strong-mutable-binding-launcher-authority.md) extends strong execution to a user-owned target only while the same native owner/workload/launcher is selected by an active root-custodied mutable binding generation; unbound strong workloads retain root-owned launcher custody. This does not downgrade pinned trust or make root ownership alone a byte pin.

An optional `workload bind plan --desktop-entry` selection is part of the digest-bound binding intent. It is admitted only when the selected workload already has desktop metadata. Transparent setup then publishes a separate receipt-owned desktop entry for the bound alias, pointing to that alias and retaining the workload's desktop terminal/icon choices; the entry name includes the bound command to distinguish it in menus. Postcondition, local doctor, repeat application, refresh, removal and retained restoration use the same selected binding intent and exact desktop-entry receipt. No unowned desktop file is replaced or removed, and inactive setup creates no desktop launcher.

The private session tool plane exposes only receipted binding aliases for that session's exact workload, after rechecking the installed alias and approved target. Both user-only and strong workload supervisors run as the authenticated non-root account; the strong receipt remains root-owned but readable under its approved custody. This makes same-workload editor children and nested shells find bound commands through the managed PATH without promoting all user-writable commands. A nested launch must match the broker-verified native owner/execution UID, workload name and authority profile, including the final probe before a structured result; an alias for another workload cannot borrow the current session's credential authority. Reserved Git/gh aliases keep their existing private routing and cannot be selected as bindings.

Setup-aware version update reuses accepted policy and binding source documents but refreshes a mutable binding plan against the current executable at the same approved location and active receipt. It records a new exact digest in the successor setup intent; it cannot redirect to another visible/canonical target or silently turn pinned into mutable trust. This permits an explicitly mutable script edit without requiring an obsolete original-byte digest during an otherwise preserving product update. The successor plan still revalidates bytes before activation and remains under the full setup transaction.

Source-free recovery of an accepted mutable generation validates the captured plan's exact structure and digest without reopening later-edited target bytes as a fresh approval. A pending generation still requires the originally approved target bytes until activation has been verified and accepted. Both retained phases use the retained before-state binding precondition rather than comparing the old plan's prior receipt with a partially or fully installed active receipt. Native owner/location and current receipt custody remain required; a new setup plan or explicit refresh still inspects current bytes before mutation. This keeps approved mutable edits usable after acceptance without admitting changed code during an unfinished setup or accepting a relabeled retained plan.

The pending target is rechecked against its captured plan immediately before accepting a verified generation, including a recovery that finds the postcondition already satisfied. Accepted repeat recovery does not perform this byte check. A target edited during the unfinished transition therefore cannot be silently accepted merely because its binding receipt and aliases were published earlier; it requires restoration or a fresh approved plan.

Restoration observes the candidate/retained binding pair before mutation, retires aliases first, then restores or removes only the exact binding receipt under the full-generation journal. A removed binding reveals the untouched original command; restoration leaves prior integrations inactive. The candidate does not copy or move the original executable. No separate binding mutator or provider dependency is introduced.

## Verification and remaining gates

Source tests cover schema cutover, explicit mutable choice, current-receipt refresh planning, collision and target validation, bound native arguments and exit status, later mutable edits, optional desktop publication, same-workload nested-shell routing, a synthetic editor child using the ordinary PATH alias, initial restoration, refresh rollback and explicit removal in a disposable installed user-only setup. Strong native setup/runtime, actual editor/desktop applications, service entry points, signal/terminal fidelity, concurrent interruption, pinned byte custody and non-Linux implementations remain unqualified. This source capability is not a signed product release.
