# ADR 0002: Common product CLI and explicit network boundaries

status: proposed
verification: pending

## Context

Standalone products need one predictable lifecycle without acquiring a runtime dependency on a central updater. The same update machinery also serves independently packaged programs whose implementation language and distribution format are irrelevant: native executables, AppImages, archives, plugins, extensions, JVM artifacts, Go binaries, Node packages, and other versioned assets. Local inspection remains fast and network-free, while explicit discovery handles heterogeneous release providers without granting remote metadata authority over commands, destinations, or privilege.

## Decision

Every public product implements the common interface and result categories in the product standard. Update status is authenticated-cache-only, update check is the explicit network boundary, install and apply are explicit managed mutations, and rollback uses only authenticated retained state. Products compile the shared `dev-tools-update` implementation and retain product-owned installation, health, setup, and enrollment adapters.

`artifact-update` exposes the same foundations as a standalone configuration-driven product for unrelated artifacts. Its local authority document names the provider, tag or version convention, platform and architecture selectors, ordered exact/glob/linear-time-regex asset rules, verification tier, and managed destination. Source adapters translate bounded remote metadata into inert candidates. Remote responses cannot contribute executable commands, shell text, destinations, selectors, or privilege.

The optional `installation` declaration initially supports `versioned-binary` for native binaries, Go binaries and AppImages. Local configuration names separate absolute native data and binary roots, a single artifact filename, and a bounded alias list. Parsing validates only desired layout syntax; it neither inspects nor adopts filesystem state. Omission leaves no installation destination configured. This declaration cannot upgrade a check-only verification tier or authorize overwriting existing paths. Receipt ownership, authenticated artifact bytes and the applicable native custody adapter remain independent mutation gates.

Artifact Update's initial Linux configuration editor accepts explicit whole-document proposals rather than invoking an editor or interpreting patch commands. `config inspect` is read-only and returns the current private document digest independently of catalog validity. `config apply --from PATH --expect absent|SHA256` captures and validates bounded proposed bytes before mutation, then requires explicit absence or the current exact content digest. An existing private directory uses a nonblocking native configuration lock across recheck and atomic file publication; a missing directory uses no-clobber complete-directory publication. Expected absence never adopts an existing file, even with identical content. Comments and formatting are retained verbatim. The lock coordinates participating writers, not arbitrary same-owner editors, and no configuration mutation initializes a release ledger, installs artifacts or grants privilege. Existing targets require nonempty single-link owner-only regular-file custody and trusted private parents; unsupported native backends fail closed. Publication failure may leave changed state and reports uncertainty rather than claiming rollback.

The source layer admits GitHub, GitLab, Forgejo/Gitea, generic JSON, XML/Atom/RSS/Sparkle, Maven, npm, crates.io, static signed manifests, direct or final-redirect URLs, bounded HTML inventories, and AppImage/zsync through separate parsers behind one candidate contract. A source becomes install-capable only when signed first-party metadata, a pinned checksum/signature scheme, or another locally declared verifier authenticates the selected bytes. Unverifiable sources remain check-only.

The initial GitLab adapter takes an explicit HTTPS API-v4 base and unencoded bounded project identifier from local configuration. It performs anonymous bounded offset-page retrieval with only that configured host admitted, excludes upcoming releases, and translates named asset links into inert candidates. It neither selects source archives nor interprets provider evidence as signatures or installation authority. GitHub and GitLab share local release ranking and ambiguity rules. Their metadata caches retain distinct schema and exact resource identities while sharing bounded codec validation and conditional-response handling; a failed complete check never advances either cache. Existing GitHub public methods and persisted bytes are unchanged. Linux Artifact Update chooses the provider cache through current local configuration; native HTTP/platform acceptance and additional provider authentication remain separate work.

The initial Forgejo adapter likewise requires an explicit HTTPS API-v1 base and bounded literal owner/repository components. Only locally generated release-page URLs enter retrieval, and only named attachments become candidates; drafts and prereleases are excluded. Since instance policy can clamp the requested page size, a short nonempty page is not completion evidence. The adapter requires an empty terminal page within its ten-request, two-MiB-per-response and sixty-second budget, otherwise returning an error rather than a partial selection. The distinct Forgejo cache schema includes that terminal page and reselects exact resource bytes under current configuration; a failed refresh leaves the prior cache unchanged. This adds no HTTP stack, authentication lookup, installation authority or Gitea compatibility claim. Existing source encodings and cache bytes are unchanged; the new Rust source-enum variant belongs to the unreleased shared-crate interface and requires the normal source-bound registry generation before downstream adoption.

The explicit Gitea adapter follows the documented release-list attachment schema using the same private bounded page parser as Forgejo, while preserving separate source validation, public check/cache entrypoints and persisted schema identity. Both wrappers require their own source variant, and existing Forgejo interfaces, limits and cache bytes remain unchanged. Gitea's locally generated resource sequence must include the terminal empty page before refresh or cached observation can succeed. This adds no dependency, credential lookup, artifact download, execution or installation authority. Compatibility covers the documented Gitea release API shape rather than all server operations or versions; the additive unreleased source interface requires source-bound registry publication before downstream use.

The initial generic-JSON adapter retrieves one explicit local HTTPS URL and uses bounded local JSON Pointers to map the release inventory, tags, assets, names, URLs and optional boolean exclusion flags. Mappings are data, not an embedded expression language. Duplicate object members are rejected throughout the response so pointer resolution cannot silently select a last duplicate. The existing JSON recursion guard and two-MiB transport bound remain, with at most 1,000 releases and 4,096 assets per included release. One sixty-second request budget and two same-host redirects bound retrieval. Remote pagination is not followed: completeness concerns only the configured response, and global release comparison requires a complete unpaginated feed. The distinct generic-JSON cache schema admits exactly that resource and reselects original bytes under current local mappings after conditional reuse or local observation; failed refreshes preserve prior bytes without fallback success. No new parser dependency, HTTP stack, ambient credential lookup or installation authority is introduced. The additive source-enum variant requires the normal source-bound registry generation before downstream adoption; existing source encodings and cache formats remain unchanged.

The initial npm adapter requires explicit local HTTPS registry, literal package identity and distribution tag. It retrieves one bounded package/tag document rather than a full version inventory, validates exact package identity and strict SemVer, excludes prereleases, and translates only the HTTPS tarball URL into one inert candidate named by its final raw path segment. Selection describes that tag, not global latestness or npm dependency/engine resolution. Scripts and provider integrity/signature fields are ignored, and no ambient npm configuration or credentials are read. The distinct npm cache schema retains exactly one resource and applies current local rules after conditional reuse or local observation; failed refreshes preserve prior bytes. The existing two-MiB/sixty-second/two-same-host-redirect transport bounds, duplicate-member rejection and 32-MiB cache codec apply. No package download, execution, installation authority, dependency or HTTP stack is added. The new source-enum variant belongs to the unreleased shared interface and requires a source-bound registry generation before downstream use.

The initial crates.io adapter takes a bounded literal package identity and uses only the public sparse index and derived static archive URLs, without ambient Cargo configuration, authentication or execution. One two-MiB/1,000-record UTF-8 newline-delimited JSON response is parsed completely, requiring exact name, strict SemVer, boolean yanked status and supported index schema. Duplicate JSON members and duplicate versions ignoring build metadata fail closed, including excluded records; yanked and prerelease versions never become candidates. Dependency and checksum fields provide no installation or verification authority. Its distinct single-resource cache reselects original bytes under current local rules with the existing 32-MiB codec, sixty-second budget, two same-host redirects and failure-preserving conditional refresh. No dependency, HTTP stack, archive download or compiler is added. The additive unreleased source-enum variant requires source-bound registry publication before downstream adoption.

The initial Maven adapter takes explicit HTTPS repository and literal group/artifact/extension/classifier coordinates. It parses the complete bounded artifact-level version inventory, requires matching identity, excludes snapshots and applies existing local ranking without interpreting Maven's `release` field as maximum version or claiming Maven version-comparator compatibility. Derived layout URLs do not prove classifier/extension availability. Its distinct one-resource conditional cache preserves failed refreshes and reselects current local coordinates. No POM, plugin, dependency, ambient settings, credential or artifact retrieval is added; observations are check-only. The additive unreleased source-enum variant requires source-bound registry publication before downstream adoption.

Maven introduces `quick-xml` 0.42 with default features disabled because the existing foundations have no XML parser. The streaming namespace-aware reader allows depth/event/attribute limits before unbounded tree construction; local validation rejects DTDs, custom entities, processing instructions, contradictory required fields and malformed admitted XML. UTF-8-only parsing needs no encoding or async runtime feature and performs no entity retrieval. The dependency is MIT licensed, publishes from `tafia/quick-xml` (0.42.0 source commit `36a2c52a4f6c90878c3f60c3c3b5c62efaef28a9`) with a locked registry checksum and no build script, and adds only its parser package while reusing `memchr`. Its Rust 1.86 minimum does not establish a new workspace MSRV claim. Dependency/license/advisory checks and target builds remain mandatory, and binary-size/startup impact remains part of source-bound release qualification. No public API exposes XML-library types and no second network, TLS, archive or cryptographic stack is introduced.

The initial Sparkle adapter takes one explicit HTTPS appcast URL and a required local choice of bundle or short version. It consumes direct RSS 2.0 items and full enclosures through the private XML reader shared with Maven, validates modern/legacy version agreement and excludes named channels. Remote URLs become inert raw-basename candidates; signatures, delta archives, release notes, OS/hardware requirements and rollout policies are not an installation engine or authority. Its distinct one-resource conditional cache reselects local rules and preserves failed refreshes. Existing Maven cache bytes and APIs remain unchanged. This adds no dependency, HTTP stack, artifact retrieval or authentication lookup; the additive unreleased source variant requires source-bound registry publication before downstream use.

The initial generic-XML adapter maps RSS, Atom and custom inventories through bounded local expanded-name direct-child paths and optional literal attribute equality, not XPath or remote expressions. Required scalar paths resolve uniquely to leaf text or an attribute; the full document is validated before ranking. The shared XML reader bounds syntax and events, and the private tree additionally caps retained expanded names, attributes and text at eight MiB to prevent inherited-namespace amplification. One configured HTTPS resource, 1,000 releases, 4,096 pre-filter asset elements per release and the existing transport/codec bounds apply. Its distinct conditional cache reselects current local mappings and preserves failed refreshes. No syndication-engine conformance, remote pagination, URL-base resolution, authentication, artifact retrieval, execution or installation authority is added. The additive unreleased source interface requires source-bound registry publication before downstream use; existing provider APIs and persisted bytes are unchanged.

The initial zsync adapter consumes only bounded control metadata. Ordered application versions come from existing local named filename captures, never the generator header; explicitly unordered rules may use the filename. Binary checksum-section length is checked without calculating or trusting those hashes. Relative full-file URLs resolve against the retained final admitted metadata location, and matching mirrors remain ambiguous. The distinct single-resource cache shares bounded page decoding while preserving original/final identities, initial-resource validator scoping and failure-preserving replacement. No delta engine, installed-AppImage inspection, subprocess, new dependency, artifact retrieval or installation authority is added. Existing provider cache bytes and APIs remain unchanged; source-bound registry publication precedes use of the additive shared interface.

The initial direct/final-URL adapter uses the additive shared `probe_https_location` HEAD-only boundary, with no GET fallback or response-content consumption. A final 200 response supplies only its admitted request URL; filename captures reuse zsync's local selection mechanism. Cross-host redirects require explicit bounded local host entries and still pass pre-request admission. The distinct 64-KiB URL cache stores original/final locations, reapplies current local host and selector policy on observation, and preserves failed probes without conditional-validator reuse. Neither response headers nor a constant opaque filename establish artifact identity, authenticity or installation authority. Existing source encodings and shared response interfaces remain unchanged; the additive source interface requires source-bound registry publication before downstream use.

The initial HTML adapter treats one bounded static response as a link inventory, extracting only inert HTTPS anchor references and deriving versions from local filename selectors. Relative references use the final admitted page location; remote base elements, visible text, scripts and download attributes do not supply candidate names or versions. The entire token stream is inspected before ranking, tokenizer errors and document-tree-dependent foreign/template/noscript contexts fail closed, and input/token/anchor/attribute/reference/release limits bound work. This is not browser DOM parsing, client-side rendering, pagination or an installation engine. Its distinct location-aware conditional cache preserves failed refreshes and reselects current local rules. Existing APIs and provider cache formats remain unchanged; the additive unreleased source interface requires source-bound registry publication before downstream use.

HTML introduces `html5gum` 0.8.4 because the existing XML parser cannot supply HTML raw-text, attribute and entity semantics safely. The MIT-licensed registry package publishes from `untitaker/html5gum`, source commit `d182efa7a6e315a4f38518697ba9addf3e8fc266`, with a locked checksum and no build script. Default features are disabled, leaving no enabled dependencies, DOM integration, SIMD dependency, async runtime or unsafe implementation feature. No public API exposes its types. License/source/advisory checks and target builds remain mandatory; binary-size and startup impact remain part of source-bound release qualification. No workspace edition or MSRV claim is changed, and no second HTTP, TLS, archive or cryptographic stack is introduced.

Signed-manifest authority names the trusted key, signed product identity, target and allowed artifact URL in local configuration; the catalog nickname and remote fields cannot supply those identities. The initial exact-URL adapter admits only one target in a source-bound v2 manifest. Acceptance state belongs to one product/target/trust authority stream and outlives evictable discovery caches. Changing a selector or cache key cannot reset accepted generations or permit replacement bytes for an accepted version.

The shared ledger's v1 authority identifier hashes a domain-separated encoding of product, target and normalized pinned root key. Its encoding is independent of the ledger document schema and accepted state, and a fixed compatibility vector protects durable lookup across updates. Products own state paths and first-use approval; the identifier is neither a signature nor permission to initialize missing state. Changing its encoding requires explicit migration rather than looking under a fresh key.

On Linux, `artifact-update trust initialize ID` is the explicit local first-use decision for the configured signed authority. It publishes an empty ledger beneath absolute `XDG_STATE_HOME` or the absolute home directory's `.local/state`, under `artifact-update/release-ledgers-v1/<authority-id>`. Existing ledger state is not replaced. Missing state blocks signed checks before retrieval; initialization cannot establish historical latestness or recover lost anti-rollback history. Signed checks retrieve metadata outside the lock, then reauthenticate and accept against the exact previously loaded ledger identity within the atomic transaction. Only durable commit permits a signed-metadata result; artifact-byte verification and installation remain separate.

`trust status ID` inspects authority-bound ledger presence without writes, locks or network. A failed initializer reports an unknown change state because publication may precede a durability error. First-use publication syncs the containing ancestor entries as well as the staged content and final directory rename; interrupted retries cannot skip ancestor durability merely because an entry already exists.

The Linux signed-metadata cache retains bounded original root and manifest documents separately from durable acceptance state. Signed check publishes this disposable evidence only after ledger commit; cache publication failure reports a failed check but never rolls back accepted generations. Local status reauthenticates the original documents against current local authority and requires an unchanged acceptance transition against the loaded ledger. Cache loss, configuration changes and valid-but-unaccepted metadata cannot initialize or advance that ledger. Only fresh evidence exposes an available version; installation stays unknown and unauthorized. A timestamp refresh is not a ledger change.

The shared ledger's read-only `verify_retained_metadata` boundary permits older signed manifests without rewinding online acceptance. Its supplied signed root must match the exact accepted root generation and digest; pairing a retained manifest with that root rechecks current signer revocation. Missing or superseded root evidence fails closed, as do future versions/generations and conflicting current-generation metadata or current-version artifact digests. This check establishes neither historical acceptance nor receipt ownership, artifact custody, freshness or rollback permission. Product adapters must additionally bind the verified version, length and digest to receipt-owned retained bytes before activation; this shared boundary alone is not a completed product rollback implementation.

The shared Linux `observe_versioned_installation` API provides a separate no-write receipt observation for status adapters. It never calls layout preparation or recovery, never creates a lock file, and fails immediately if the existing lock cannot be acquired. A pending journal requires an explicit recovery operation. Present receipts are checked against the declared layout, owner/mode, bounded artifact bytes and exact links while holding that lock. No receipt means only absence of managed evidence, not absence of an external installation. Products retain ancestor-trust policy and release authentication; this receipt observation alone does not authenticate a release or authorize an update.

The additive shared `apply_versioned_installation_if_unchanged` boundary compares the complete caller-observed receipt with current state while holding the installation lock through verification and activation. Expected absence requires no receipt. A mismatch, pending journal or receipt drift fails before candidate preparation/publication; the operation may create base directories and a lock, but does not implicitly recover or repair. Existing apply callers retain their recovery/repair behavior. Products own version policy, authentication and any independent ledger ordering; receipt equality is not a monotonic generation and does not detect a change away from and back to the same state. Local verification callbacks must not reacquire the installation lock or wait for its holder.

The additive shared `rollback_versioned_installation_if_unchanged` boundary likewise requires the complete caller-observed receipt under the installation lock before verifying or activating the retained candidate. It rejects journals and drift without implicit recovery or repair, and preserves the existing rollback API's recovery behavior. Rejection may create a lock file. The product still owns retained-release authentication, current trust and ledger ordering; receipt equality has the same change-away-and-back limitation as conditional apply. Verification callbacks perform bounded local work and must not reacquire the installation lock or wait for its holder.

The additive Linux `recover_versioned_installation_with_verification` boundary validates all prior/next journal receipts through a caller callback and checks bounded artifact custody before restoring links or removing the journal. It holds the installation lock throughout, rejects legacy adoption and unrelated receipts, and verifies current state without implicit link repair when no journal exists. Callbacks perform bounded local work without reacquiring this lock or waiting for its holder. Existing recovery callers are unchanged. Artifact Update's explicit `recover ID` supplies current-ledger signature authentication and exact configured alias binding under ledger-then-installation lock order. It performs no retrieval, execution, ledger acceptance or cache publication. A committed transition clears its verified journal; an interrupted transition restores its prior receipt-owned links or removes first-install journal-owned links. An error after entering this potentially mutating API reports unknown change state. Inactive candidate and orphaned staging cleanup remain separate work, and native crash acceptance remains required.

Unix installation-lock acquisition rechecks the named file's device/inode and the retained descriptor's link count after obtaining the lock. An opener that waited while uninstall removed or replaced the lock fails closed instead of mutating under a detached inode. This check applies to blocking and nonblocking acquisition; it does not establish native Windows lock custody or protect against an adversary already holding the same user's filesystem authority.

The Artifact Update status adapter applies that observer only to explicitly configured binary layouts, after checking ancestor custody. It distinguishes receipt-verified managed content from external alias entries, and reports `installed_version` separately from signed available-release evidence. Neither local receipt content nor an external filename grants signed release authentication. Absent managed evidence without a configured external alias remains unknown; malformed custody, receipt drift or pending recovery fails without repair.

When receipt-bound original signed documents exist beneath the configured data root's `release-evidence-v1`, Artifact Update additionally applies retained-metadata verification and exact version/length/digest binding before reporting signed installed content. Missing proof leaves the weaker receipt-content observation; present invalid proof or superseded root fails closed. These durable entries reuse the bounded signed-document codec, not the discovery cache location or freshness policy. Status never publishes or refreshes evidence and does not grant activation authority.

The initial Linux `artifact-update install ID` adapter admits only a configured native-target signed binary layout and an explicitly initialized ledger. It checks external ownership, receipt drift and candidate layout validity before artifact retrieval or durable acceptance. Shared candidate validation is network/filesystem-free; version components retain exact SemVer build metadata with `+` while keeping the 128-byte component bound and existing alias grammar. Downloaded bytes remain in private temporary quarantine until exact identity verification and fsync. After acceptance, local activation holds the ledger, then installation, then evidence lock; network and external commands never run under those locks. The ledger must still accept the metadata without change, and the complete observed receipt must still match. Candidate and retained proofs publish before activation. Retained manifests are paired with the accepted root and reverified, so a revoked retained signer blocks this initial upgrade path rather than silently discarding rollback protection. Successful online installation publishes disposable artifact bytes and then refreshes signed discovery metadata; a later cache error cannot undo activation. The CLI reports late uncertain changes as null. Abandoned-staging cleanup and native release acceptance remain incomplete.

The Linux `--offline` adapter reauthenticates configuration-keyed original signed metadata and requires an unchanged transition against the already initialized ledger before staging cached bytes. It holds that original ledger identity through activation without a ledger write transaction, preserving ledger-then-installation-then-evidence lock order. Content-addressed artifact files are not authentication evidence: bounded streaming verifies owner/mode/single-link custody and exact signed length/digest before use. Offline installation never accesses the network, publishes disposable cache entries or refreshes check time; an older timestamp does not prevent explicit reuse of accepted bytes and does not establish currentness. Missing cache entries block and corrupt entries fail closed. Online publication uses private synced no-clobber entries after activation and can report a concurrent collision without undoing installation. Separate `artifact_cache_changed` and `metadata_cache_changed` fields keep disposable publication distinct from durable installation changes. Native offline acceptance remains a release gate.

The Linux `artifact-update rollback ID` adapter now supplies that retained rollback implementation for explicitly configured native-target signed binary layouts. It requires both receipt-owned versions to authenticate under the exact current ledger root, holds the ledger guard through conditional installation rollback, and neither retrieves metadata nor rewrites the ledger or discovery cache. Missing or superseded proof fails closed. Success swaps active and previous versions, so a repeated invocation swaps them back. The `artifact-update-rollback-v1` result reports a network-free operation, false change on preflight rejection and unknown change after a potentially mutating activation failure. Abandoned-staging cleanup and native acceptance remain incomplete.

`VersionedLayout` can explicitly separate `bin_directory_mode` from its private data/versions `directory_mode`. Omission preserves the existing shared-mode behavior and serialized document shape; existing product callers retain that omission. Both effective modes must remain owner-writable-only and readable/traversable by the owner. Preparation, legacy adoption and read-only observation apply the mode to its declared directory role, never chmod an existing collision to make a new install succeed. Rust callers constructing the expanded layout supply `None` for the legacy behavior or an explicit mode for the new capability; external consumers require a corresponding shared-crate release before using this source interface.

One bounded Rust HTTP/TLS implementation owns HTTPS, allowed-host redirect policy, ETag and Last-Modified validation, 304 reuse, Retry-After and rate-limit handling, size limits, streaming downloads, timeouts, cancellation, and bounded global/per-host concurrency. A runtime replacement is accepted only through comparative startup, memory, binary-size, throughput, and p95 latency evidence; implementation fashion alone does not add a second network stack.

Redirect admission precedes each network request. Automatic client redirection is disabled; the transport resolves bounded locations with the shared standard URL parser, rejects prohibited origins and credential-bearing URLs before connection, and retains one deadline across all hops. Conditional validators belong to the initial resource and are not forwarded to a redirected resource. The URL parser is not a second HTTP or TLS stack; its dependency and binary-size impact remains part of release measurement.

The additive `fetch_conditional_json_https` boundary explicitly requests `application/json` while retaining that redirect, deadline, bounded-body and conditional-response machinery. Callers bind validators to both the exact URL and JSON representation and validate the returned bytes independently. Npm uses this path because its version endpoint returns a non-JSON string for an octet-stream request. Existing `fetch_https`, `fetch_conditional_https`, signed-resource and artifact transfer callers preserve their prior representation behavior; this is neither a host-specific npm branch in the shared transport nor a new HTTP stack.

The additive `fetch_located_conditional_https` interface retains the normalized final admitted request URL alongside the existing bounded conditional response. The redirect guard supplies location from its own request state, never from a server-provided location claim. Validators remain initial-resource-only; redirected 304 responses are rejected and redirected 200 responses retain no validators for replay against the original URL. Existing response types and interfaces are unchanged. `resolve_https_reference` is a separate pure URL-resolution helper using the same URL parser and syntax restrictions; it may produce a different HTTPS host as inert metadata but cannot extend request policy, fetch bytes, authenticate a release or grant installation authority. Relative-link adapters must retain the final resource location with cached bytes and reapply their local policy on observation.

The additive shared `fetch_artifact_to_staging` interface reauthenticates original signed metadata under caller-supplied release authority before any artifact request. It accepts only HTTP 200 and transfers through a fixed 64 KiB buffer, enforcing exact signed length and SHA-256 before successful writer flush. It does not accept a caller-constructed `VerifiedRelease` as authentication evidence. The writer is empty private quarantine storage: errors can leave unverified partial bytes, never publication permission. Callers retain durable anti-rollback acceptance, private-file custody, fsync, atomic publication, installation ownership and execution approval. A blocking caller writer is outside the HTTP timeout guarantee. Existing buffered APIs and callers remain unchanged; the [transfer probe](../artifact-transfer-measurements.md) measures this new path, not completed product integration.

The streaming API preserves its existing `anyhow::Result` signature and exposes downcastable `ArtifactTransferError` categories for authentication, invalid limits, transport, integrity and storage. Top-level display text and categories are value-free; an underlying diagnostic source may retain transport or I/O detail. Artifact Update maps operational transport/storage failures to exit 1 and failed authentication/content integrity to exit 4 without parsing error strings. Transport includes HTTP policy/request refusal and read errors; that category does not assert that a signature or digest failed.

The additive Linux `copy_verified_artifact_to_staging` installation primitive copies a local regular file through a fixed 64 KiB buffer, checks owner/mode/single-link custody and exact expected length/digest, detects observable descriptor metadata changes, and flushes the caller's quarantine writer before success. It reuses the no-follow, nonblocking file-open boundary and never publishes or executes bytes. The caller supplies authenticated identity and trusted ancestors and retains destination custody, fsync and publication responsibility. Failure can leave unverified partial quarantine bytes. This mechanism alone does not establish authenticated offline installation or native cache acceptance.

The existing cross-platform `publish_executable` copy phase is also capped at the caller-approved length, with at most one extra source byte inspected and never written. Short or growing sources fail before publication, while the existing post-copy digest check still rejects same-length replacement content. The public signature, no-clobber publication and caller-owned authentication/custody responsibilities are unchanged; source preflight alone is not a bound on a later copy.

The additive Linux `StagingArea` installation primitive reserves a dedicated private directory through an explicit no-clobber first-use publication. A bounded immutable `dev-tools-staging-reservation-v1` record binds a caller-owned 32-byte target identifier to one fixed quarantine payload; it is ownership evidence, not release authentication. Acquisition validates the record, root custody and closed directory inventory, then obtains a nonblocking native exclusive lease before removing a prior owner-only single-link regular payload and creating an empty payload. A busy lease never permits cleanup. The stable lock and reservation are retained. Unknown entries, mismatched target records and symlink/hardlink payloads fail closed without adoption. Successful explicit cleanup checks the retained payload identity before removal and directory sync; dropping the lease merely closes it and leaves residual payload bytes eligible for later explicit acquisition. Callers own ancestor trust, target-identifier policy and the lifetime of all work or duplicated descriptors using the payload. This cooperating-process protocol does not isolate a same-owner filesystem adversary. Cleanup of older unmarked files and unpublished initial-directory temporaries, and native release acceptance remain separate gates.

Artifact Update uses that reservation for online and offline installation quarantine under its existing native `artifact-staging-v1` root. The v1 target key hashes `artifact-update-staging-target-v1` followed by a NUL, then big-endian-u64-length-delimited artifact ID, native data-root bytes, native binary-root bytes and artifact filename, big-endian-u32 owner, and big-endian-u64 alias count followed by each sorted length-delimited alias. Release versions and unrelated configuration fields do not allocate a new reservation. Missing target directories are explicitly reserved; collisions are not adopted or blindly retried. Acquisition precedes artifact transfer, and the staging lease stays outermost around ledger-then-installation-then-evidence locks; no ledger or installation lock spans network work. Installation receipt equality remains required across independent staging roots. Early failure leaves recoverable reserved bytes without changing the durable-installation change contract. Success removes the payload explicitly; a late cleanup failure reports an operational error with known durable progress. Existing unmarked files and initial-publication or cache-publication temporaries are not deleted by this mechanism. Native signed-release crash acceptance remains required.

The additive Linux `StagingLease::publish_private_noclobber` boundary verifies the reserved payload against caller-supplied exact identity, syncs it, rechecks custody, and renames it without replacement between retained directory descriptors. The destination parent must already be a distinct private owner-only directory on the same filesystem; callers retain ancestor trust and authentication responsibility. The operation preserves mode 0600 and single-link identity, never makes the payload executable, and has no cross-device copy or hard-link fallback. Success syncs the destination and reservation directories. Failure after rename can leave published bytes and does not authorize blind retry or rollback.

Artifact Update's disposable artifact cache uses one reservation per content identity beneath `artifacts-v1/.publication-staging-v1`, named with the existing digest-length artifact filename. The target identifier hashes `artifact-update-cache-publication-v1` followed by NUL, the big-endian-u64-length-delimited native cache-root bytes, big-endian-u32 owner, the validated 64-byte lowercase hexadecimal SHA-256 and big-endian-u64 artifact length. Missing reservations are explicitly initialized; existing collisions are not adopted. A nonblocking lease spans the bounded local copy and publication, independently for each identity and outside installation and ledger locks. A failed copy leaves only its reserved payload for a later explicit save attempt; a completed publication moves that payload instead of creating another unmarked temporary file. Read-only cache staging never acquires a lease or recovers residual state. Reservation records and locks remain; their eviction, older unmarked files, metadata-publication temporaries and unpublished initial-directory temporaries are not covered by this recovery protocol.

The additive Linux `StagingLease::publish_private_document` boundary extends reserved publication to bounded private documents under an externally held stable writer lock. It verifies exact proposed payload identity and owner-only custody before checking the destination: equal bytes are unchanged, otherwise absence or the exact expected current identity is required before rename. It is compare-before-replace for cooperating writers, not filesystem compare-and-swap against the same owner or a monotonic generation. Successful replacement syncs the payload and both directories; a late failure may leave the new document published. Authentication, trusted ancestors, target binding and destination writer serialization remain caller-owned. Existing no-clobber publication callers are unchanged.

Artifact Update applies this boundary only to disposable provider and signed-discovery metadata, preserving existing cache bytes, timestamp framing and root-level `cache.lock` serialization. Each `.publication-staging-v1/<key>.cache` reservation binds the native cache-root bytes, owner and exact entry name through the SHA-256 domain `artifact-update-metadata-publication-v1` followed by NUL, big-endian-u64-length-delimited root bytes, big-endian-u32 owner and big-endian-u64-length-delimited UTF-8 name. An explicit save recovers only its validated reservation-owned residual payload, including when the destination already contains identical bytes. Loads, status and offline reuse do not inspect or clean reservations. Durable signed installation evidence retains its existing publication path; the shared codec does not merge its authority or lifetime with discovery caches. Unknown entries and busy or mismatched reservations fail closed. Older unmarked temporaries, interrupted first-use directory publication and retained reservation eviction remain outside this protocol.

The additive `calendar-tag` version rule supplies a bounded literal prefix and required locale-independent Gregorian format: exact zero-padded full dates with hyphens, dots or no separator, or year-month periods with hyphens or dots. It preserves the public unit-style `Calendar` rule and all prior valid version syntax. Comparisons use the parsed calendar period, never lexical ordering or guessed syntax; year-month ordering does not claim a release day. Observed version text strips only the exact prefix. Cached provider bytes are reselected under current local rules without changing their codecs. No date parser dependency, timezone behavior or authentication authority is introduced; the additive Rust variant and format enum belong to the unreleased shared interface and require source-bound registry publication before downstream use.

Version-rule unit variants and check-only verification deserialize their remaining map through a private empty struct with unknown-field rejection, preserving public Rust unit construction. The generic internally tagged unit visitor otherwise discards extra fields despite enum-level `deny_unknown_fields`. This correction rejects previously ignored options instead of treating misspelled format or verification declarations as effective authority; valid existing documents and persisted cache formats remain unchanged.

Artifact Update's additive local-only `completion SHELL` command emits static scripts for Bash, Zsh, Fish, Elvish and PowerShell without reading configuration, invoking sibling products or mutating shell startup files. Product-owned completion metadata describes only implemented commands and options; artifact IDs are not dynamically discovered. Generation runs only on the explicit completion path and preserves the existing parser. [ADR 0012](0012-static-product-completion-rendering.md) owns the shared rendering boundary, dependency choices and tested Bash compatibility adjustment. Standalone feature-isolation and binary-size qualification remain part of release acceptance.

Dev Auth adds the stable `--version` line and `build-info --json` common identity document through the existing core frontend dispatcher. Identity comes from build-time values, never runtime discovery, configuration or broker access; unsupported extra arguments fail before output. The no-argument build-info command and public library `BuildInfo` retain their existing three-field source-bound release-verification contract. Dev Auth owns that compatibility until release/setup consumers migrate to the common document and the last receipt-owned 0.3 rollback generation requiring the old shape leaves its acceptance window; executable release and rollback acceptance is the removal gate. This addition does not change authentication, frontend identity, setup approval or release-signing authority.

## Invariants

Its narrower ownership and compatibility contract supersedes the corresponding unpublished-initial-directory limitation above; unmarked legacy entries, post-publication product reconciliation and reservation retirement remain explicitly separate.

- Ordinary commands, `--version`, `build-info`, `doctor`, status, and rollback are network-free.
- Expired or absent release evidence produces `unknown`, not `current`.
- An external installation is never overwritten implicitly.
- Cache freshness defaults to 24 hours; a check is the only implicit metadata-network operation.

- Install and rollback replace only receipt-owned state and never infer authority from a filename or redirect.
- JSON output contains exactly one schema-versioned document and value-free failure kinds.
