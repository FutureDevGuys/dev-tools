# ADR 0099: Explicit native container build-cache scope

status: proposed
verification: pending

## Decision

Dev Cache adds an explicit `container-cache` command, separate from routed-cache filesystem GC. The first adapter targets a caller-selected Linux Unix-socket endpoint through Docker Engine API 1.51. Preview observes native engine identity, backend-locality evidence and build-cache accounting. Apply requires positive local-daemon attestation, the expected engine ID, exact `DockerRootDir`, rootless/rootful domain, and one to 32 distinct explicit cache IDs. A preview is an observation, not retained authorization or a filesystem deletion plan. Apply reobserves scope and records before issuing bounded, per-record native requests.

Native storage remains wholly engine-owned. The product never traverses, relocates, catalogs, renames or deletes that storage, and never puts it into `gc.rs`, automatic maintenance, intercept routing or the Dev Cache root. Images, containers, volumes, other Buildx stores, general prune and remote engines are outside this capability. Podman and non-Linux operation return unsupported without contacting a provider. No Docker CLI, Buildx plugin, context, configuration, environment-based endpoint, interpreter or temporary-directory prerequisite is introduced.

## Native selection and results

The provider must positively identify a Linux Docker Engine with an advertised API range containing 1.51. Apply binds its current identity to the caller's explicit expectations. Only known `regular`, `source.local`, `source.git.checkout` and `exec.cachemount` records can be eligible. Active, shared, unknown, malformed or ambiguously identified records never become candidates. Any present-but-ineligible selection rejects the complete selection before mutation. Selected IDs already absent from valid current accounting are clean no-ops and issue no POST, allowing an already satisfied apply to complete without change.

Each prune fixes `all=false` and combines one exact anchored ID regular expression, the freshly observed allowed type, and an empty-valued `private` presence filter. IDs are validated before interpolation. Moby joins these constraints with AND. Its `shared=false` and `inuse=false` string filters do not express the desired predicates: BuildKit exposes these as presence fields. Native locked reference checks protect active records; `all=false` excludes shared, internal and frontend records. The product retains its own preceding exclusions. These are native record-selection guarantees, not a promise about individual engine-internal files or paired cache metadata.

Successful responses retain provider-reported deleted IDs and reclaimed bytes, followed by fresh accounting. Missing or malformed accounting is failure, never fabricated zero. Explicit `BuildCache: null` is the provider's empty-list representation and is accepted; an absent field is not. The same required-but-nullable distinction applies to `CachesDeleted`. Record-size sums are estimates, not guaranteed physical recovery. Returned deleted IDs outside the single requested ID are an integrity failure. A batch may partially complete. Once a POST may have reached the engine, cancellation, timeout or an unusable response cannot establish no change. Results preserve confirmed progress and uncertainty, stop further mutation, and do not imply rollback or automatically retry an uncertain POST.

Provider-confirmed deleted IDs are retained before reclaimed-byte accumulation. A sum overflow fails the operation and reports `reclaimed_bytes: null`, preserving every confirmed deletion and established change instead of returning a misleading partial total.

Post-observation must not erase or overstate the native result. A provider-reported deleted ID still present afterward is a scope failure with established change preserved. A selected record still eligible after a successful no-deletion response produces an incomplete result, `native-prune-deferred`, with exit category 3. A record that became protected by active/shared state may remain without deletion and complete with the observed abstention. HTTP success alone never establishes that an eligible selection was satisfied.

## Narrow local protocol boundary

The adapter uses direct Linux Unix-domain sockets and a fixed HTTP/1.0 close-delimited JSON exchange. Socket inode/owner and `SO_PEERCRED` PID/UID/GID observations bind the connections in an operation. The complete request is written without half-closing the write side; the socket stays open until response completion, cancellation or deadline. The only product-generated requests are `GET /version`, `GET /v1.51/info`, `GET /v1.51/system/df?type=build-cache` and the fixed constrained `POST /v1.51/build/prune` form. There is no user-supplied URL, method, header, filter program, redirect, compression, IP, DNS or TLS transport. Unsupported HTTP framing fails closed. Socket-protocol work has a 120-second deadline, initialized after the initial socket canonicalization and custody checks; each GET has a deadline of at most 20 seconds within the remaining budget, and response capture is limited to 8 MiB. Connection establishment, writes and reads use 100-millisecond bounded waits to participate in cancellation and remaining deadlines. These deadlines and cancellation checks do not interrupt synchronous filesystem/procfs or executable-custody calls, so they do not guarantee a hard wall-clock limit for the whole command.

A local socket alone does not prove a local engine: an SSH or socat proxy could forward it elsewhere. Apply therefore requires readable `/proc/PID/exe` evidence for the `SO_PEERCRED` peer. The executable must have basename `dockerd`, be a root-owned ELF file, and be admitted by `dev-tools-command::HeldExecutable::open_with_validation` with root-owned executable and ancestors. The shared no-link rejection remains mandatory. Product validation additionally rejects every group/world-writable component, including root-owned sticky directories that the shared foundation can otherwise admit. The retained executable's device/inode must match the peer executable target metadata. The product reattests on each connection and rejects changed proof or scope before further requests. This reuses executable custody without spawning the executable or introducing a privileged helper.

Scope reports `backend_locality` as `verified-local-dockerd` or `unverified`, and nullable `daemon_executable`. Unreadable procfs evidence, a forwarding process, a user-owned daemon executable or otherwise unprovable executable custody yields unverified locality. Preview can still report accounting through that explicitly selected endpoint. Apply completes its initial version, scope and accounting GETs, then reports outcome `blocked` and exits 3 with `native-daemon-locality-unverified` before any POST when locality remains unverified; the result retains the useful observations. This gate also precedes already-absent selection handling. There is no trust override, operator assertion flag, helper installation or automatic elevation. Ordinary Docker-group access to a rootful socket may be read-only here because procfs executable access is independently restricted. A rootless daemon running a vendor-installed root-owned executable can qualify when its peer evidence is readable; rootless launch mode alone does not establish qualification.

Linux peer credentials reflect the process credentials captured when the socket was connected or began listening. An inherited or systemd socket-activated listener can therefore identify a process other than `dockerd`; that case remains unverified and read-only. Direct daemon-created listeners are the initial native acceptance target. No alternate peer inference silently admits activated listeners.

This attestation relies on the root-administered executable and native process boundaries. It is not signed-vendor provenance, a defense against a compromised trusted daemon/root administrator, or proof that engine storage uses a local filesystem. It does not relax the engine identity, native privilege-domain, socket custody or cache-record checks.

This ADR owns the product-standard exception for this narrowly scoped local HTTP-shaped native protocol parser. The existing audited ureq web transport does not directly supply the required bounded cancellable Unix-socket connection and custody boundary. Adding another general HTTP client, runtime or TLS stack would widen this local-only operation unnecessarily. This parser is product-owned, does not replace the shared update HTTP stack and must not acquire generic web-client functionality. Any additional endpoint, platform or remote transport requires a new review and qualification boundary.

The dependency audit adds a Linux-only `socket2` 0.6 edge, using already locked 0.6.5, and `ctrlc` 3, using already locked 3.5.2. Both are MIT/Apache-2.0 and retain their existing Cargo.lock registry checksums. `socket2` comes from `rust-lang/socket2` and supplies bounded native socket connection setup without extra features; `ctrlc` comes from `Detegr/rust-ctrlc` and supplies the cancellation flag without its optional termination feature. Neither adds an HTTP/TLS implementation, async runtime, command runner or new package version. Socket custody, provider admission, deadlines and mutation policy remain product-owned.

An initially considered `docker system dial-stdio` subprocess is rejected. CLI initialization adds implicit `/_ping` requests; finite staged stdin also causes an early socket write-half close, which can cancel a Go HTTP handler before its response. Using the existing bounded command foundation would bound the process but would not repair these native protocol semantics.

## Compatibility and verification

Existing routed caches, GC, root observation, interception and lifecycle behavior are unchanged. There is no existing native-scope state to migrate. Removing this command does not require filesystem or provider-state migration; already pruned cache is regenerated by the native builder, not restored by Dev Cache.

Public CLI/completion/conformance coverage and adversarial Unix-socket protocol fixtures must cover fixed destinations, missing data, explicit null, identity changes, blocked candidates, exact predicates, partial progress, framing bounds and cancellation. Forwarders, unreadable peer executables, untrusted executable custody and changed attestation must prove no POST; read-only accounting remains available when the provider observation is otherwise valid. Fake providers and successful builds establish source behavior only, and fake-socket apply tests must not introduce a production locality bypass. The [disposable native acceptance procedure](../dev-cache-native-cache.md#disposable-native-acceptance) must independently pass for each claimed rootful/rootless and storage-backend combination before native support is advertised. Native acceptance and installed-release qualification remain NOT RUN until evidence for the exact candidate is recorded.
