# Release Admin

`release-admin` is the planned standalone native authority coordinator for Dev Tools releases. It is compiled from the same focused Rust release, installation, product, and command foundations as the products it administers; it does not invoke repository Python tooling or accept ambient publication credentials.

The pre-acceptance command surface constructs canonical signed root documents from explicitly supplied offline root keys, reproducibly constructs shared registry packages, constructs source-bound multi-target product manifests and shared-crate authorization inventories through an operation-only signer, and verifies complete release sets without network access. `release-admin crate-set package` requires a clean canonical checkout at the exact declared commit, admits only regular tracked files, retains exact Git and Cargo executable identities, makes two private non-local clones, runs Cargo packaging offline in independent target directories, rejects symlinks and submodules, revalidates each archive, and publishes output only when both byte streams match. `crate-set build` binds each exact `.crate` file to its public package name, stable SemVer, declared source commit, registry, byte length, and SHA-256; `crate-set verify` requires the supplied packages to match that signed set exactly. The archive checks read the normalized Cargo manifest and VCS snapshot and reject dirty package construction, but Cargo's VCS snapshot does not itself prove derivation from source. Root private keys must be owner-owned, owner-only, single-link regular files on accepted Unix hosts. Routine signing receives only canonical public document bytes through standard input; the raw release key remains behind the configured signer. Linux is the first accepted build and signing host: it retains the exact tool executable by file descriptor and fails closed on platforms without an equivalent held-executable backend.

`release-admin set build`, binary publication, and crates.io upload remain unavailable until their native implementations pass the ADR 0003 acceptance contract. Reproducible package construction and crate-set construction are offline preparation and authorization steps, not uploads. Shared packages are constructed and published in dependency-order batches: dependency-free foundations first, then packages whose exact registry dependencies are anonymously visible. The product therefore remains at the conformance inventory stage and is not distributed as a supported public release.

The accepted target registry is fail closed. Release-candidate metadata is currently limited to `linux-x86_64` for `update-all`, `dev-auth`, `dev-cache`, `sync-configs`, and `skills-sync`; unknown products, `release-admin` itself, and every other target are rejected before signing. Constructing authenticated candidate metadata is necessary for native acceptance and is not a support or publication claim. Publication remains a separate admitted operation and requires the product's native acceptance gate.
