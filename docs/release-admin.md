# Release Admin

`release-admin` is the standalone native authority coordinator for Dev Tools releases. It is compiled from the same focused Rust release, installation, product, and command foundations as the products it administers; it does not invoke repository Python tooling or accept ambient publication credentials.

The pre-acceptance command surface constructs canonical signed root documents from explicitly supplied offline root keys, reproducibly constructs shared registry packages, constructs source-bound multi-target product manifests and shared-crate authorization inventories through an operation-only signer, and verifies complete release sets without network access. `release-admin crate-set package` requires a clean canonical checkout at the exact declared commit, admits only regular tracked files, retains exact Git and Cargo executable identities, makes two private non-local clones, runs Cargo packaging offline in independent target directories, rejects symlinks and submodules, revalidates each archive, and publishes output only when both byte streams match. `crate-set build` binds each exact `.crate` file to its public package name, stable SemVer, declared source commit, registry, byte length, and SHA-256; `crate-set verify` requires the supplied packages to match that signed set exactly. After publication, `crate-set verify-registry` authenticates the signed inventory, reads the crates.io sparse index anonymously through a fixed bounded HTTPS policy, rejects missing, duplicate, yanked, or checksum-mismatched versions, downloads from the exact crates.io artifact authority, and verifies every downloaded byte stream against the signed length and digest. The archive checks read the normalized Cargo manifest and VCS snapshot and reject dirty package construction, but Cargo's VCS snapshot does not itself prove derivation from source. Root private keys must be owner-owned, owner-only, single-link regular files on accepted Unix hosts. Routine signing receives only canonical public document bytes through standard input; the raw release key remains behind the configured signer. Linux is the first accepted build and signing host: it retains the exact tool executable by file descriptor and fails closed on platforms without an equivalent held-executable backend.

`release-admin crate-set bootstrap-publish` owns the one-time first-version crates.io path on accepted Linux hosts. It authenticates the signed inventory and every local package before reading standard input, verifies existing versions anonymously and skips exact matches, retains exact Git and Cargo identities, publishes from a private clean clone, and makes its private Cargo home select only the internal checksum-authorizing credential provider. The credential exists only in zeroizing memory and a sealed anonymous descriptor; the provider releases it only for the exact signed package checksum from the live held Cargo child. The token never enters argv, environment variables, a named file, Cargo credentials, a plan, receipt, diagnostic, or log. A successful upload is not complete until the sparse index and downloaded bytes verify anonymously. This command is a current-user bootstrap boundary, not hostile-same-user isolation, and is removed from routine use after each package configures crates.io Trusted Publishing.

`release-admin set build` and binary publication remain unavailable until their native implementations pass the ADR 0003 acceptance contract. Shared packages are constructed and bootstrap-published in dependency-order batches: dependency-free foundations first, then packages whose exact registry dependencies are anonymously visible. New versions use short-lived Trusted Publishing authority rather than the bootstrap token. Until the initial versions and their Trusted Publisher bindings are accepted, the product remains pre-release and is not distributed as a supported public release.

The accepted target registry is fail closed. Release-candidate metadata is currently limited to `linux-x86_64` for `update-all`, `dev-auth`, `dev-cache`, `sync-configs`, and `skills-sync`; unknown products, `release-admin` itself, and every other target are rejected before signing. Constructing authenticated candidate metadata is necessary for native acceptance and is not a support or publication claim. Publication remains a separate admitted operation and requires the product's native acceptance gate.
