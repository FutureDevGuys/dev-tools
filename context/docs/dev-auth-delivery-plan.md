# Dev Auth: complete the usable, general-purpose product

## Outcome and shared ownership

Deliver a standalone Rust CLI that applications, scripts, services, desktop programs and interactive users can use for authorized credentials and reusable privilege sessions. Explicit programmatic invocation and normal configured launch are equally supported. No new client SDK, MCP interface, public broker protocol commitment, private downstream dependency or bespoke workstation implementation is in scope.

Support policy-selected enrollment-authorized noninteractive admission and launch-time approval. Deliver task-scoped and separately approved general administrator sessions. Programmatic privilege requests specify duration; interactive approval can offer short and overnight choices within administrator policy. Activity, credential refresh and keepalive never extend the approved hard deadline. Remove the fixed eight-hour product-wide maximum without creating unbounded implicit authority.

Complete the initial 1Password Service Account implementation behind generic interfaces and prove the consumer contract with an independent test provider. Additional production providers remain future work. Shared crates own reusable mechanisms; each product compiles its dependencies and owns policy, setup and lifecycle. The separate 1Password MCP server is neither a dependency nor alternate Dev Auth authority.

Centralize reusable secret contracts, process execution, native execution primitives, privilege-session lifecycle/delegation, installation transactions, release verification, common results and completion rendering in focused Rust crates. Each public tool compiles the mechanisms it needs, supplies typed product policy and remains independently executable. Do not create a catch-all core or a required sibling-product service. Keep one 1Password adapter implementation; extract a focused shared adapter before another product needs it instead of copying it or putting provider-specific policy into the generic secret contract.

## Delivery sequence

1. Separate configuration validity, executable readiness/compatibility, enrollment presence, provider access and actual workload execution. Keep doctor local and network-free; add component-selectable explicit validation and versioned results. Provider-only validation must not invoke Git or gh. Aggregate checks report independent outcomes even after another component fails. Use existing enrollment through protected product interfaces and establish the first standalone candidate → admitted generic workload → logical resource → truthful result → cleanup path.
2. Finish shared retained-executable, native argument/stream, cancellation, deadline and cleanup mechanisms and integrate them into Dev Auth immediately. Complete V3 authority and all existing operation families through the same logical-resource resolution. Qualify cross-slot provider selection, enrollment, rotation, revocation, refresh, prompt-free store reads, projection custody and whole-workload cleanup with the real enrolled provider and an independent fake. Executable readiness or syntactic provider metadata never establishes online authentication or resource existence.
3. Make the successor broker's native Git/gh route authoritative. Preserve upstream syntax and native human passthrough; authorize admitted calls by native session and provider resource/permission scope. Do not globally downgrade gh, spoof its banner or extend the legacy command grammar/version allowlist. Keep executable custody separate from diagnostic version observations and concrete capability checks; no version subprocess or artifact hashing on ordinary hot paths. Qualify old/current releases, alternate banners, unknown arguments, API routing, subprocesses and denied-session no-fallback. Derived bearer tokens remain revealable by the authorized workload; never claim command-level containment from a banner or parser.
4. Complete continuation and structured binding execution and common journaled setup activation, then separately permitted pinned-shell bindings. Preserve wrappers, adjacent resources, complete native UID/GID identity, native argv, cwd/environment, mutable workspaces, terminals and signals. First qualify captured-byte projection in the existing strong full-identity service boundary; ordinary unprivileged Bubblewrap projection is not accepted as complete supplementary-group identity preservation. A failed required property reopens the mechanism before activation, not the requirement. Complete explicit refresh/rebind, cycle rejection, externally managed source proposals, owned removal and verified prior-generation rollback. Qualify generic CLI/script/service/desktop/editor/nested paths; Codex and Claude remain instances. User-only mode stays explicitly weaker and cannot silently replace failed strong admission.
5. Complete shared native privilege identity, authority registries, execution ownership, conserved narrowed delegation and teardown, then Dev Auth approval/policy/CLI integration. Support typed/exact-plan and separately permitted unrestricted sessions, disclosing workload, authority and finite deadline. Implement bounded executable DAGs, binary pipes, PTY/ConPTY, output limits and exit aggregation. Expiry, revocation, logout, policy/identity loss and broker failure deny new work and terminalize privileged descendants; failed cleanup is not successful revocation. Add Linux/WSL sudo convenience only after native enforcement passes, with passthrough outside a lease and no fallback inside a denied lease.
6. Complete stopped-broker V3 migration, interrupted forward binary installation, all policy/configuration writer coordination and active-broker teardown. Preserve enrollment, scope and admission choices. Qualify signed standalone fresh install, migration, repeat/no-op, upgrade, repair, interruption, recovery, rollback and owned uninstall. Use shared installation/release primitives for Dev Auth's setup-aware update surface and activate only after complete verification. Do not wait for unrelated product adapters.
7. Build equivalent Windows, WSL and macOS implementations and provide their native acceptance tests in that order. Share policy-neutral semantics and supply native credential-store, identity, IPC, process, terminal, approval and custody adapters. WSL never inherits Windows authority. The user selected Linux runtime acceptance for the current delivery and will run the other native suites later; those tests and build artifacts remain current deliverables. Required SDKs, signing and entitlements still constrain builds and distribution, and unrun native suites cannot establish platform support.

## Interfaces and acceptance

Extend existing workload/setup/status/explain surfaces and add secret and privilege command families. New control operations use versioned JSON and common exit categories; noninteractive input/approval requirements return promptly without a prompt. Execution preserves native streams and child status; optional structured results have an explicitly separate destination. Logical resource names are the caller interface. Operation-only private keys are not exportable. Session identifiers/environment hints never grant authority. Keep new parsing/help/completion definitions authoritative in one place.

Local doctor remains read-only and network-free. Explicit provider checks separately establish actual use. Extend workload/setup/status/explain and secret interfaces, component-selectable validation, explicit provider metadata discovery, and privilege request/inspection/execution/delegation/revocation. Discovery never exports credential values or turns provider access into workload authorization. Acceptance covers generic native programs, scripts, unattended services, desktop programs, nested shells and concurrent workloads; real GitHub/SSH/exportable-secret operations; prompt counts; token refresh; accelerated clocks and a real overnight grant; expiry/revocation/crash/logout/policy-change cleanup; wrong identity and copied hints; native arguments/streams/terminals/signals/wrappers; interrupted setup, rotation, upgrade, repair, repeat, rollback and owned uninstall. Tests, strict lint, formatting, relevant conformance, five-shell completions and existing performance limits accompany each independent slice. Record source, native, installed and released evidence separately.

## Migration and release

Changed authority schemas use stopped-broker migration: deactivate affected launchers, retain rollback inputs, validate new policy/release, install, verify and activate last. Preserve existing enrollment and scope; never silently enable automatic admission or general privilege during migration. Preserve exact 0.3.11 verification compatibility until its receipt-owned rollback window closes. Incompatible broker versions cannot communicate under the old protocol identity.

Use the existing service account as the credential source. Inspect declared resources first and use explicitly requested provider metadata discovery where permitted to prepare concrete, bounded acceptance inputs. Account access never selects arbitrary destructive targets or grants every available resource. Ask only for consequential choices that discovery cannot resolve. Prepare exact reviewable publication/enrollment inputs before user interaction. Do not substitute credentials or widen policy around a blocked native approval, signing or platform gate. Current completion requires a released independently installable Linux product with real authorized callers and Linux native acceptance, plus the other platform builds and runnable native tests for the user's later qualification; component tests, installed services and draft plans alone are insufficient.

Implement shared mechanisms together with their required product integration instead of accumulating unconsumed foundations. Preserve unrelated dirty work and frozen publication inputs. Broader shared-crate publication, updater adapters, Dev Cache lifecycle, Skills Sync improvements, Sync Configs defects and portfolio cleanup remain tracked deferred work; advance them early only for a concrete Dev Auth delivery dependency.
